Plain Language

Tether In Plain Words

Every actor placed in an Unreal level carries a hidden ID that the engine made up when the actor was placed. Think of it as a serial number. It's unique, it never changes, and when you place a room three times, each copy of the door inside gets its own.

A "Tether Ref" is a small note that holds one of those serial numbers, plus the door's name so the note still reads sensibly when the door isn't around. When the game needs the door, the plugin looks through the actors that have the tag and hands back the one whose serial number matches.

If two actors ever had the same serial number, the plugin refuses to guess and gives back nothing. Opening the wrong door would be worse than opening no door. The editor's checks tell you about the clash long before that.

For Engineers

The Technical Version

The identity is the engine's per-placement actor instance guid: the actor's ActorGuid, combined with the guids of the level instances above it. In the editor the plugin takes the engine's instance guid where one exists and folds that chain itself where it doesn't, which is a level instance open for editing. Nothing is minted. A ref picked at an actor in the owner's own level is stored relative. It holds the target's bare guid plus the level instances in between, and folds onto the owner's placement at resolve time. 

UPROPERTY(EditAnywhere, meta = (AllowedClasses = "/Script/MyGame.Door"))
FTetherRef TargetDoor;

if (ADoor* Door = UTetherLibrary::ResolveTetherRef<ADoor>(this, TargetDoor))
{
    Door->Open();
}

Resolution

Each UTetherComponent registers with a world subsystem as its level becomes visible and leaves when it's hidden or destroyed. A resolve is a hash lookup in that set by placement id, and returns one actor or null. Refs are equal when they point at the same actor the same way. That lets them work as TSet elements and TMap keys.

Packaged builds

A cooked build releases the engine's instance guid before gameplay runs. So during a cooking save, the editor module writes the live guid into the component, and restores the editor copy afterwards. At runtime the plugin reads that baked value, folding the level-instance guid back in for Standalone level instances. We verify this path from a packaged build. Embedded, Standalone, nested, classic, distance-streamed, and runtime-loaded level instances all resolve every reference to the right placement, and nothing lands on a wrong actor.

Validation

UTetherValidator runs under Data Validation. It indexes every loaded actor by placement id and checks each tag and each ref, including refs inside containers and components. Under World Partition it also reads the actor descriptors. That lets it tell "not loaded" apart from "gone".

Deep Dive

The Details Under The Details

This section is for the engineer who wants the exact number a ref holds, the path it takes into a cooked build, and the test measurements. Everything here is as of UE 5.8 and will drift as the engine does. The code is the final word.

The identity arithmetic

A placement id is FGuid::Combine(container, ActorGuid), where the container is the fold of the level-instance guids above the actor, outermost first, each combined onto the last. That's the same arithmetic as the engine's FActorContainerID, so the plugin lands on the value World Partition writes into ActorInstanceGuid for every flattened actor. An actor in the main level has no container. Its placement id is its bare ActorGuid.

A level's container follows one rule in both builds. If the level instance actor that owns the level is itself placed inside something, the container is that actor's own placement. Otherwise it's the engine's level-instance guid, which the editor folds from the actors instead of reading, since reading it registers the level. A level loaded as a renamed copy of its package, which is what ULevelStreamingDynamic::LoadLevelInstance makes, takes a guid from the name the game gave it instead. Without one, it takes a guid from its source level and the spot it was loaded at. Otherwise there is no container.

The owner rule exists for one shape: a Standalone level instance inside an Embedded one. The engine gives every placement of the outer one the same inner guid. Three rooms under three wings would hold three doors with one id. The room's level instance actor, flattened into the wing, carries the wing's term in its own instance guid. The room's level folds onto that.

Relative refs

The picker decides the form. It takes the level-instance chain of the owner and of the target. When the owner's chain is a prefix of the target's, which means the same level or a level instance nested in it, the ref stores the target's bare ActorGuid in TargetId and the chain below the owner in RelativePath, and sets bRelative. Otherwise it stores the absolute placement id. At resolve time a relative ref folds onto the owner's container, then through its path, then onto the actor guid. Equality and hashing include the form. A relative and an absolute ref to one actor are two keys.

The cook step

The engine serializes ActorInstanceGuid into every cooked actor and releases it in PostRegisterAllComponents, before any gameplay code runs. During a cooking save, OnObjectPreSave fires for each object. The editor module does two things while the value is still live. It writes each tethered actor's instance guid into its component's PlacementId. And on any actor the cook has flattened into a World Partition cell, it folds relative refs to their absolute form, since the game has no container for a cell to fold onto. Refs whose owner is in the main container stay relative, because a level cooking on its own learns its placement when it loads. Both edits are undone after each package saves and again when the cook finishes. No editor asset keeps a baked value. The cook log reports both counts.

At runtime GetBakedPlacementId folds the level's container onto the baked value. A Standalone level instance cooked on its own baked only the actor's half. The fold restores the placement. Embedded content baked the absolute value and sits in a level with no container. The fold adds nothing. It reads like a double combine. It isn't.

The capture window

The owner rule needs the level instance actor's own instance guid at runtime. The engine throws it away. The subsystem reads it in the window between load and release: in OnLevelBeginMakingVisible for a streamed level, and in its own Initialize for the persistent level, since subsystems come up before the persistent level registers anything and a cooked World Partition map keeps its flattened content there. It only captures from a level nothing owns. Inside a streamed level instance the engine derives a value without the terms above it. The owner rule folds those by hand. The capture is compiled out of editor builds, where the value is a live property.

The index

UTetherSubsystem keys every registered tethered actor by placement id. An actor is filed on the first resolve after it registers, which is the earliest its placement is known, since registration happens while its level instance may still be loading. One whose id isn't ready yet stays pending for the next resolve. Unregister removes it from its bucket. A bucket with two live actors resolves to null, which is the unique-or-null rule.

Validation, in full

UTetherValidator indexes every loaded actor by placement id once per run. Errors, which fail validation: a PlacementId saved in editor data, two loaded tethered actors sharing an id, a ref matching more than one, a ref to an actor with no component, a ref to a child actor, a ref outside its AllowedClasses, and in a World Partition world a ref matching no actor at all. For that last one it rebuilds every id from the actor descriptors as ContainerID.GetActorGuid(ActorGuid) and trusts the set only when every loaded tethered actor's live id is in it. Warnings: more than one component on an actor, a tethered actor with no guid, and a ref matching nothing loaded, which outside World Partition is the whole story and inside it means the descriptors couldn't be checked, as happens while a level instance is mid-load.

Verified so far

We test the plugin against the engine's own options, all aimed at the same door: a plain soft pointer, a hard pointer, an Editor Path, and a Universal Object Locator. The maps cover Embedded, Standalone, nested three deep, Standalone under Embedded, classic sublevels, a partitioned room placed Embedded, placements a kilometre apart with a moving streaming source, and a room loaded twice at runtime. Each runs in the editor and from a packaged build, judged by where the resolved actor is.

  • A tether ref resolves every placement in every map, in both builds. The only misses are from the start position of the wide map before a room has streamed in. Those hit once the player gets there.
  • Nothing resolves to a wrong actor, in any map, either build.
  • Editor Paths and the locator resolve Embedded placements in a packaged build and nothing else. Plain and hard pointers resolve nothing inside a level instance.
  • Editor edits behave: removing and re-adding the component, duplicating and deleting the door or the room, undo, redo, commit, swapping the world asset, and break. Every one gives null or the original, never a copy.
  • Saved and loaded: every door a ref hit on all five maps, saved to a slot, then loaded by a new process, in the editor and from a packaged build. Each build made 330 lookups, and all 330 hit. The first run had 4 wrong, in the runtime-copy case below, and the same day's fix closed them.

The ones that can name a single placement went on the same probe actor as a tether ref, all aimed at the same door, across five test maps. Each ran in the editor and from a packaged Win64 build, judged by where the resolved actor actually was. The rest we read from the 5.8 engine source and didn't probe.

In a save game

A tether ref saves like any struct. Tether.SaveGame writes refs to a real slot file, to memory, and through a game's actor-state archive, then loads them into a fresh world. They come back whole and resolve to the same placements. That test also found the one real gap: an actor-state save writes only fields flagged SaveGame, and the ref's fields weren't. They are now.

The probe then did it for real. On every map it saved a ref to each door it found three ways, quit, and loaded the slot in a new process, uncooked and packaged. The three ways are a ref made at runtime from the found door, a copy of the authored ref, and the owner's actor state.

Note:

A level loaded at runtime with LoadLevelInstance gets a package name with a load counter in it, unless you pass OptionalLevelNameOverride. The first run keyed copies on that name, so they traded ids when they loaded in a different order. A saved ref gave the wrong copy's actor rather than null. That's the one wrong result any of these tests has produced. A copy with a generated name now keys on its source level and the spot it was loaded at, which the game picks again next session. A name you pass yourself still wins.

Two runtime cases can't be keyed reliably, so Tether refuses them. One is an unnamed copy loaded at the same spot as another unnamed copy of the same level. The other is a World Partition world loaded at runtime with LoadLevelInstance. Making a ref to an actor in either gives an unset ref and a warning, and every resolve into them gives null. The probe loads both on purpose and checks every door, authored ref and runtime ref in them, plus the doors that should still work.

Limits

Limits

  • It points at things placed in a level, not things spawned while the game runs.
  • "Move to Level", "Create Level Instance", and "Break" give an actor a new ID. Refs to it need re-picking. Validation flags them.
  • Two placements of one room are two different targets. A ref picks one copy, never all copies of the door.
  • Resolve a ref from the thing that holds it. A relative ref folds onto its owner's placement. Resolving it from an actor in another level gives nothing.
  • An absolute ref saved against a level copy loaded at runtime finds it next session when the copy loads at the same spot or under the same name.
  • Refused outright: an unnamed runtime copy sharing its spot with another unnamed copy of the same level, and a World Partition world loaded at runtime. Refs into them can't be made and don't resolve.
