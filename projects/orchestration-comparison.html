Comparative reference — 2026-07-08

Four ways to structure an AI coding session

smartplan is one answer to "how should an agent plan and delegate work." feature-dev, pilotfish, and Superpowers are three others, each optimizing a different axis. This is where they agree, where they don't, and why.

smartplan feature-dev pilotfish Superpowers

What each one actually is

Same problem space — Claude Code, agentic coding sessions — four different shapes.

smartplan

Policy skill · this project

A tiering policy laid over whatever workflow you're already running: strong model plans, cheap models implement behind a verifier, escalate on failure. No runtime engine, no bespoke agent personas — a drop-in skill directory read natively by five different harnesses.

feature-dev

Claude Code plugin · Anthropic

A fixed 7-phase feature workflow — discover, explore, clarify, design, implement, review, summarize — run by three bespoke subagent personas (explorer, architect, reviewer), all pinned flat to Sonnet. Optimizes for thoroughness and human dialogue, not cost.

pilotfish

Global installer · third-party (Nanako0129)

A one-time install into ~/.claude/: six role agents (scout, executor, mech-executor, verifier, security-executor, Explore) each pinned to a model tier, plus a model-free delegation policy in your global CLAUDE.md. Not a workflow — a standing orchestration layer under whatever you do.

Superpowers

Skills library · third-party (obra)

Dozens of narrow, rule-heavy skills — TDD, systematic debugging, brainstorming, code-review reception, git worktrees — each an "Iron Law" enforced with red-flag tables and forbidden phrases. About how to work correctly, not about which model does the work.

The two axes that actually separate them

Cost-tiering and process-rigor turn out to be nearly independent — each project picked a different corner.

High process rigor

Six model-pinned roles, a delegation policy, an adversarial verifier. Almost no opinion on how the executor should work — TDD, debugging method, etc. are out of scope.
smartplan
Tiers cost and gates quality (brief → smartcheck → fail-twice escalation), but treats TDD/debugging discipline as the executing seat's own business — this policy stops at the leaf boundary.

Everything — explore, design, implement, review — runs on Sonnet. Real process (7 phases, confidence-scored review) with zero cost-awareness.
Superpowers
No model parameter appears anywhere in the library. Every subagent dispatch is process-first — TDD Iron Law, four-phase debugging, verification-before-completion — and silent on which model runs it.

The practical read: smartplan and Superpowers are less rivals than orthogonal — smartplan's own history backs this up. An earlier draft tried a formal interop seam between the two families and the author pulled it, on the grounds that "process skills stay inside seats" already holds without a bridge: nothing stops a smartplan executor leaf from also being a Superpowers TDD practitioner. The two just never had to agree on anything, because they're regulating different variables.

Planning & the human-in-the-loop

How much of the ask gets pinned down before code gets written, and how many times the human is asked.

ProjectPlanning shapeHuman checkpoints
smartplan Single plan on the planner seat (Opus default, drops on fit). A pre-plan clarification step resolves plan-shape ambiguity before the decomposition is finalized. 1 formal gate — the plan review — plus the folded-in clarification pass when the ask is ambiguous.
feature-dev Explore (parallel recon) → blocking clarifying-questions phase → 3 parallel architecture proposals (minimal / clean / pragmatic) synthesized with a recommendation. 4 — confirm understanding, answer all clarifying questions, pick an architecture, approve before implementation.
pilotfish None of its own — it's a standing policy, not a task flow. Whatever planning happens is the main session's normal behavior, just delegated per its role table. 0 — no workflow to gate. (The install itself has one: show the merge plan, wait for approval.)
Superpowers Explicit Socratic refinement (brainstorming skill): one question at a time, 2-3 alternatives explored with trade-offs, design presented in 200-300 word sections, each validated before continuing. Explicitly non-linear — designed to go backward. Many, by design — the whole point is continuous incremental validation, not a single gate.

The spectrum runs pilotfish (zero) → smartplan (one, sized to ambiguity) → feature-dev (four fixed) → Superpowers (continuous). Superpowers is optimizing for a human pairing closely with one session; smartplan is optimizing for a plan that then runs unattended across a wide fan-out — more upfront checkpoints would fight that goal.

Dispatch & parallelism

All four spawn subagents. What they spawn them for differs sharply.

ProjectDefault shapeParallel implementation?
smartplan Wide fan-out of disjoint-FILES plan leaves, sized 3-5 per wave, each a subagent with its own tiered model. Yes — the default. A hotspot file serializes; everything else dispatches concurrently.
feature-dev Parallel perspectives on the same question — 2-3 explorers, 2-3 architects, 3 reviewers, all reading or judging, not writing. No — implementation (Phase 5) is a single serial pass.
pilotfish No fan-out sizing of its own; dispatch decisions belong to whatever session it's installed under. Its own rule is just "set model explicitly on any ad-hoc fan-out." Unspecified — inherits the host session's judgment.
Superpowers Two named, opposite patterns: subagent-driven-development (one task's subagent, then a review subagent, then the next — explicitly serial) and dispatching-parallel-agents (reserved for 3+ provably independent bug investigations). Actively discouraged for implementation — "Never: dispatch multiple implementation subagents in parallel (conflicts)" is a named red flag.

This is the sharpest philosophical fork of the four. smartplan treats independent plan leaves as the default parallel unit and trusts contracts.md plus post-wave Integrate to catch the seams. Superpowers treats parallel writing as inherently conflict-prone and reserves concurrency for read-only investigation — serial-with-a-review-gate is its default execution mode, not an exception.

Verification & review

Every project has some form of "don't trust the executor's own report." The shape of that check varies a lot.

ProjectMechanismIndependence enforced by
smartplan smartcheck: fresh-context verifier re-runs ACCEPTANCE, diffs FILES against scope, issues PASS or a numbered FAIL tied to brief sections. Optional 3-verifier majority panel for high-value leaves. Prose rule ("never verify what you executed") + a hard rule against fixing.
feature-dev 3 parallel code-reviewer agents (simplicity/DRY, correctness, conventions), confidence-scored 0-100, reports only ≥80. One pass at the end of the whole feature, not per-leaf. Separate subagent context; no tool restriction.
pilotfish A single verifier role: adversarial, tries to REFUTE the claim, returns CONFIRMED/REFUTED with its own reproduced evidence. Tool-locked — disallowedTools: Write, Edit, NotebookEdit in the agent's own frontmatter. Can't fix even if it wanted to.
Superpowers Two layers: verification-before-completion ("no completion claim without fresh command evidence, run in this message") applies to every claim anywhere, not just leaves; requesting/receiving-code-review defines a full reception protocol — no performative agreement, technical pushback required, YAGNI-check on reviewer suggestions. Rule-and-vigilance, not tooling — reinforced by an explicit forbidden-phrases list ("You're absolutely right!").

pilotfish and smartplan converge almost exactly on independence-as-design-goal — smartplan's own reference file only recently gained an explicit tool-lockdown template for Claude Code, closing a gap pilotfish's frontmatter had closed from day one. Superpowers is the outlier in a different way: its rigor is aimed at the human-facing side of review (how you receive feedback, not just how you generate a verdict) — a dimension none of the other three touch at all.

Failure handling

ProjectWhat happens on failure
smartplan Fail-twice → escalate exactly one tier, ESCALATION REPORT artifact (task / tier history / evidence / hypothesis / next). At the top tier, the orchestrator takes the leaf over itself — there's nowhere higher to escalate to.
feature-dev No escalation ladder. Review findings go back to the human, who chooses fix-now / fix-later / proceed-as-is.
pilotfish "Two failed attempts, then escalate one tier or take over" — the same shape as smartplan's rule, stated as a policy line rather than a tracked artifact.
Superpowers A different axis entirely: systematic-debugging's escalation isn't about model tier, it's about giving up on incremental fixes. Three failed fix attempts on the same bug means stop and question the architecture with the human — treated as a wrong-foundation signal, not a strength signal.

Process discipline smartplan doesn't touch

smartplan deliberately stops at the leaf boundary — what happens inside an executor's own work is out of its scope. This is where that gap is most visible.

  • TDD as an Iron Law. Superpowers: no production code without a failing test first, no exceptions without the human's permission, delete-and-restart on violation. smartplan's brief format recommends TDD-shaped ACCEPTANCE as the strongest option, not a requirement — an executor can satisfy a brief without ever writing a test first.
  • Root-cause debugging as a named method. Superpowers' four-phase framework (root cause → pattern → hypothesis → implementation) is the only one of the four with any debugging methodology at all. smartplan's ESCALATION REPORT has a HYPOTHESIS field, but no process for producing one.
  • Structured code-review reception. Only Superpowers defines how to receive feedback — verify before implementing, ask before assuming, push back with reasoning, no performative agreement. The other three only define how to produce a verdict.
  • Socratic requirements-gathering. Superpowers' brainstorming skill is a full multi-turn negotiation with defined backward-navigation rules. smartplan's newly-added clarification step is a single fold-in, not a phase of its own.

None of this is a gap smartplan needs to close by importing Superpowers' rules wholesale — the two compose instead. A smartplan executor leaf dispatched into a Superpowers-equipped session would pick up TDD and systematic debugging for free, without either family needing to know about the other.

Persistence & distribution

ProjectLearns across runs?How it ships
smartplan smart-ledger.md (append-only outcome log) + a zero-model digest script that drafts floor reclassifications from measured bounce rates. Drop-in skill directory or plugin install. Zero standing footprint outside the project; portable across five harnesses.
feature-dev No — every run starts cold. Claude Code plugin via marketplace. Claude Code only.
pilotfish No outcome tracking — it's static configuration, not a run log. Global installer — rewrites ~/.claude/settings.json, adds six agent files, patches CLAUDE.md between markers. Heaviest install of the four; also the only one with an explicit uninstall/backup/update flow.
Superpowers Different kind of learning — not per-project outcomes but a community-editable skills library (meta/gardening-skills-wiki, sharing-skills): the library itself accretes technique, not any one project's run history. Plugin that clones a large external skills repo to ~/.config/superpowers/skills/, enforced by a mandatory session-start bootstrap skill. The most behaviorally invasive install — it actively polices phrasing and workflow adherence every session.

Where this leaves smartplan

smartplan's actual bet is narrow and stated plainly in its own honest-scope note: tiering lowers the bill, it doesn't shrink total tokens, and it only pays off on classes that bounce below roughly 20-30%. feature-dev bets on thoroughness at a flat, premium cost. pilotfish bets on the same tiering thesis smartplan does, arrived at independently, with less process around it but a cleaner enforcement mechanism (tool-locked agents) that smartplan only just caught up to. Superpowers doesn't bet on cost at all — it bets that most failures are process failures (skipped tests, guessed root causes, unverified completion claims), and that no amount of model strength fixes a skipped step.

The four aren't really competing for the same job. A session running smartplan for cost-aware fan-out, Superpowers' skills for how each seat actually works, and pilotfish's tool-locked verifier pattern for structural enforcement would be running all three theses at once, none of them contradicting the others.
