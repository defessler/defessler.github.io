Serving Local Models

llama.cpp, GGUF, quantization as block compression, the MoE trick that fits 120B in 32 GB, and the roster that staffs the stack.

The serving layer is where the hardware constraint gets negotiated with. Everything in this chapter answers one question: how do you get frontier-adjacent capability out of one 32 GB card. The answers rhyme with rendering engineering more than anything else in the stack: compression formats, working-set management, streaming, and cache discipline.

The engine: llama.cpp

llama.cpp (llama-server) is the inference engine, a C/C++ runtime that executes transformer inference with CUDA acceleration, no Python in the hot path. DokiDex runs a native Windows CUDA build (b9878 / CUDA 13.3, pinned in serving/llama-swap.yaml’s header) because native is the fastest single-user path on this hardware and WSL costs 20 to 40%. The flags that matter are load-bearing enough to name:

  • --jinja uses the model’s native chat/tool-call template with grammar-constrained decoding. This is the tool-call reliability story. Without it, agents built on local models degrade into prose-parsing hacks.
  • --flash-attn + --cache-type-k/v q8_0 pair an attention kernel with 8-bit KV cache quantization. That pair is what makes a 128k context fit the budget.
  • --cache-reuse gives prompt-cache reuse across requests. Measured on this stack: 92 to 99% of each agent turn’s prefill is served from cache, because every turn re-sends a history that’s identical except for the tail. Without this, a long session re-pays the whole prefill every turn. With it, turn latency is dominated by the new tokens only.
  • --n-cpu-moe N is the 120B trick, below.

There is more than one engine tree on disk. Mixing them up is a real failure mode. Three directories live under serving/: llama.cpp (the pinned tree, at b9878), llama.cpp-b10472, and llama.cpp-v4. Counting the real cmd lines in serving/llama-swap.yaml, 17 model rows launch from the pinned tree, 4 from llama.cpp-b10472, and 1 from llama.cpp-v4, for 22 model keys in total. Note the folder names are what they are. Don’t write a build number as a path: the pinned tree is serving/llama.cpp, not serving/llama.cpp-b9878.

GGUF and quantization: cooked assets and block compression

A GGUF file is a cooked model: weights plus metadata (architecture, tokenizer, template) in one memory-mappable file, the .pak of the LLM world. The interesting engineering is quantization, meaning storing weights at reduced precision. The right mental model is texture block compression, almost exactly:

  • Q4_K_XL (the daily-driver coder’s format) stores weights in blocks with per-block scales/offsets at ~4.5 bits per weight. It’s BC-style: quality loss is real but perceptually managed, and it’s the difference between a 30B model taking ~17 GB instead of ~60 GB in fp16.
  • MXFP4 (the heavy reasoner’s format) is a 4-bit floating-point microformat. The model was trained to tolerate it, which is why a 120B fits in ~63 GB total footprint.
  • Q8_0 for the KV cache exists because activations tolerate less error than weights. The cache gets 8 bits, not 4.

The discipline is empirical, not theoretical: when a Q5 quant of the daily driver was evaluated here, it never beat Q4 on the golden tasks (fidelity 99.3 vs 99.5, which is noise), while its VRAM footprint (94.3%) killed the headroom that autocomplete coexistence needs. Parked, with the numbers written down (docs/decisions.md). Compression settings are a shipping decision, and this repo treats them with shipping-decision rigor.

The MoE trick: 120B parameters, 3B at a time

Both flagship models are Mixture-of-Experts, which means the parameter count describes the library, not the working set. Qwen3-Coder-30B-A3B activates ~3B parameters per token. gpt-oss-120b similarly routes each token through a small subset of experts. If you’ve built virtual texturing, you already understand this: capability scales with the full library on disk, cost scales with the resident set.

That’s what --n-cpu-moe 22 exploits for gpt-oss-120b [128k] (Reasoning, Heavy): park 22 layers’ worth of expert tensors in system RAM (~40 GB of DDR5) and keep attention plus the hot path in VRAM (~27 GB). Experts stream across the PCIe bus per token. The result: a 120B-parameter model on a 32 GB card at ~27 tok/s. Not fast, but a completely different quality tier for planning and review work, and usable precisely because it’s cast in the planner seat, not the streaming-code seat.

llama-swap: level streaming for models

One model owns the card at a time (the Rule, chapter 1), but the stack needs many models. The answer is llama-swap (:8080), a proxy that exposes a single OpenAI-compatible endpoint and hot-swaps llama-server processes based on the model id in each request. Ask for gpt-oss-120b [128k] (Reasoning, Heavy) while Qwen3-Coder-30B-A3B [128k] (Coding, Light) is loaded, and llama-swap stops one process, starts the other with its exact tuned command line, waits for health, and forwards the request. Model switching becomes level streaming: expensive (seconds), automatic, and invisible to every client.

The config (serving/llama-swap.yaml) is a template, where __DOKI_ROOT__ placeholders are substituted at launch into .run/llama-swap.generated.yaml, so the whole stack survives a repo move. Model acquisition is a separate concern: media-assets/llm-model-catalog.json pins every download source with a SHA-256 (a hard-won rule after a truncated-weights incident), and serving/model-manifest.json drives the installer’s per-model opt-in checkboxes.

The roster

Every tier’s name is its id, since the 2026-08-25 rename dropped the high-fantasy-sci-fi call-signs this table used to carry (media-assets/llm-model-catalog.json’s old displayName fields, retired along with the aliases they decorated). The real model, its per-request context window in brackets, then what it is and what it costs you in parens: read the name and you already know what it does. The autocomplete and embedding rows below are identified by role, not by a display name, because they aren’t llama-swap rows and never carried an alias to lose.

The four everyday models

Four rows in serving/llama-swap.yaml cover a job rather than a specific bake-off question, so a task can be routed to the right weight class just by naming the row. As of 2026-08-25 there’s no alias standing in front of any of them:

  • gpt-oss-120b [128k] (Reasoning, Heavy), the heaviest thing on the box.
  • Qwen3.6-35B-A3B-MTP [128k] (Thinking, Standard), the seat and the strongest coder here.
  • Qwen3-Coder-30B-A3B [128k] (Coding, Light), the fast daily driver.
  • Qwen2.5-3B-Instruct [32k] (Utility, Free), the background slot. It was co-resident with the seat until 2026-08-26 and is not any more, so naming it evicts the seat unless you have switched to the utility preset.

Four matching skills live in harness/claude-skills/, one per model. Every model row’s name: field is the row’s own key, which is why /v1/models reports back exactly the string you’d ask for, with nothing to decode.

Two honesty notes baked into the tiers. The /effort dial maps to gpt-oss’s real reasoning rungs. There are three, so the CLI’s xhigh/max honestly reuse high and differentiate via tool-step and token budgets instead of pretending a fourth rung exists. And measurement showed high effort loses on gpt-oss-120b [128k] (Reasoning, Heavy) for coding tasks, because the extended reasoning starves the answer budget. The default stays medium by data, not by intuition.

Coexistence and parallel slots

coexist mode is the one deliberate double-booking: the daily-driver coder drops to its 32k-ctx row (64k ctx frees ~5 GB) so the autocomplete server can live alongside it, giving you agent + editor autocomplete simultaneously. And the lite tier runs -np 2, meaning two parallel server slots, because fan-out requests (the desktop app’s background summarizers, batched evals) parallelize with 99.98% prompt-cache reuse per slot. That was measured before adoption, like everything else here.

The rest of the fleet follows the same pattern: FIM autocomplete on :8012 and the CPU-only embedder on :8090. Own process, own health URL, one $Services entry each, group-tagged so the control plane can enforce the Rule.

The other kind of coexistence is the seat and its sidecar. Qwen2.5-3B-Instruct [32k] (Utility, Free) is deliberately small enough to sit on the card alongside the Qwen3.6-35B-A3B-MTP [128k] (Thinking, Standard) seat. A background or small-fast call doesn’t evict the ~27 GB model you’re actually working with.
