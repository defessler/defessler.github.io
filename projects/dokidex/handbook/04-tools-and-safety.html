:: THE GATE

GATE

Tools, Permissions, Safety

The authority model, and how an imperfect model gets real hands on your working tree without ever holding the keys.

Chapter 2 established the frame. The model is a client that requests. The harness holds authority. This chapter is that authority model in detail, because it’s the part that makes a local agent trustworthy enough to run against real source trees. It’s also where DokiDex’s engineering diverges most from “call an API in a loop” tutorials.

The mechanisms below were built and measured in this stack’s own agent, which is gone. The shapes are the ones every serious coding agent converges on, so they are described here as patterns rather than as one implementation. Original sources were tools.cpp (dispatch and gates), permissions.cpp (rules and the approval UI), checkpoints.cpp, and hooks.cpp. The desktop’s C# agent implemented the same shape independently.

The dispatch pipeline

Every tool call the model emits passes through one chokepoint, tools::dispatch(). A mutating call (write, edit, notebook edit, shell) walks this gauntlet in order:

tool_call
  → path containment      which root does the target live under? (or: none)
  → rule evaluation       persisted allow/deny rules, deny evaluated first
  → safety heuristics     destructive-pattern downgrades (can force Ask, never force Allow)
  → doom-loop guard       3rd identical call this turn re-prompts even under Allow
  → sensitive-target      permission-store/.doki writes: always interactive, even under bypass
  → approval              auto-approve if the mode allows it, else the y/a/n gate
  → checkpoint            snapshot the file before first mutation this turn
  → execute
  → undo journal          success-prefixed results push a single-step /undo entry

The ordering is the security argument. Deny rules are evaluated before allow rules and cannot be overridden by any mode, flag, or hook. A deny is a deny under --yolo too. Safety heuristics can only tighten a decision, never loosen one. And the sensitive-target check (anything that would rewrite the permission store itself, or the .doki config surfaces) refuses to be automated at all. The agent can’t grant itself permissions, the way a game client can’t grant itself authority by asking nicely over RPC.

Where a path is allowed to point

The workspace root is the process working directory, and every file-touching tool resolves its target against it. Relative paths resolve only against the primary root, with lexical .. normalization and a case-insensitive strict-prefix containment check. The sibling-prefix trap, D:\proj against D:\project, is a unit-tested case, not an afterthought. A path that lands outside every declared root classifies as external_directory, a distinct prompt class with its own approval language.

Multi-root is deliberate and narrow: --add-dir <path> (repeatable) declares extra working roots for a session. Extra roots grant file access only: no hooks, skills, or instructions are ever loaded from them, which is why they don’t need their own trust ceremony. There’s nothing for the trust gate to gate. The flag itself is the grant. Relative paths still resolve against the primary root only. You reach an extra root by absolute path, and the orientation tells the model the extra roots exist.

Modes: the four postures

The permission mode sets the default posture, and each mode owns a color that runs through the entire UI, across statusline, prompt and approval chrome. You always know the blast radius at a glance. This is the palette rule from the product’s design system doing safety work:

Mode Color Posture
ask grey-white every mutation prompts (the default)
plan cerulean read-only exploration. The exit_plan tool presents a plan and offers the gate out
auto orange in-workspace, non-sensitive edits auto-approve. Shell still prompts
bypass pink --yolo. Everything auto-approves except deny rules and sensitive targets, which survive even here

The approval gate itself is richer than y/n: yes · yes-for-this-session · always (persist a rule) · no-with-a-reason. The reason is fed back to the model as a machine-readable refusal, so a “no” teaches rather than just blocks. “Always” echoes the exact rule pattern it’s about to persist before committing it. Rules live per-workspace and are managed with /permissions.

Trust: the first-open gate

A freshly cloned repo can carry hooks (auto-executing), skills, instruction files, and MCP server configs (.mcp.json, which spawns processes). A careful agent treats these as a trust surface and runs trust-on-first-use, the same instinct as an editor asking whether you trust a downloaded plugin before it loads:

  • On first open of a workspace whose trust surface is non-empty, an interactive gate asks. The decision persists per-root (keyed by a hash of the canonical path) in a store outside the workspace.
  • The hooks file’s hash is recorded at trust time: if hooks change, trust refires. A trusted repo doesn’t stay trusted through a hostile edit.
  • Non-interactive contexts (piped stdin, IDE sessions on first touch) fail closed to untrusted rather than guessing.
  • /teleport (mid-session workspace switch) re-runs the full gate for the new root, never shortcutting off the old root’s cached answer.

The .mcp.json line item is there because an audit round found it missing. A workspace-local file that spawns processes wasn’t part of the trust surface. Found, fixed, and now it’s a probe in the parity ledger. That’s the pattern for this whole layer: the safety property isn’t “we thought about it,” it’s “there’s a selftest pinning it.”

Checkpoints: the transaction system

Two independent recovery mechanisms, deliberately not unified:

  • Checkpoints (checkpoints.cpp). Before a tool’s first mutation of a file each turn, the file is snapshotted into a session-scoped store. That store is git-independent, working in non-repos and surviving operations git would tangle. /rewind lists checkpoints and restores code, chat, or both, with supersede semantics so rewinding doesn’t orphan later states. Snapshots GC after 30 days (kCheckpointGcMaxAgeDays). If you’ve used Unreal’s transaction system, GEditor->BeginTransaction and the undo buffer, this is that, for an agent’s edits.
  • /undo is a single-step revert of the last edit, journaled at dispatch time. Small, immediate, separate, and kept distinct from the checkpoint system on purpose. One is a scalpel, one is a time machine, and merging them historically produces tools that are neither.

Hooks: lifecycle delegates

Hooks are the extension seam: user-supplied handlers bound to agent lifecycle events, exactly the shape of engine delegates (PreToolUse ≈ a validating pre-save handler):

Event Power
PreToolUse exit code 2 blocks the call. JSON stdout can allow/deny/ask or rewrite the tool’s input
PostToolUse can append context to the result the model sees
UserPromptSubmit can block a turn or inject context before it starts
Stop can force continuation with extra instructions at turn end

Handlers are declared in .doki/hooks.json, which is workspace-local only, with no global root (a global hook that runs in every repo is an attack surface with no matching need), trust-gated as above. Three handler types ship: command (a process), http (loopback-only POST), and prompt (templated). A fourth, agent, parses and validates but is a documented v1 stub. It warns at fire time rather than pretending, because wiring a model-invoking hook without its own prompt-injection review would be exactly the kind of quiet hole this layer exists to prevent. A separate statusline script hook (.doki/statusline*) feeds one JSON-in/text-out call per turn into the row above the prompt.

Why this much machinery

Because the failure mode of agent tooling isn’t the model being dumb. It’s the harness being credulous. A local model will occasionally emit a destructive command, target the wrong directory, or loop on a broken edit. Every mechanism in this chapter exists because one of those actually happened, and each fix landed with a selftest so it stays fixed. See --selftest-security, --selftest-checkpoints and --selftest-hooks, because the binary carries its own test suite (chapter 7). The result reads paranoid until you’ve watched an agent work unsupervised for an hour. Then it reads like the minimum.
