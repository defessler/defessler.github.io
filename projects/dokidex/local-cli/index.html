:: CLOUD CLIS, LOCAL WEIGHTS

Claude Code and Copilot CLI, on your own GPU

Run Anthropic's real Claude Code CLI and GitHub's real Copilot CLI against the models on your own card. No cloud, no proxy, no rewrite of either tool.

Beginner

This is the Claude Code CLI you already know, running against the GPU under your desk. It isn’t a clone or a fork. There’s no translation proxy in the middle either. llama.cpp’s llama-server implements the Anthropic Messages API natively and llama-swap routes it. Claude Code talks straight to 127.0.0.1:8080. The whole integration is a handful of environment variables. Nothing leaves the machine. There’s nothing new to install beyond the CLI itself either. GitHub’s Copilot CLI works the same way through its own BYOK setting. It needs no GitHub sign-in when a custom provider is configured.

This page is the short version, aimed at getting you working. The deep reference (every variable, why each one is set, the per-route flag-collision tables) is docs/local-cli-setup.md in the DokiDex checkout. DokiDex is a private repo. That file isn’t something you can open from here. Everything you actually need to run either CLI is on this page.

This page is the checkout path. The two launchers live at scripts/claude-local.ps1 and scripts/copilot-local.ps1. There is no app installer any more: the Electron shell that used to package a subset of the tree went on 2026-09-02 with the rest of the non-coding stack. Clone the repo, run setup.ps1, and everything on this page is present.

There is one smaller path, for a second machine. The bootstrapper bundle is an 82 KB archive holding the two launchers, the manager and their installer, for a box that talks to a DokiDex backend without carrying a checkout of it. It serves no models and it replaces nothing on this page.

Note: every command and every terminal capture on this page was run on the DokiDex development box against a live backend. The Claude Code captures and the residency listing were re-taken on 2026-08-26, after the seat moved to a 256k window. The Copilot capture and the shim listing are still from 2026-08-19 and each says so where it appears. Where a line is cited from a script instead of run, it says so and names the file. Model names throughout reflect the 2026-08-25 rename: every model is named for itself (real model, its context window, then what it is and what it costs you), with no alias standing in front of it.

1. What you need first

Three things. You probably have two of them already.

  • The DokiDex stack itself, so something is serving on 127.0.0.1:8080. See the CLI tutorial.
  • Anthropic’s Claude Code CLI on your PATH. If it’s missing, the launcher stops and tells you what to run: npm install -g @anthropic-ai/claude-code (scripts/claude-local.ps1:161).
  • Optionally GitHub’s Copilot CLI, if you want that one too: winget install GitHub.Copilot (scripts/copilot-local.ps1:143).

No API key, no account, and no sign-in for either client. The launchers set a dummy credential because both CLIs want a value in that slot. llama-swap never looks at it.

2. Get running

Bring the coder tier up first. It’s a separate process from the CLI. The CLI has nothing to talk to without it.

.\doki.ps1 up agent

There are two profiles, agent and coexist, and doki.ps1 up takes one of them. There was a third until 2026-09-02, media, which was mutually exclusive with the coding models and went with the rest of the non-coding stack. Then, from any project directory:

.\doki.ps1 claude

That opens the normal interactive Claude Code session. The capture below is a one-shot run instead, because the launcher prints the same header either way (scripts/claude-local.ps1:144-345 runs before the one-shot branch at :358) and a one-shot finishes on screen where you can read it:

.\doki.ps1 claude "Reply with exactly one word: ready"

Claude Code -> DokiDex local models
------------------------------------
  cleared   inherited: CLAUDECODE, CLAUDE_PID, CLAUDE_CODE_SESSION_ID, ...
  claude    2.1.246 (Claude Code)
  backend   http://127.0.0.1:8080  (not probed: a working run should not wait on a health check)
  model     Qwen3.6-35B-A3B-MTP [128k] (Thinking, Standard)
  tiers     every slot on the seat: 'Qwen3.6-35B-A3B-MTP [128k] (Thinking, Standard)' is not loaded, so nothing else was seated
  context   262144 tokens, auto-compact at 196608

  telemetry recording to D:\Projects\DokiDex	elemetry (doki-telemetry report to view, -NoTelemetry to skip)
[claude-code:unrecognized_model] {"model":"Qwen3.6-35B-A3B-MTP [128k] (Thinking, Standard)","query_source":"sdk"}
ready

Reading that top to bottom:

  • cleared is the launcher stripping variables it inherited from an outer Claude Code session, so a nested run can’t quietly talk to the wrong backend. If you’re not already inside Claude Code this line won’t appear.
  • backend is not probed. It used to be. The reachability check moved off the happy path (scripts/claude-local.ps1:333) because it cost a round trip on every launch to catch a case that fails loudly anyway. If nothing is serving, the first request errors and the fix is .\doki.ps1 up agent.
  • tiers is the honest one. Claude Code’s opus, sonnet, haiku and fable aliases each get pointed at a real local model. When nothing is resident yet, they all land on the seat, and the launcher says exactly that rather than implying a tiering that isn’t happening. Section 5 covers what this costs and how to avoid it.
  • context is read from the [256k] in the model’s own name. Auto-compact is set to Max(100000, ctx * 0.75) (scripts/claude-local.ps1:573), which is 196,608 here.
  • [claude-code:unrecognized_model] is normal and harmless. Qwen3.8-27B [256k] (Candidate, Standard) isn’t one of Anthropic’s own model ids. Claude Code notes that it doesn’t recognize the name and carries on.

The first run on a cold card pauses before any of this finishes. The seat loads three files off disk, 17.6 GB between them, and that took about 35 seconds measured across nine transitions in telemetry/residency.jsonl. It’s a one-time cost per load, not per turn.

Running it from anywhere

Typing .\doki.ps1 means being in the DokiDex checkout. One script puts a pair of shims on your User PATH so you can launch from any folder:

.\scripts\install-clients.ps1

It needs no elevation, writes only to HKCU\Environment, and is idempotent in both directions. -Uninstall takes it all back out. Here’s a real second run (2026-08-19):

DokiDex local-model CLI shims
------------------------------
  pwsh      C:\Program Files\WindowsApps\Microsoft.PowerShell_7.6.5.0_x64__8wekyb3d8bbwe\pwsh.exe
  claude    C:\Users\<you>\.local\bin\claude.exe
  copilot   C:\Users\<you>\AppData\Local\...\copilot.exe
  doki-claude.cmd already current
  doki-copilot.cmd already current
  doki-shim.ps1 already current
  D:\Projects\DokiDex\scripts\shims already on your User PATH

Already installed. Nothing changed.
  Open a NEW terminal (this one already has its PATH), then:
    doki-claude                 interactive Claude Code on the Qwen3.6-35B-A3B-MTP [128k] (Thinking, Standard) seat
    doki-claude -Task "..."      one-shot
    doki-claude -- -r <id>      short CLI flags go after the divider
    doki-copilot                the same for GitHub Copilot CLI
  Both need the backend up:  .\doki.ps1 up agent

The shims are named doki-claude and doki-copilot, never claude and copilot. Your ordinary cloud clients keep working, untouched, from the same terminal. That’s deliberate. A same-stem .exe beats a .cmd in the same directory anyway. A shim named claude would be shadowed at best and would hijack the cloud client at worst.

A fourth shim points the other way. zai-claude runs Claude Code on z.ai’s GLM models, cloud and billed, with nothing local involved: no GPU, no model swap, no lease. It keeps your global config, since a cloud run is the home configuration. The key lives in a key file (%USERPROFILE%\.claude\zai.key) that only this launcher reads, so your settings.json carries no GLM configuration at all and a plain claude never touches the paid endpoint. Every tier the launcher recognizes carries the same (Nature) category tag as a local row name, in the banner and in Claude Code’s own /model picker, whose entries would otherwise read “Custom Opus model” over bare ids. It also sizes the session’s context window from each model’s real limit (1M for the 5.x generation, 200K for the budget tiers) instead of the client’s stock 200k guess. zai-claude -Models lists the whole GLM catalog with a one-line good-for summary for each model. The launcher is scripts\claude-zai.ps1, and its header is the full documentation.

Tip: open a new terminal after the first install. The one you ran it in already resolved its PATH and won’t see the new entry.

3. Doing actual work

Four shapes cover almost everything.

A one-shot task. Give it a prompt and it runs, prints, and exits.

.\doki.ps1 claude "fix the off-by-one in the pagination helper"

Measured, that reaches claude as --print -- "fix the off-by-one in the pagination helper". The --print is what makes it one-shot. The -- guard is what keeps a prompt starting with a dash from being parsed as a flag.

An interactive session. Drop the prompt and you get the normal REPL:

.\doki.ps1 claude

Resuming. Both of Claude Code’s own long flags forward as typed:

.\doki.ps1 claude --continue
.\doki.ps1 claude --resume 0cb916db

Measured, those reach claude as --continue and --resume 0cb916db. Nothing is rewritten on the way through.

Passing anything else. Every long flag forwards verbatim and in order. --dangerously-skip-permissions, --output-format, and the rest all work the way the CLI’s own docs describe them.

.\doki.ps1 claude "fix the parser" --dangerously-skip-permissions

That one arrives as --dangerously-skip-permissions --print -- "fix the parser". Flags first, prompt last, which is the ordering that keeps a forwarded flag from being read as part of the prompt text.

The -- divider, for short flags

This is the one rule you’ll hit and want to know in advance. Single-dash short flags collide with the launcher’s own parameter names, because PowerShell binds parameters by prefix and does it before a single line of the launcher runs. -r, -c, -p, -d, and -v all get eaten. The launcher carries the full letter-by-letter table (scripts/claude-local.ps1:36-44). Put a literal -- in front of them and everything after it forwards untouched:

.\doki.ps1 claude -- -r 0cb916db
doki-claude -- -r 0cb916db

Both are measured to reach claude as -r 0cb916db. The quiet one is -r without the divider. The flag itself vanishes while its value survives as a bare token. -r 0cb916db then arrives as 0cb916db, which is a prompt where a resume was meant. Long flags never need the divider.

Common trap: through the doki-claude shim, a bare quoted string is forwarded as-is rather than turned into a one-shot. Use -Task there instead. doki-claude -Task "fix the parser" is measured to reach claude as --print -- "fix the parser", the same as .\doki.ps1 claude "fix the parser".

Your global config is never touched

Claude Code’s /model picker persists whatever you pick into the global %USERPROFILE%\.claude\settings.json. A local tier written there makes every other terminal’s plain claude exit 1 at startup. That isn’t hypothetical. It happened on this box on 2026-08-18.

So the launchers redirect the whole per-user surface to %LOCALAPPDATA%\DokiDex\claude-home and ...\copilot-home for the run, seeded on first use. Your CLAUDE.md, skills, and agents are shared across. Sessions, history, and credentials deliberately are not. .\doki.ps1 doctor also reads the global file and warns if something has pinned a local tier there.

4. Copilot CLI, the other seat

Same idea, same backend, different agent:

.\doki.ps1 copilot
.\doki.ps1 copilot "fix the parser"
pwsh -NoProfile -File .\scripts\copilot-local.ps1 -Task "fix the parser"

A real run of the third one (2026-08-19, when the seat still had a 104k window):

Copilot CLI -> DokiDex local models
------------------------------------
  copilot   GitHub Copilot CLI 1.0.80.
  backend   http://127.0.0.1:8080  (23 models, openai wire)
  warming Qwen3.8-27B [256k] (Candidate, Standard) (first load pages the weights off disk; this can take a minute) ...
  ready     Qwen3.8-27B [256k] (Candidate, Standard) answered
  model     Qwen3.8-27B [256k] (Candidate, Standard)  (78848 prompt / 26624 output tokens)

ready

Changes    +0 -0
Duration   9s
Tokens     ↑ 16.0k • ↓ 56
Resume     copilot --resume=a8601382-3bde-4ac0-86a8-4bc15c6cae23

Copilot’s one-shot form adds --allow-all-tools on your behalf. A -Task run is unattended by design. Bear that in mind before pointing it at a directory you care about.

Which one should you reach for? They’re different agents with different tool sets and different prompting, sharing one local backend. It’s genuinely a per-task call. A few concrete differences worth knowing:

  • Wire format - Claude Code talks the Anthropic Messages API at :8080. Copilot defaults to OpenAI chat-completions at :8080/v1. Passing -ProviderType anthropic moves it onto the same Messages endpoint Claude Code uses. llama-swap serves both shapes, which is why neither client needs a translation proxy.
  • Context sizing - both launchers read the window from the [Nk] in the model’s own name, so neither can drift from what the server is actually serving. The seat gives 262,144 tokens today. Copilot isn’t in GitHub’s built-in context catalog under a local model id, so deriving it from the name is the only way it fits at all. The capture above shows the 104k figures because it predates the window move.
  • Network posture - -Offline sets COPILOT_OFFLINE=true, which turns off GitHub contact, telemetry, MCP, and auto-update in one switch (scripts/copilot-local.ps1:96,261). If zero outbound traffic is the point of the exercise, that’s the flag.
  • Sign-in - neither needs one. Copilot’s own help states that GitHub authentication isn’t required when a custom provider is configured, which is what makes this work on a machine that has never signed in.

The same -- divider rule applies, with a different collision set. -a, -b, -n, -o, and -t bind to launcher parameters. -m and -p hard-error as ambiguous (scripts/copilot-local.ps1:38-50).

5. How the stack actually works

You don’t need this to use either CLI. It’s here because “it just runs locally” hides four moving parts, and knowing them explains everything odd you’ll see.

The four layers, top to bottom

  Claude Code / Copilot CLI          the agent. unmodified, off npm or winget
        |  HTTP to 127.0.0.1:8080
  llama-swap                         a router. picks a model, starts and stops it
        |  spawns, one process per model
  llama-server (llama.cpp b10472)    the inference engine. speaks both wire formats itself
        |  reads
  a .gguf file on disk               quantized weights, 19 GB for the seat

There is no translation proxy anywhere in that stack, and that’s the unusual part. llama.cpp’s llama-server implements Anthropic’s Messages API natively, so Claude Code’s requests are served as they arrive. Copilot’s OpenAI-shaped requests are served by the same process on the same port. The whole client-side integration is a handful of environment variables (ANTHROPIC_BASE_URL at scripts/claude-local.ps1:366, the tier variables around :497-515). Nothing rewrites a request in flight, which means nothing can silently mangle one.

Layer 2: why a router at all

One 32 GB card holds one useful model at a time. llama-swap’s job is to notice which model a request names, start it if it isn’t running, and stop whatever was running before.

That “stop whatever was running” is the expensive part, so the config groups models that should coexist. The agent-seat group sets swap: false so its members stay resident together, exclusive: true so nothing outside the group runs alongside them, and persistent: false so the whole group still unloads when a model outside it is asked for.

Measured cost of getting this wrong: a load takes a median of 35 seconds (15 unload-to-load transitions in telemetry/residency.jsonl, thirteen of them between 15 and 60 s, plus two outliers at 125 and 448 s), and a request that arrives mid-swap pays all of it plus a cold re-read of the conversation. One recorded example took 46.1 seconds to produce 91 tokens, re-reading 26,216 of them first. A mid-session swap costs roughly twice the load time alone.

The good news is they’re rare once a session is running. Inside a continuous stretch of work, the only model transitions in the log are deliberate probes and tests.

Stated carefully, because an earlier version of this page overstated it: the residency log that records loads and unloads was blind for 13.8 hours of the window measured, and the served model demonstrably changed during one of those gaps. So “rare” is what the request log supports. “Zero” is not, and reading a silent log as a measured zero is the exact mistake this project keeps a test suite to catch.

Layer 3: the seat, and why it’s a slow model on purpose

Qwen3.8-27B [256k] (Candidate, Standard) is the model itself at Q4_K_M, no alias in front of it. Its row is the one keyed by that exact name in serving/llama-swap.yaml, named rather than cited by line because the line moves every time the file grows. It won the seat on the 23-task coding suite that existed then, as the only candidate that cleared the project’s own gate. The suite has since grown to 26 tasks (three image tasks added around 2026-08-30).

It is also, measured, one of the slowest models on this box. gpt-oss-20b decodes about 3.4x faster. The quick ones are mixture-of-experts models, where only a fraction of the weights work on any given token. The seat is dense, so all 27 billion parameters take part in every token. That’s the whole trade, and the performance data page has the full comparison across 19 models.

Three things claw that speed back.

Speculative decoding, worth a measured +24% at depth. A small draft head guesses the next few tokens and the big model checks them all in one pass, which is far cheaper than generating them one at a time. The seat runs --spec-type draft-mtp --spec-draft-n-max 3 against a separate draft file (serving/llama-swap.yaml:773-775). Draft acceptance is 0.5245 on the benchmark corpus and 0.70 on real traffic, and the gain measured 2026-09-03 at 131k depth on the shipping seat is 54.7 tok/s with the draft head against 44.1 without it, a 1.24x multiplier. An earlier pass through this harness reported +42.9%, +43.6%, and roughly 57% of the draft head’s own theoretical ceiling. Those figures are retracted: they ran against a bench-corpus file that topped out at 7,840 tokens, on the stock weights this stack shipped before the 2026-08-29 abliterated swap, not the seat running today.

A quantized KV cache, which made the window bigger and cheaper at the same time. The conversation is kept at q4_0 rather than f16 (:776-777), a quarter of the size. The seat now holds 262,144 tokens using 910 MiB less memory than the 104k f16 configuration it replaced.

The model’s own shape helps here. Reading the GGUF header directly: 64 blocks, but full_attention_interval = 4, so only 16 of them carry a KV cache at all. The other 48 are recurrent. That works out to 18,432 bytes per token, or 4,608 MiB for the entire 256k window. A conventional dense 27B would need several times that.

Layer 4: prefix reuse, and the one place it fails

Normally every message re-reads the whole conversation from scratch. llama-server keeps the previous read and continues from where it stopped. Inside a session this works extremely well: a warm request freshly reads a mean of 613 tokens against a roughly 27,000-token conversation.

Across sessions it does nothing at all. Measured on this repo’s own telemetry, 232 requests re-read a full ~26,000-token prompt from cold, and those account for 87% of every token this stack has ever prefilled. That is the single largest cost in the whole system.

How much time it costs depends on which prefill rate you anchor to, and the honest range is wide: roughly 31 to 98 minutes out of a six-hour stretch. It went unnoticed for a while because the dashboard’s own reuse metric was computed wrong and read 100% on 84% of requests. Both the defect and the candidate fixes are written up in research/bottlenecks-2026-08-26.md, along with the claims that did not survive adversarial checking.

Worth knowing, because it sets expectations: a fresh session starts slow and a continued one starts fast. --continue is not only a convenience.

Serving configurations, and what each costs

The seat’s flags aren’t a single fixed answer. doki-manager config (which delegates to scripts/doki-preset.ps1) switches between three measured configurations and prints the free VRAM it expects from each:

  • mtp - seat plus speculative decoding, nothing else resident. The fastest that fits, and still the tightest of the three, though no longer marginal. It measured 1,045 MiB free under load on 2026-08-26, inside this box’s own 818 MiB of desktop drift. Two flags landed the next day, -np 1 and a q4_0 draft cache, and gave back 1,456 MiB between them, so the real figure is a few thousand rather than one. This is the default.
  • utility - seat plus a small co-resident model, no speculative decoding. The most headroom, and the conservative choice. Roughly 19% slower to decode at depth (the inverse of the +24% the draft head buys, above).
  • compat - the pre-2026-08-26 configuration, a 104k window with an f16 cache. Kept for A/B against older scorecards. It uses more memory than 256k q4_0 and compacts sooner, so there’s no measured reason to run it day to day.

The mtp default is why the tiers line in section 2 says every slot landed on the seat. Nothing small is co-resident to receive the cheap background calls, so they go to the seat instead. Under utility there is one, and the launcher seats haiku on it once it’s loaded.

One honest caveat on that. The launcher only seats a cheaper tier if it finds one already resident (scripts/claude-local.ps1:444-470), and preloading is off by default, so on a cold launch every tier lands on the seat regardless of preset. Running doki-manager warm first, or passing -HaikuModel explicitly, is what actually collects the benefit.

Nobody has measured what that is worth. An earlier draft put a number on it and had to withdraw it: the measurements available come from a benchmark harness that bypasses this launcher entirely and pins every tier itself, on purpose. So this is a real rough edge with an unknown price, not a quantified one. research/bottlenecks-2026-08-26.md records what it would take to settle.

What the server reports about itself

/v1/models and /running return a model’s own name: field, and since the 2026-08-25 rename that string is identical to the key. Nothing to decode:

(Invoke-RestMethod http://127.0.0.1:8080/running).running |
  Format-Table model, state, name -AutoSize

model                                   state name
-----                                   ----- ----
Qwen3.8-27B [256k] (Candidate, Standard) ready Qwen3.8-27B [256k] (Candidate, Standard)

That’s live, on 2026-08-26, immediately after the one-shot in section 2. One model resident, which is the mtp default. The server offers 25 models in total today and runs whichever you name.

6. What it costs you

Three honest constraints. None of them is a dealbreaker. All three are better known up front.

One model on the card at a time. 32 GB holds one seat, and naming a different model evicts the one that is loaded and pays a multi-gigabyte reload. There were two mutually exclusive groups until 2026-09-02, when the image and video half of the stack was removed along with its media profile (see archive.md). What is left is agent and coexist, and the budget underneath them is unchanged. The launcher drops a lease file for the life of a Claude Code session so doki can warn you before it pulls the weights out from under a live turn. That warning is best-effort by design. It won’t stop you.

VRAM headroom is thin, though less thin than it was. The mtp default measured 31,562 MiB of the card’s 32,607 MiB under load on 2026-08-26, leaving 1,045 MiB free, which is inside this box’s own 818 MiB of desktop drift. -np 1 and a q4_0 draft cache landed on 2026-08-27 and gave back 1,456 MiB between them, so that figure is the floor of what this preset costs rather than a current reading. doki-manager config utility trades the +24%-at-depth decode for more room again if you’d rather have it, and doki-manager config prints what is actually free right now instead of remembering a number.

Three things follow, and all three are worth knowing before you tune anything:

  • WDDM oversubscribes rather than fails. On Windows an over-budget load doesn’t error, it silently spills to host RAM and keeps answering, slower. A service that starts successfully is not by itself proof that it fit. Measure a footprint by the solo-delta method, never by whether it launched.
  • Per-process VRAM isn’t readable here at all. nvidia-smi --query-compute-apps returns [N/A] for used_gpu_memory under WDDM, which is why every figure in this project is a whole-card reading stated against a baseline.
  • These are one 32 GB card’s numbers. Smaller-card guidance exists in the repo but is unverified, because there’s no smaller card on this machine to measure it on. Treat it as untested until someone measures it.

Ctrl+C through the .cmd shim is untested. cmd.exe classically queues “Terminate batch job (Y/N)?” when a batch file receives a Ctrl+C. Ctrl+C is also Claude Code’s own interrupt key. The session that built the shims had no interactive terminal to press it in. So this is documented rather than claimed to work (scripts/shims/doki-claude.cmd:11-12). If it bites you, skip the shim and run the launcher directly:

pwsh -NoProfile -File .\scripts\claude-local.ps1

One caveat on that route. pwsh -File hands -- to PowerShell’s parameter binder. No short flag survives it. The divider doesn’t rescue them there either. Use the long forms (--continue, --resume <id>). Failing that, go back through doki-claude.

Checking it all still works

.\doki.ps1 verify cycles the profiles and hits every capability with a real API call. On this box on 2026-08-19 it reported 17 passed, 0 failed and 2 skipped, though that run predates the 2026-09-02 removal of the speech and media checks, so the totals are lower now. If something here misbehaves, those two are the first things to reach for.
