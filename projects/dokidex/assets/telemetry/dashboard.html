cache_tokens over the whole prompt (cache_tokens + input_tokens). The two fields are disjoint: input_tokens is what had to be read fresh, cache_tokens is what was served from cache. How to read this

What each number rests on

Worth a minute before you draw a conclusion from anything above.

Sample counts are on everything. The n= chip beside a statistic is how many measurements went into it. Anything under 10 is marked in amber, because a median over three requests is an indication and not a measurement. Hover a marked one for the count.

Time to first token is approximated, everywhere it appears. Nothing in the schema measures it. It is computed as input_tokens divided by prefill_tps, which is the prefill wall time. That is the dominant term and not the whole of it. Queueing and the load of a cold model sit outside it, which makes the real number a little worse than what you see.

Context windows come from the model's own name. Section 1 of contracts.md puts the per-request window in the id. [32k] is read as 32 × 1024 = 32,768 tokens. A model whose name carries no bracket has no known window and is left out of the context panel rather than assumed into it.

Throughput medians cover successful requests only. A request that failed has no meaningful tok/s. Letting it count as zero would drag every model's number down by however often the stack was restarted underneath it.

A missing or empty file is normal. Panels say so in words rather than drawing an empty chart, because an empty chart reads as a measured zero.

Nothing here is stored. Every derived number is computed at render time from the raw records, which is why changing the maths never invalidates data you already collected. The raw schema is frozen in contracts.md section 10c and the derived list is 10d.
