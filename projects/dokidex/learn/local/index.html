:: LOCAL INFERENCE

Running models locally

What you can actually run on hardware you own: runtimes, the VRAM arithmetic worked in full, quantization cliffs, prefix caching, and where local genuinely beats a frontier API.

IntermediateAdvanced

Everything here is written against one reference machine: a single NVIDIA RTX 5090 (32GB GDDR7) with 64GB of system DDR5, on Windows (the machine DokiDex itself targets). It’s a useful anchor because it sits at an honest middle point: big enough for real coding models, small enough that every gigabyte has to be accounted for. If your hardware differs, the arithmetic still applies. Only the numbers change, and the hardware section below covers the other common classes (Apple Silicon, unified-memory mini-PCs, multi-GPU rigs).

The goal is narrow and practical: by the end, you should be able to work out what a given model costs you in VRAM at a given quantization and context length, and pick a runtime without guessing.

Which one, on your desktop

The decision tree below is the short version. In prose: default to llama.cpp: it covers every quant family on Hugging Face natively on Windows+CUDA, and --n-gpu-layers is the sane way to exceed 32GB by spilling into system DDR5. That default has a real cost, easy to overlook: llama.cpp is tuned for single-stream latency, not raw throughput, and ships no ahead-of-time-compiled kernel path the way TensorRT-LLM does. You’re trading peak speed for format coverage and flexibility, not getting both for free.

Reach for Ollama or LM Studio only when “running in two minutes” outweighs controlling every flag. vLLM or SGLang earn their setup cost when concurrency (several simultaneous sessions on one GPU) is the actual problem. A single interactive user mostly leaves their throughput advantage unused. Between the two, SGLang wins when traffic shares a long common prefix (an agent harness, a big system prompt). vLLM wins on broader model/quant support. TensorRT-LLM’s per-model compile step is a bad fit for frequent swapping. Reserve it for one model settled on long-term. ExLlamaV2/V3 earns its place when GGUF’s K-quants don’t hit a bit-width cleanly on one NVIDIA card (a 70B model at 3-4 bpw, say). MLX only matters on an Apple Silicon Mac instead of this page’s reference PC. See the hardware section below.

Model swapping and multi-model serving

A 32GB card holds one large model’s weights plus its KV cache, or several small models, but not several large models at once. There’s no VRAM overcommit for GPU inference that doesn’t fall back to catastrophic host-RAM paging. This makes model swapping mandatory on a single-GPU desktop: something has to own the “one model resident at a time” state machine and load/unload transparently as requests arrive.

llama-swap is the standard tool: a single Go binary, one YAML config, no dependencies. It sits in front of llama-server (or vLLM, TabbyAPI, any OpenAI-compatible backend) behind one endpoint. On each request it reads the model field and, if the running backend doesn’t match, stops the current process and starts the requested one with its exact configured command. Useful features: a groups mechanism for holding more than one model resident when VRAM allows, TTL-based auto-unload of idle models, and /health//metrics.

DokiDex runs exactly this pattern: one llama-swap endpoint in front of a roster of tiers, each with its own tuned flags, swapping in on demand. Full detail, the actual roster, and per-tier VRAM footprints live on the models page. Two patterns from that setup generalize to any single-GPU desktop: a small model held warm in a groups slot alongside the swappable large model (embeddings, fill-in-middle autocomplete, a speculative-decoding draft model), sized so both fit the budget at once. The second is TTL auto-unload, which frees VRAM after idle periods without a human remembering to kill the process.

The cost of cold-swapping is a load-time stall (seconds to tens of seconds, depending on model size and OS page-cache state) on every switch between models outside the same warm group. That stall is the real price of running more model capability than fits in VRAM at once, which is why the arithmetic below matters: the better you fit inside one budget, the fewer swaps a session needs.

The VRAM math, worked

This is the arithmetic that decides what you can run. It has three terms: weights, KV cache, and a smaller overhead term. Each behaves differently as you change quantization, context length, and batch size.

One unit choice, stated up front: the totals below use GiB (2^30 bytes = 1,073,741,824 B), not decimal GB (10^9 bytes). This matches both llama.cpp’s own reported sizes and how VRAM is labeled on a graphics-card box (a “32GB” card is 32 GiB. In decimal terms that’s 34.36 GB). The formulas below produce raw bytes. Converting to GiB means dividing by 2^30, not by 1,000,000,000. Where a figure is shown in decimal GB instead, it’s called out as GB explicitly.

Weights:

weights_bytes ≈ total_params × (bits_per_weight / 8)

bits_per_weight (bpw) comes from the quantization scheme, not the model: GGUF K-quants and I-quants publish near-constant bpw figures because the encoding is per-block, largely independent of overall model size. From llama.cpp’s own quantize reference (measured on Llama-3.1-8B, but the bpw column generalizes to any model at that format):

Format bits/weight Format bits/weight
IQ1_S 2.004 Q4_K_S 4.667
IQ2_XXS 2.382 Q4_K_M 4.894
Q2_K 3.159 Q5_K_S 5.570
IQ3_XXS 3.255 Q5_K_M 5.704
Q3_K_S 3.643 Q6_K 6.563
Q3_K_M 3.996 Q8_0 8.501
IQ4_XS 4.460 F16 16.000

This table is a representative subset. The full table covers every K-quant and I-quant llama.cpp ships.

KV cache, standard multi-head or grouped-query attention (GQA):

kv_bytes_per_token = 2 (K and V) × n_layers × n_kv_heads × head_dim × bytes_per_element
kv_bytes_total     = kv_bytes_per_token × context_length × batch_size

n_kv_heads equals n_heads for plain multi-head attention and is smaller under GQA: the cache-size reduction from GQA is exactly the ratio n_heads / n_kv_heads. Sources: KV-cache/GQA sizing writeup, PyImageSearch GQA cache guide.

KV cache under Multi-Head Latent Attention (MLA, the DeepSeek-V3/R1 family): instead of caching per-head K and V, MLA caches one shared compressed latent per token per layer:

kv_bytes_per_token = n_layers × (kv_lora_rank + qk_rope_head_dim) × bytes_per_element

No ×2 term: a single latent reconstructs both K and V at inference time. Sources: MLA KV-cache mechanism, DeepSeek MLA overview.

Activation/overhead: a smaller, less standardized term: attention-kernel scratch space, CUDA graph buffers, framework bookkeeping. It doesn’t scale with context the way KV cache does, and it isn’t zero either. Budget a few hundred MB to a couple of GB of slack on top of weights + KV cache rather than trusting a formula, since it’s framework- and kernel-dependent.

Mixture-of-Experts, the term that changes shape: weights_bytes has to be computed from total parameters, because every expert must be resident in memory (routing is data-dependent: any expert might be selected on any token), while compute and throughput track active parameters only. This is the single biggest thing MoE changes: capacity sizing uses the big number. Speed sizing uses the small number. Source: DeepSeek-V3 model card (671B total / 37B activated per token).

Key idea: a 671B-parameter MoE model that activates 37B per token needs VRAM for 671B and generates tokens at roughly the speed of a 37B model. Neither number alone describes the model. You need both.

Four worked examples

1. Llama-3.1-8B, dense, GQA (small). 32 layers, hidden 4096, 32 heads, 8 KV heads (4:1 GQA), head_dim 128. (config source)

  • Weights at Q4_K_M (4.894 bpw): llama.cpp’s own table gives this exact model at 4.58 GiB.
  • KV cache/token (fp16): 2 × 32 × 8 × 128 × 2 = 131,072 bytes = 128 KiB/token.
  • At 32K context, batch 1: 131,072 × 32,768 = 4,294,967,296 bytes ≈ 4.295 GB = 4.00 GiB.
  • Total ≈ 4.58 + 4.00 + ~1 GiB overhead ≈ 9.6 GiB: comfortably inside a 32 GiB card, with roughly 22 GiB left over for a second concurrently-loaded model, a bigger batch, or a much longer context.

2. Qwen2.5-32B, dense, GQA (where a single 32GB card starts to feel it). 64 layers, hidden 5120, 40 heads, 8 KV heads (5:1 GQA), head_dim 128, 32.5B params. (config)

  • Weights at Q4_K_M (4.894 bpw): 32.5e9 × 4.894 / 8 = 19.88e9 B ≈ 18.5 GiB.
  • KV cache/token (fp16): 2 × 64 × 8 × 128 × 2 = 262,144 bytes = 256 KiB/token.
  • At 32K context, batch 1: 262,144 × 32,768 = 8,589,934,592 bytes ≈ 8.59 GB = 8.00 GiB.
  • Total ≈ 18.5 + 8.0 + ~1 GiB overhead ≈ 27.5 GiB of 32 GiB: snug but not saturating, at a single 32K-context conversation. Quantizing the KV cache to 8-bit (--cache-type-k q8_0 --cache-type-v q8_0 in llama.cpp) doesn’t cleanly halve it: q8_0 packs 8.5 bits/element (34 bytes per 32 values) against fp16’s 16. So the cache shrinks to roughly 53% of its size (about 4.25 GiB), bringing the total to ≈23.75 GiB, real headroom for a bigger batch or a longer context. It isn’t free, though: 8-bit KV is measurably lossier than 8-bit weights at the same width, and in llama.cpp, quantizing the V-cache specifically requires flash attention to be enabled.

3. Llama-3.1-70B, dense, GQA (where a single 32GB card hits a wall). 80 layers, hidden 8192, 64 heads, 8 KV heads (8:1 GQA), head_dim 128, 70B params. (config)

  • Weights at Q4_K_M (4.894 bpw): 70e9 × 4.894 / 8 ≈ 42.82e9 B ≈ 39.9 GiB: already over a 32 GiB card before any KV cache. A dense 70B model at Q4 doesn’t fit on this card alone.
  • Dropping to IQ3_XXS (3.255 bpw): 70e9 × 3.255 / 8 = 28.48e9 B ≈ 26.5 GiB.
  • KV cache/token (fp16): 2 × 80 × 8 × 128 × 2 = 327,680 bytes = 320 KiB/token. At a modest 8K context: 327,680 × 8,192 = 2,684,354,560 bytes ≈ 2.68 GB = 2.50 GiB.
  • Total ≈ 26.5 + 2.5 + ~1 GiB overhead ≈ 30.0 GiB of 32 GiB. Close to the ceiling, but not the zero-headroom situation it can look like: roughly 2 GiB spare, worth about 6,500 more tokens of context at this KV rate before the card is genuinely full. It’s tighter in practice than that math implies: driver and display overhead typically leave only ~31 GiB usable, and real IQ3_XXS 70B GGUF files tend to land nearer 27 GiB than the theoretical 26.5, which eats most of that margin back. This quantization level is also past the point the quantization section below flags for measurable reasoning-task loss on aggressive 3-bit K-quants. The realistic options: a low-bit format specifically tuned for it (EXL3, or an I-quant), partial CPU offload of some layers (steep latency cost, see below), or treating a dense 70B-class model on one 32GB card as workable only at reduced context on an aggressive quant, not a comfortable everyday setup.

4. DeepSeek-V3, MoE + MLA (where the MoE math flips). 61 layers, hidden 7168, 128 heads, MLA with kv_lora_rank=512 and qk_rope_head_dim=64, 256 routed experts + 1 shared expert, 8 experts active per token, 671B total / 37B active. (config)

  • Capacity uses total params: at Q4_K_M-equivalent (4.894 bpw): 671e9 × 4.894 / 8 ≈ 410.5 GB of weights alone. That’s impossible on any single consumer box, and beyond even a 128GB unified-memory machine. Even at an aggressive IQ2_XXS (2.382 bpw): 671e9 × 2.382 / 8 ≈ 199.8 GB: still larger than one NVIDIA DGX Spark’s 128GB, but it fits inside the 256GB two networked Sparks pool together, in line with NVIDIA’s own stated 405B-parameter envelope for that dual configuration (405B at 4-bit ≈ 203GB, essentially the same byte budget as DeepSeek-V3’s 199.8GB here). One Spark can’t hold it. Two, pooled, can. (DGX Spark specs)
  • Compute tracks active params (~37B): roughly the decode cost of a dense ~37B model, which is why DeepSeek-class MoE models generate far faster than their total size implies, if you can find enough memory to hold every expert.
  • KV cache under MLA is dramatically smaller than GQA would predict: 61 × (512+64) × 2 = 70,272 bytes ≈ 68.6 KB/token. This is independently corroborated by a third-party estimate of roughly 70 KB/token for DeepSeek-V3 versus 192-328 KB/token for GQA models of comparable class, a 2.7-4.7× reduction. (source) At 32K context: 68.6 KB × 32,768 ≈ 2.3 GB, smaller than the 70B dense model’s cache at 8K context in example 3, despite DeepSeek-V3 being roughly 10× larger.
  • Bottom line: the practical way non-hyperscalers run DeepSeek-class models at all is a heavily-quantized (often sub-2-bit-average, mixed-precision) GGUF on a big-RAM CPU+partial-GPU rig, not a single 32GB GPU. Total-parameter accounting is unforgiving even though the active-parameter compute cost feels cheap. Smaller MoE models (30B-120B total-param class) are the realistic MoE tier for a single-GPU desktop or a 128GB unified-memory box.

Quantization quality: where the real cliff is

The most directly relevant primary source here is a single 2026 arXiv evaluation of 13 llama.cpp GGUF formats against Llama-3.1-8B-Instruct at an FP16 baseline (perplexity 7.32). Source: “Which Quantization Should I Use? A Unified Evaluation of llama.cpp Quantization on Llama-3.1-8B-Instruct,” arXiv 2601.14277.

Note: every specific number in this section traces to that one paper. It hasn’t been independently replicated this session. So treat it as a single 2026 study reports…, not as settled consensus across the field.

That study’s perplexity deltas: Q3_K_S at 8.96 (+1.64 over baseline), Q4_K_M at 7.56 (+0.24), Q5_0 at 7.43 (+0.11), and Q6_K/Q8_0 at roughly 7.33-7.35 (effectively lossless). But perplexity alone is a blunt instrument. Task-level scores tell a sharper story:

  • Math reasoning (GSM8K), the most sensitive benchmark tested: Q3_K_S dropped 9.3 points (68.31 vs. a 77.63 baseline), while Q4_K_S recovered to essentially baseline (77.33).
  • Commonsense reasoning (HellaSwag) stayed flat, 71-73.5, across every format, largely quantization-insensitive.
  • Instruction-following (IFEval) varied non-monotonically: Q4_K_S actually exceeded FP16 (80.26 vs. 78.93), a sign that small deltas at moderate quantization are noisy, not a clean curve.
  • Knowledge (MMLU) showed modest 1-4 point variance, worst at Q3_K_S (59.31 vs. 63.50).

The paper identifies 3-bit quantization (Q3_K_S specifically) as the critical degradation threshold, with the largest aggregate loss concentrated there and driven overwhelmingly by the math-reasoning collapse rather than broad degradation. It reports 5-bit configurations (Q5_0/Q5_K_M) as the strongest quality/size trade-off, in one case slightly exceeding aggregate baseline performance at roughly 65% of FP16’s size.

Common trap: perplexity isn’t a good proxy for coding, agentic tool-use, or multi-step reasoning quality, which are exactly the workloads a local coding agent stresses. A quant that looks fine on a perplexity chart can still fail at the tasks you actually care about.

Practical rule: Q4_K_M is a reasonable floor for a model expected to do real reasoning or coding work. Treat anything at Q3 or below as a capability cut, not just a fidelity cut, and validate task-specific behavior, not just perplexity, before shipping a quant that low. Consistent secondary framing: runaihome.com, presenc.ai.

For vLLM-side weight-only formats, third-party reporting states AWQ typically delivers 5-15% higher throughput than GPTQ due to more optimized kernels, with comparable quality at INT4. FP8 on Hopper-class GPUs is described as “near-lossless” with roughly 2× throughput over FP16, though this is a vendor/aggregator characterization, not an independently-run perplexity study, and is flagged as such here. Sources: vLLM quantization performance discussion, GPUStack quantization writeup.

Prompt and prefix caching, locally

This is central to local agent economics: an agent harness resends a large, mostly-unchanged system prompt, tool schema, and conversation history on every turn. Without prefix reuse, every turn re-pays full prefill cost for that entire prefix.

llama.cpp (llama-server) compares each new prompt to the previous completion via cache_prompt (default true) and evaluates only the “unseen” suffix: a longest-common-prefix match reusing already-computed KV states. --cache-ram (default 8192 MiB, -1 = no limit) caps host RAM for the mechanism. --cache-reuse (default 0) sets the minimum chunk size for reuse via KV shifting: reusing tokens even after they’ve moved position, which matters when earlier turns get truncated or summarized. Source: llama.cpp server README.

vLLM’s Automatic Prefix Caching hashes each KV-cache block by the tokens inside it plus every token preceding it, storing blocks in a hash table. A new request sharing a cached prefix reuses those blocks directly. Eviction under memory pressure uses LRU that evicts the end of the longest prefix chain first, preserving shorter, more broadly-shared prefixes longer. Source: vLLM Automatic Prefix Caching design doc.

SGLang’s RadixAttention generalizes the same idea into a radix tree shared across all requests, not just one session. Third-party benchmarking found its hit rate reaching 71% on a shared-prefix multi-turn workload versus 18% for vLLM without sticky routing, with time-to-first-token dropping from a reported 1.4s to 380ms in that comparison. That’s a third-party benchmark, not a vendor claim, and the magnitude will vary by workload, but it’s directionally why SGLang gets recommended for shared-system-prompt agent traffic. Source.

What breaks the cache, concretely: any edit to the prompt before its end. Both llama.cpp’s longest-common-prefix matching and vLLM/SGLang’s block-hash schemes derive validity from exact token-sequence identity up to that point. A single changed token anywhere in the prefix invalidates everything after it, even if 99% of the text is unchanged (editing message 2 of a 50-message history invalidates the cache for messages 3-50). Also, non-deterministic content injected early (timestamps, random IDs, templating that varies an otherwise-static system prompt) defeats caching for the whole prefix. Context-shift/eviction (llama.cpp) discards older tokens’ KV state, so a later request that needs them re-pays full prefill. Cache pressure under --cache-ram limits or vLLM block-eviction can also thrash a cold multi-tenant workload faster than it’s populated.

Practical rule: keep the shared prefix (system prompt, tool schemas, few-shot scaffolding) byte-identical and append-only for as long as possible. Put anything that changes per call as late in the prompt as the API allows. That keeps the invalidated region as small as possible, instead of wiping out the whole prefix.

DokiDex’s own agent sessions measure 92-99% of each turn’s prefill served from cache, because every turn resends a history that’s identical except for the tail, documented in the serving chapter of the engineering handbook. That number is the reason a local agent stack can feel responsive turn-to-turn despite resending its entire context every time.

Speculative decoding and draft models

A small, fast “draft” model proposes several tokens ahead. The large “target” model verifies them in a single batched forward pass, accepting the longest correct prefix and discarding the rest. Because verification is exact, a correctly-implemented speculative decoder produces the same output distribution as the target model alone. It changes speed, not quality, by construction. Net speedup depends on the draft’s per-token acceptance rate and how many tokens get speculated per round.

Third-party benchmarks (not vendor marketing): at an acceptance rate ≥0.6 with ≥5 speculated tokens, 2-3× speedups over baseline autoregressive decoding are reported as the general pattern. Specific figures: Llama-3.1-70B with a 1B draft model, 2.31× on vLLM, and Llama-3.1-8B on a single A100, 1.8×. On llama.cpp/Apple Silicon, one reported case reached 3.2× (64 → 206 tok/s), with a general cited range of 1.5-3× depending on acceptance rate. Sources: speculative decoding production guide, BentoML overview, llama.cpp Apple Silicon benchmarks.

Newer method variants (EAGLE-family, PARD-2) claim larger gains: one source reports 4-5× over standard decoding, and NVIDIA reports 3.6× on H200 with its own method. Read these as upper bounds under favorable conditions, not typical desktop-GGUF results. Source.

When it actually buys you something on a single desktop GPU:

  • Best case: low-temperature, deterministic-leaning tasks (code completion, structured output, translation) where a small same-family draft model (sharing a tokenizer with the target) agrees with the target most of the time.
  • Worst case: creative, high-temperature generation, where the draft’s guesses are frequently wrong and acceptance rate collapses. At that point the extra draft-model forward passes are pure overhead, and speculative decoding can be a net slowdown. One production write-up notes real-world acceptance rates were “likely in the 0.6-0.8 range, not the near-perfect values used in theory.” Plan around the low end, not the demo numbers.
  • VRAM cost: the draft model needs to be resident alongside the target, on a 32GB card competing with a large target model’s weights and KV cache. That’s a real constraint, and exactly the “small model always warm” use case llama-swap’s groups feature is built for.

Consumer hardware, current

Warning: GPU and mini-PC prices move fast and vary heavily by retailer. Everything below is reported as of mid-2026. Treat it as directional, not as a quote.

Discrete NVIDIA GPUs. The RTX 5090 (32GB GDDR7, ~1.79 TB/s, 575W) launched at $1,999 in January 2025. Mid-2026 street prices are reported as high as $4,000-$8,000+, one tracker citing “$4,329, topping $5,000 for premium cards,” attributed to GDDR7 memory cost inflation (~15-20% quarter-over-quarter by Q2 2026) as AI demand drains global memory supply. So the VRAM-heavy card is disproportionately exposed to a memory-market shock. Sources: RTX 5090 pricing analysis, pricing guide. The workstation RTX PRO 6000 Blackwell (96GB GDDR7 ECC, 1,792 GB/s, 600W) sidesteps the ceiling entirely, at a price NVIDIA’s own product page didn’t disclose this session. RTX 5080/5070 Ti/5070 are commonly cited at 16/16/12GB but weren’t re-confirmed against a live spec page. Treat cautiously. A used RTX 3090 (24GB) is a commonly- cited budget option with no confirmed current price.

Multi-GPU: NVIDIA removed NVLink from GeForce starting with the 40-series. The last consumer cards that have it are the RTX 3090 and 3090 Ti, where NVIDIA’s own spec table lists “NVIDIA NVLink (SLI-Ready): Yes” and the GA102 whitepaper gives 112.5 GB/s of total bandwidth between two GPUs. Compare that against a PCIe 4.0 x16 slot’s 64 GB/s and it’s about 1.76x, not the 3.5x you get by accidentally comparing an aggregate figure against a one-direction one. The 4090 and 5090 spec pages both say “No”, so a pair of those talks over PCIe only.

Either way, the interconnect matters less than it sounds. It’s only the bottleneck for tensor-parallel or row-split serving, which does cross-GPU reductions on every layer. The usual default, splitting layers across cards, barely touches the link at all. llama.cpp also gates peer-to-peer behind a GGML_CUDA_P2P opt-in and warns that driver support is usually restricted to workstation and datacenter cards, and there are unresolved reports of 3090 peer-to-peer reading as present but inactive. So on a desktop, multi-GPU mainly buys aggregate VRAM (two 5090s pool to 64GB), not proportionally faster single-stream generation.

Apple Silicon (unified memory). Mac Studio M4 Max ships 410-546 GB/s depending on configuration, starting at 36GB. M3 Ultra reaches 819 GB/s, starting at 96GB. Secondary trackers report Apple pulled the 512GB configuration in March 2026 and the 256GB configuration in May 2026, both attributed to the memory-chip shortage. But neither cut is confirmed on Apple’s own product page. So treat the resulting ceiling as unsettled rather than assuming a specific number (State of AI covers the supply picture behind it). Apple specs. The advantage is architectural, not just bandwidth: CPU and GPU share physical memory with zero-copy access, skipping the PCIe transfer a discrete-GPU system pays every time, and since decode is memory-bandwidth-bound, bandwidth predicts tokens/sec more than capacity does. A third-party comparison reports the M3 Ultra at up to 23× more tokens-per-joule than an RTX 5090, an efficiency claim, not a speed one. The 5090’s ~1.79 TB/s is still over double the M3 Ultra’s 819 GB/s in absolute terms. Source, third-party-reported. Mac Studio pricing wasn’t captured with confidence this session.

Strix Halo / AMD Ryzen AI Max class. The Ryzen AI Max+ 395 pairs a 16-core Zen 5 CPU, a 40-CU Radeon 8060S iGPU, and an XDNA 2 NPU sharing up to 128GB of LPDDR5X on a 256-bit bus: theoretical 256 GB/s, real-world ~212-215 GB/s, roughly 115-120GB usable after OS reservation. Reported throughput: MoE models in the 30B-120B range at 50-70+ tok/s, and the platform can load (not necessarily run fast) models up to ~200B params, beyond any single consumer discrete GPU. Mini-PCs on this chip are reported at $1,499-$1,999, undercutting a comparable Mac Studio by roughly 3×. Chip identity is corroborated by AMD’s developer article. Throughput/price figures are third-party blog reporting.

DGX Spark class. NVIDIA’s DGX Spark (GB10 Grace Blackwell Superchip) packs 128GB LPDDR5x unified memory, 273 GB/s bandwidth, up to 1 PFLOP FP4, a 20-core Grace ARM CPU, and ConnectX-7 for networking two units: NVIDIA states dual-configuration support up to 405B params, below DeepSeek-V3’s 671B from worked example 4. Price is reported at $4,699 as of mid-2026, up from an initial $3,999, though not disclosed on NVIDIA’s own pages this session. Specs, price reporting. The tension is in its own spec sheet: huge FP4 compute paired with modest bandwidth: strong at prefill-heavy work (batch, long-document ingestion), bandwidth-limited on the token-by-token decode that dominates chat latency, similar in kind to Strix Halo’s ceiling.

CPU offload. llama.cpp’s --n-gpu-layers splits layers between VRAM and system RAM when a model doesn’t fit in VRAM alone: the mechanism behind worked example 3’s “barely fits at IQ3” surviving even when it doesn’t quite fit. The cost is steep: CPU-executed layers are bottlenecked by system-RAM bandwidth (tens of GB/s on DDR5) versus the GPU’s ~1.79 TB/s, plus a PCIe round-trip per layer. Treat this as a capability-of-last-resort lever, not a sizing strategy (no single verified per-layer multiplier is given here, since it’s too hardware- and model-specific), and prefer fitting fully in VRAM at a lower quant when that’s available.

Where local genuinely wins, and where a frontier API wins outright

No local-maximalist framing here: the gap is real in both directions, and it’s workload-shaped, not model-shaped.

Where local wins outright:

  • Bulk, well-specified tasks: classification, extraction, semantic search, RAG retrieval, summarization at scale. Third-party pricing analysis notes open-weight models “trail frontier models on hard reasoning, agentic tool use, and frontier-grade coding” but are “dramatically cheaper… sometimes by 10-100×,” with an imperceptible quality gap for these task shapes. Sources: CloudZero, inference.net.
  • Latency-critical loops with no network round-trip tolerance: no WAN hop, no provider queueing, no rate-limit backoff. For tight tool-use loops this can dominate wall-clock time regardless of raw tokens/sec.
  • Anything where the data can’t leave the machine. The one argument here with no break-even point: if the requirement is “this data must never be sent to a third party,” no amount of API cost efficiency substitutes for it.
  • Sustained, high-volume usage against a sunk hardware cost: once the GPU is bought, additional tokens are close to free, which favors local specifically for heavy ongoing usage, not occasional use.

Where a frontier API still wins outright:

  • Hard reasoning, agentic tool-use, and frontier-grade coding. The direction is consistent across every source touched for this page, including Artificial Analysis’s own open-source leaderboard, which shows its strongest open-weight models (GLM-5.2 at Intelligence Index 51, MiniMax-M3 and DeepSeek V4 Pro at 44) without a directly comparable closed-model score extractable from that page. The qualitative direction is stated here, not a specific numeric gap.
  • Novel, one-off hard problems, where a bigger frontier model’s ceiling matters more than per-token cost: the API cost of one hard query is trivial regardless of provider.
  • Multimodal and agentic breadth (computer use, complex tool orchestration, very long-context reasoning) where frontier providers ship capabilities without a mature local equivalent yet.
  • Zero-maintenance reliability: no GPU driver issues, no VRAM OOM, no model-swap latency, no “which quant of which fork” decision fatigue.

The cost argument, precisely, not as a slogan. Local cost is hardware amortization plus electricity, roughly fixed regardless of volume above the idle floor. API cost is linear per token with zero fixed cost. As one illustration, using Anthropic’s published pricing (as of July 2026): Claude Sonnet 5 at an introductory $2/$10 per MTok input/output through August 31, 2026, moving to $3/$15 standard from September 1. Haiku 4.5 at $1/$5. Opus 5 at $5/$25. Anthropic pricing docs. A workload of 50M input + 10M output tokens/month at Sonnet 5’s post-September rate costs 50 × $3 + 10 × $15 = $300/month. Payback is against the card itself, not a markup over MSRP. Using this page’s own cited street prices, that’s $4,329 / $300 ≈ 14.4 months. At the top of the cited $4,000-$8,000+ range, it stretches to $8,000 / $300 ≈ 26.7 months, roughly 1.2 to 2.2 years to break even, before counting the 575W of extra electricity draw the card carries. That payback holds if and only if the local model actually meets the task’s quality bar. That condition carries the whole argument. At lower volumes, or for task classes only a frontier model can do, the API’s zero-fixed-cost structure wins outright. A hardware purchase isn’t justified on cost alone in that case. The same caveat covers multi-user or bursty-concurrency workloads, where a single desktop GPU’s fixed throughput ceiling is the bottleneck against an API’s elastic capacity, and rapidly-improving-model workloads, where a purchased GPU is a sunk cost against an API price curve that keeps falling.

Fine-tuning locally: LoRA and QLoRA in practice

LoRA freezes the base model’s weights and trains small low-rank adapter matrices injected into attention/MLP layers. QLoRA additionally loads the frozen base model in 4-bit (typically NF4) while keeping the trainable adapters in higher precision, cutting base-model memory further at a small compute cost from the dequantize-on-the-fly step.

VRAM and cost, current figures (third-party/vendor-blog reporting, not independently re-derived). QLoRA fine-tuning of Llama-3.1-8B needs roughly 10GB VRAM, fitting a 24GB card (RTX 4090/3090) with headroom. Full fine-tuning of the same model is reported at ~69GB versus LoRA’s ~18GB, a gap large enough to be the whole reason consumer-GPU fine-tuning of this model class is viable at all. A 24GB-class card is reported viable for QLoRA on 7B models at batch size 4-8 and 13B models at 2-4. A 32GB card implies meaningful headroom above that baseline (QLoRA through the 30B-class dense range should fit), though no source gave 32GB-specific figures directly. Treat the 24GB numbers as a conservative lower bound. On cost: a LoRA fine-tune of Llama-3.1-8B on a 50K-sample dataset on a rented RTX 4090 is reported at $2.64-$3.96, QLoRA at $1.76-$2.64, roughly 6-13× cheaper than full fine-tuning, needing ~6× less VRAM, for a reported 1-3% quality trade-off on most benchmarks. On owned hardware the marginal cost is just electricity for a few GPU-hours, since the card is already sunk. Sources: VRAM sizing guide, LoRA vs full fine-tune memory, GPU-for-fine-tuning guide, cost analysis.

When fine-tuning beats prompting or RAG (a synthesis judgment call, flagged as such rather than a single sourced fact): fine-tuning wins for a consistent, low-variance output format, style, or voice across huge volumes of near-identical requests. It also wins when the target is a behavior pattern (a tone, a decision policy, a classification boundary) rather than a retrievable fact.

RAG or prompting wins in the opposite cases: when the underlying facts change over time (fine-tuning bakes in a snapshot that goes stale), when the answer needs to cite specific documents, or when iteration speed matters more than steady-state efficiency. A prompt change is instant and free. A fine-tune run is a QLoRA job plus an eval cycle, even at the cheap end above.

For an agent/coding-tool stack, the strongest fine-tuning case is a narrow, high-volume sub-task inside the loop (a classification or routing step, a consistent tool-call format), not the agent’s core reasoning. The local-vs-frontier gap above argues for a bigger local model or a frontier call there, not a fine-tuned small model pretending to reason.

The throughline across all of this: a local stack is a series of explicit trade-offs, bits per weight against task quality, KV cache size against context length, one resident model against several, hardware cost against per-token API cost. Every one of them is arithmetic you can do yourself with the formulas above. What you build on top of a serving stack like this (the agent loop, the tool calls, the approval model) is the next page.
