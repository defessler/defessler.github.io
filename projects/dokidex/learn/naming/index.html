Decoding Model Names

A component-by-component decoder for any model name you meet in the wild: architecture markers, size notation, tier words, training-stage suffixes, specialization tags, quantization grammar, versioning, and context notation. Real strings get parsed end to end.

BeginnerIntermediate

A model name string is several independent pieces of grammar mashed together: some standardized across the field, some vendor dialect, some pure adjective with no technical content at all. Qwen3-235B-A22B-Thinking-2507 tells you a total parameter count, an active parameter count, a training regime, and a release date, once you know the grammar. Claude Opus 5 tells you almost none of that. It’s a tier name that only means something once you already know Anthropic’s ladder.

Key idea: split any name into the parts that are standardized (the A<n>B active-parameter suffix, the Q4_K_M-style quant suffix, the YYYYMMDD date suffix) and the parts that are vendor dialect (Flash, Pro, Air, Turbo). This page is organized around that split.

1. Architecture markers

Dense vs. Mixture-of-Experts, and the A<n>B grammar

A dense model runs every parameter on every token (classic GPT/Llama/Mistral-7B style). A sparse Mixture-of-Experts (MoE) model has many parallel expert feed-forward blocks per layer plus a router that activates only a subset per token. Stored weights end up far larger than weights multiplied per token.

Reading rule: in XXXB-AYYB, the first number is total (stored, VRAM) parameters and the A number is active (compute) parameters per token. A 235B-A22B model needs storage for 235B parameters but computes roughly like a 22B dense model per token.

  • Qwen3-235B-A22B: 235B total, 8 of 128 experts active per token (~22B activated). Qwen3 blog
  • DeepSeek-V3: 671B total / 37B active, 256 routed + shared experts, Multi-head Latent Attention for cheap KV-cache. arXiv:2412.19437
  • Llama 4 Scout / Maverick: Scout is 17B active / ~109B total (16 experts). Maverick is 17B active / ~400B total (128 routed + 1 shared expert). Maverick alternates dense and MoE layers rather than running MoE at every layer. Scout doesn’t. Meta AI blog
  • gpt-oss-120b: 117B total / 5.1B active. gpt-oss-20b: 21B total / 3.6B active. OpenAI README
  • Gemma 4 26B-A4B: 25.2B total / 3.8B active. Hugging Face

Common trap: Mixtral-8x7B reads like “8 experts of 7B, so 56B total.” The real total is 47B: attention layers and the embedding table are shared across experts, only the feed-forward blocks are duplicated. A bare <E>x<S>B string is never simply E × S: check the card. Hugging Face

Two more names worth knowing exactly: Qwen3-Coder-480B-A35B (480B total / 35B active, code-specialized) Qwen3-Coder blog, and GLM-4.6, whose card states 357B total parameters (easy to transpose with predecessor GLM-4.5’s 355B). Hugging Face GLM-4.6’s active-parameter count isn’t confirmed here, so it’s left out rather than guessed.

Hybrid SSM / Mamba markers

State Space Models (the Mamba family) supplement or replace attention with a linear-time recurrent scan, trading some quality for much cheaper long-context inference (no KV-cache growth with sequence length). Jamba (AI21) is literally an acronym for Joint Attention and Mamba: an interleaved hybrid of attention and Mamba blocks plus MoE. arXiv:2403.19887 Zamba (Zyphra) is lighter still: a Mamba backbone with one shared attention module inserted periodically rather than Jamba’s fuller interleaving. arXiv:2405.16712 Samba and Hymba round out the family. The “-amba”/”-ymba” suffix nods to Mamba, not a formal spec. Reading rule: any “hybrid”/”SSM”/Mamba-sounding name mixes recurrent blocks with a minority of attention layers. The exact ratio is a card detail, never in the name.

MatFormer / nested (“Matryoshka”) models

Google’s MatFormer trains one large model containing several smaller, independently-usable submodels nested inside it. One run yields multiple deployable sizes with no separate distillation pass. arXiv:2310.07707 Gemma 3n’s 4B-effective (E4B) checkpoint has a fully-functional 2B-effective (E2B) submodel nested inside it, switchable at runtime. E means effective parameters via Per-Layer Embedding caching, smaller than the raw on-disk count. Gemma docs Reading rule: E<n>B is not the same axis as a plain <n>B elsewhere.

Multi-token prediction and attention variants

MTP predicts several future tokens from one hidden state instead of just the next, densifying the training signal. DeepSeek-V3’s MTP module adds ~14B parameters, mainly for training and speculative decoding. arXiv:2412.19437 It rarely appears in the name itself. Sliding-window attention caps each token to a nearby window, interleaved with occasional global layers to cut KV-cache cost. Gemma 3 uses 5 local layers per 1 global, a 1,024-token window. Hugging Face blog Names never encode this ratio directly, though it correlates with whether a huge advertised context (1M-10M) is computationally viable at all.

2. Size notation

The suffix number is total learnable parameters (weight matrix entries), not FLOPs, not “capability,” and not disk size directly (disk size = parameters × bytes per weight, Section 6). It includes attention and feed-forward/MoE weights plus the embedding and unembedding matrices, which can be a surprisingly large or small fraction of the total depending on vocabulary size and whether embeddings are tied. It does not include KV-cache, which scales with context length and batch size, not parameter count (Section 6). For MoE, 235B-A22B is unambiguous. A bare 235B alone is genuinely ambiguous without checking whether the card means total or active.

Why parameter count stopped predicting capability: two developments broke the old heuristic. First, overtraining past Chinchilla-optimal: the Chinchilla paper found that for fixed training compute, size and token count should scale together, at roughly 20 tokens per parameter (their own model: 70B params / 1.4T tokens). arXiv:2203.15556 Since 2023, most labs deliberately abandon that ratio, because Chinchilla minimizes training compute only, saying nothing about inference cost, which recurs on every request. Llama 3 8B was reportedly trained on roughly 15 trillion tokens (well-corroborated secondary reporting, no single verbatim primary quote available here), about 94x the Chinchilla ratio, to buy a smaller, cheaper-to-serve model. This tradeoff is formally called “inference-optimal” or “overtrained” scaling. arXiv:2401.00448 Second, architecture and post-training gains compound: Qwen’s own comparison shows each Qwen3 dense model (1.7B-32B) roughly matches the prior-generation Qwen2.5 model one size class up, credited to pretraining-recipe improvements rather than scale. Qwen3 blog

Net effect: a bare parameter count tells you little without also knowing tokens-trained relative to size, MoE total-vs-active split, and generation. There’s no name-string notation for tokens-trained. Check the card, since a 2024-era 8B trained on 2T tokens and a 2025-era 8B trained on 15T+ aren’t comparable despite an identical size suffix.

3. Tier words: a vendor-by-vendor dictionary

Almost none of these words mean the same thing twice across vendors. A few (Flash, mini/nano, Air) at least carry a consistent direction within one vendor’s own lineup: faster, cheaper, smaller. But the absolute capability behind the word is never comparable across vendors. Several (Pro, Max, Plus, Turbo, Ultra, Fast) are close to pure marketing: “better than the word next to it in this catalog,” and nothing that survives crossing a vendor boundary.

4. Training-stage suffixes

Suffix What happened to the weights
Base Raw next-token pretraining only, no chat tuning. Prompt with text continuation, not chat turns
Instruct/-It/Chat SFT (usually plus RLHF/DPO/RLAIF) for instruction-following. Gemma: PT = base, IT = instruction-tuned. Hugging Face blog
SFT Supervised fine-tuning on curated (prompt, ideal-response) pairs (the first alignment stage). It’s rarely in a shipped model’s name
DPO Direct Preference Optimization: skips a separate reward model and the RL loop, reformulating preference data as a classification-style loss. arXiv:2305.18290
RLHF A reward model trained on human preferences, then RL against it. The dominant recipe since ChatGPT
RLAIF Same as RLHF but the reward model trains on AI-generated preferences. Reported comparable quality at lower labeling cost. arXiv:2309.00267
Thinking/Reasoner Trained to emit extended chain-of-thought, often via RL on verifiable rewards: give it room, don’t truncate the trace, budget for far higher output tokens
Distill A smaller “student” trained to imitate a larger “teacher.” DeepSeek-R1-Distill-Qwen-7B was SFT’d on ~800K R1-generated reasoning traces atop a Qwen2.5 base. The grammar is <Teacher>-Distill-<StudentBase>-<Size>. Hugging Face Treat teacher benchmarks as an upper bound, not a guarantee, for the student
Abliterated/Uncensored Post-hoc weight editing, not a training stage: the refusal-mediating direction is found and projected out, no retraining. Labonne’s writeup Community-produced, no safety guardrails. Research/red-team use, not production

5. Specialization markers

Marker Meaning
Coder/Code Heavy code-token pretraining (often 50-70%+ of the mix), often plus FIM and coding-agent RL. Qwen3-Coder-480B-A35B: 70% code across 7.5T tokens. Qwen3-Coder blog A genuinely different checkpoint, not a prompt template
VL/Vision Adds an image (sometimes video) encoder plus multimodal training (Qwen2.5-VL, Command A Vision). docs.cohere.com Often a distinct branch, not a strict superset of the text-only sibling
Omni Marketing shorthand for “many modalities in one model.” No fixed technical definition: descriptive, not a formal token
Audio Speech-in/out capable, often a separate model line entirely (Mistral Voxtral, OpenAI GPT-Realtime). docs.mistral.ai Frequently not a general chat model at all
Embed Outputs a fixed-size similarity vector, not text. text-embedding-3-large (3,072 dims) vs. -small (1,536). developers.openai.com “small/large” tracks dimensionality and accuracy. It’s a different axis from generative parameter count
Rerank Cross-encoder scoring of (query, document) pairs, a second retrieval stage. Cohere rerank-v4.0-pro (quality) vs. -fast (latency). docs.cohere.com Not a generator

Math Extra pretraining/RL on math corpora (Qwen2.5-Math). Can regress on general chat quality vs. a generalist sibling
Med Medical-domain specialization exists across labs. No confirmed current naming convention for this page. Flagged, not asserted
FIM (fill-in-the-middle) Trained on <prefix><suffix> → <middle> alongside normal next-token prediction (Qwen2.5-Coder, 5.2T tokens). arXiv:2409.12186 A pure chat model fakes this via prompting, with materially worse completion quality. IDE autocomplete wants a FIM-trained (often Base/Coder-Base) checkpoint

6. Quantization and format

GGUF quantization grammar (llama.cpp)

GGUF is llama.cpp’s container format, split into three families. Bits-per-weight figures are from the llama.cpp quantize README. llama.cpp README

Legacy/linear types use simple per-block affine scaling, block size 32:

Type Bits/weight Note
Q8_0 ~8.50 “Almost indistinguishable from float16,” per llama.cpp
Q4_0, Q5_0, Q4_1, Q5_1 N/A Older, cruder. Superseded by K-quants at a comparable bit budget

K-quant family (Q2_K…Q6_K) uses 256-value super-blocks with per-sub-block scale/offset. The _S/_M/_L suffix selects which tensors get bumped to higher precision:

Type Bits/weight What _S/_M/_L does
Q4_K_M 4.89 Uses Q6_K for half of attention.wv/feed_forward.w2, else Q4_K. The recommended default
Q4_K_S 4.67 Plain all-Q4_K, no selective upgrade
Q5_K_S/Q5_K_M 5.57 / 5.70 Same _S/_M pattern one bit-family up
Q3_K_S/Q3_K_M/Q3_K_L 3.64 / 4.00 / 4.30 _L upgrades more tensors than _M
Q2_K_S/Q2_K 2.97 / 3.16 Quality drop becomes noticeable here for most models
Q6_K 6.56 Close to Q8_0 quality at meaningfully smaller size

I-quant family (IQ*) uses non-uniform, importance/codebook-based quantization for aggressive 2-3 bit compression:

Type Bits/weight
IQ1_S/IQ1_M ~2.00 / 2.15
IQ2_XXS/IQ2_XS/IQ2_S/IQ2_M ~2.38 / 2.59 / 2.74 / 2.93
IQ3_XXS/IQ3_XS/IQ3_S/IQ3_M ~3.25 / 3.50 / 3.66 / 3.76
IQ4_XS/IQ4_NL ~4.46 / 4.68

I-quants hold quality better than K-quants below ~3 bits, at the cost of more dequant compute. This is reported (community discussion, not an official benchmark) to run slower on CPU than a similarly-sized K-quant. GitHub discussion Reading rule: _S = smaller/plainer, _M = medium (upgrades the most error-sensitive tensors), _L = large (upgrades more), all within a fixed bit family, not an independent size class. _XS/_XXS push further down than _S, used only at the 1-3 bit end.

Other formats

Format Mechanism
AWQ Finds “salient” weight channels via activation magnitude, scales them before INT4/INT3 quantization. No backprop, generalizes well across domains. arXiv:2306.00978
GPTQ One-shot, Hessian-informed layer-wise quantization minimizing output error. The long-standing GPU INT4 standard. arXiv:2210.17323
EXL2 ExLlamaV2’s mixed-bitrate format (2-8 bits, non-uniform within one model), plain safetensors. exllamav2
EXL3 ExLlamaV3’s format, derived from Cornell’s QTIP. Lattice-codebook encoding, closer in spirit to I-quants than to GPTQ’s linear scaling. EXL3 doc
NF4 (bitsandbytes) “4-bit NormalFloat”: levels placed for equal probability mass under a Gaussian weight-distribution assumption. Built for QLoRA fine-tuning. arXiv:2305.14314

Floating-point/integer precision: FP16/BF16 (~2.00 bytes/weight) is the pre-2024 “full precision” baseline. FP8 (E4M3, 1 byte/weight) powered DeepSeek-V3’s entire pretraining run. It’s the first large validated FP8 training run at this scale. arXiv:2412.19437 MXFP4 (4-bit, open OCP spec, block-32 shared scale) is gpt-oss’s MoE-weight format at 4.25 bits/parameter, fitting gpt-oss-120b on one 80GB GPU. OpenAI README NVFP4 (NVIDIA-specific, finer block-16 scale) is reported (vendor-reported) to beat MXFP4 by roughly 0.3-0.5 perplexity at equal bitrate. NVIDIA dev blog INT8/INT4 are the fixed-point substrate under GPTQ/AWQ/bitsandbytes. INT4 ≈ 0.5 bytes/weight before ~10-20% group-scale overhead.

QAT vs. PTQ: everything above (besides NF4-for-fine-tuning) is PTQ: an already-trained model quantized afterward. QAT bakes simulated quantization noise into training itself, generally yielding higher quality at a given bit-width, at the cost of training compute and data access instead of a cheap one-shot conversion. gpt-oss’s MXFP4 is applied post-training (OpenAI’s own card language), i.e. PTQ-adjacent, despite unusually little quality loss.

VRAM math: the practical rule and a worked example

Tip: VRAM (GB) ≈ Total_Parameters(B) × Bytes_per_Weight × 1.05–1.20 + KV-cache overhead

The 1.05-1.20 multiplier covers quantization metadata, the embedding table, and runtime buffers. KV-cache is a separate, context-length-dependent line item. It grows with context tokens × batch × layers × hidden size × 2 (K and V), independent of weight footprint, which is why a model can fit at short context and still OOM near its advertised maximum. For MoE, use the total parameter count. Every expert must be resident in VRAM even though only a few compute per token.

Take a 70B-parameter dense model (the class Llama 3.1 70B sits in):

  • Q4_K_M (0.61 B/wt): 70 × 0.61 ≈ 43 GB weights alone, roughly 48-52 GB with overhead.
  • Q8_0 (1.06 B/wt): 70 × 1.06 ≈ 74 GB weights, roughly 85-89 GB with overhead.
  • FP16 (2.00 B/wt): 70 × 2.00 = 140 GB weights, roughly 150-160 GB with overhead.

The same math on a 235B-A22B MoE model at Q4_K_M needs roughly 155-165 GB to load, despite computing at close to the speed of a 22B dense model per token. That gap is the single most common practical surprise in MoE size math.

This is napkin math, not a benchmark. For measured end-to-end fitting guidance and per-GPU tier recommendations, see Running models locally.

7. Version and date conventions

Anthropic pins releases with an 8-digit date suffix: claude-sonnet-4-5-20250929, claude-opus-4-1-20250805. Every dated model ID is fixed to that release. Starting with Claude 4.6, IDs use a dateless format (claude-opus-4-6) that’s still a pinned snapshot, not an evergreen pointer. platform.claude.com For pre-4.6 models, a separate “API alias” (claude-opus-4-5) resolves to the dated ID (claude-opus-4-5-20251101). The alias can, in principle, be repointed. The dated ID never moves. The same alias/dated-ID split is standard across major API vendors.

Common trap: a date suffix marks the release snapshot, not the knowledge cutoff. The two can differ. Claude Sonnet 4.5’s reliable knowledge cutoff is January 2025. Its training-data cutoff is July 2025. Those are two different columns in the same table. platform.claude.com

-latest/undated aliases are a production hazard: a vendor can silently swap the weights behind an alias with zero code change on your side. Reproducibility breaks, eval numbers become unattributable to a specific weight set, and a regression can appear with zero deploy on your end. Pin the dated/versioned ID in production. Reserve bare aliases for exploratory work.

-preview/-exp signal an unstable, possibly short-lived release (gemini-3.1-pro-preview), with faster deprecation and looser SLAs than GA under the same base name. ai.google.dev

A live example of the churn this causes: as of this page’s snapshot (July 2026), DeepSeek’s docs had deprecated deepseek-chat/deepseek-reasoner on 2026-07-24 in favor of deepseek-v4-flash/deepseek-v4-pro, collapsing what used to be two model IDs into one mode flag. Any integration hardcoded to the old names needed a change within the week. api-docs.deepseek.com Similarly, xAI ships grok-4.20-0309-reasoning, grok-4.20-0309-non-reasoning, and grok-4.20-multi-agent-0309 as distinct IDs. There’s no bare “Grok 4.20.” docs.x.ai Treat a date, a specific patch version, or an explicit “stable” designation as safe to hardcode. Treat bare family names, -latest, -preview, and -exp as requiring active re-validation.

8. Context notation

“128k,” “200k,” “1M” mean the maximum input-plus-output token budget the model’s attention scheme was trained or extended to support, not a guarantee of usable quality at that length. Input and output limits are sometimes reported separately and differ a lot: Claude Sonnet 5, Opus 5, and Fable 5 all show a 1M-token context window but only a 128k-token max output in the same table. platform.claude.com Tokenizer choice complicates this further. Anthropic notes Claude Opus 4.7+/Fable 5’s newer tokenizer produces roughly 30% more tokens than pre-4.7 models for the same text, so a nominal “1M-token” window isn’t directly comparable across generations of the same vendor, and the same caveat applies to per-token price comparisons.

Warning: an advertised context window isn’t a promise the model reasons reliably across the whole thing.

  • NVIDIA’s RULER benchmark evaluated 17 models across 13 tasks and found that although all of them claim 32K context or more, only about half maintained satisfactory performance at 32K, despite near-perfect scores on the vanilla needle-in-a-haystack test. arXiv:2404.06654
  • Chroma’s “Context Rot” report evaluated 18 frontier models and found 20-50% accuracy drops between 10K and 100K+ tokens. A 200K window can show serious loss by 50K input, and a 1M window doesn’t reliably reason across 1M. Safe budgets for 2M-window models landed around 150K-400K tokens for high-accuracy work. Chroma research
  • The NoLiMa benchmark found 11 of 13 models dropped below 50% of their short-context baseline by 32K tokens. See Advanced concepts for the fuller treatment.

Practical implication: never treat an advertised context window as a proxy for how much you can put in front of a model and get reliable output. Effective context is empirically a fraction of the advertised figure (commonly cited in a 15-65% range depending on task). That fraction is vendor- and task-dependent, not a fixed ratio.

Llama-4-Maverick-17B-128E-Instruct: Hugging Face Llama-4 = Meta’s 4th generation · Maverick = the mid/flagship tier (Scout below it, unreleased Behemoth above) · 17B = active parameters · 128E = 128 routed experts plus one shared expert every token also passes through · Instruct = chat-tuned, not base · total ~400B · context up to a vendor-claimed 1M tokens.

5. Qwen3-Coder-480B-A35B-Instruct: Qwen3-Coder blog Qwen3-Coder = the code-specialized branch (70% code across 7.5T tokens, plus agentic-coding RL) · 480B-A35B = 480B total / 35B active · Instruct = chat/agent-tuned · 256K native context, extending to 1M via extrapolation.

6. DeepSeek-R1-Distill-Qwen-7B: Hugging Face DeepSeek-R1 = the teacher · Distill = the student was SFT’d on ~800K R1-generated reasoning traces · Qwen = the base architecture (Qwen2.5’s 7B checkpoint), not a from-scratch DeepSeek design · 7B = the student’s own dense parameter count. Reading trap: this isn’t a shrunk version of R1’s own MoE architecture. It’s someone else’s dense model imitating R1’s outputs.

7. google/gemma-4-26B-A4B-it: Hugging Face gemma-4 = Google’s 4th Gemma generation (this MoE variant doesn’t exist in the Gemma 3 line, despite the string being easy to misattribute) · 26B-A4B = 25.2B total / 3.8B active · it = instruction-tuned · 256K context.

10. unsloth/gpt-oss-120b-GGUF, Q4_K_M variant: Hugging Face unsloth = the community re-packager (not OpenAI) · gpt-oss-120b = the source model (see #3) · GGUF = llama.cpp’s container format · Q4_K_M = 4-bit K-quant, most error-sensitive tensors upgraded to Q6_K, 4.89 bits/weight. This is notably a re-quantization of a model whose MoE weights were already native ~4.25-bit MXFP4, so the precision loss versus the original checkpoint is smaller than a naive from-FP16 conversion would suggest.
