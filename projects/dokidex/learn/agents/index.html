:: THE AGENT LANDSCAPE

Coding agents

How Claude Code, Cursor, Codex and a dozen others compare, and the engineering patterns (agent loop, permissions, context, checkpoints) that matter more than any single product's marketing page.

Intermediate

A year ago “coding agent” mostly meant autocomplete with better taste. Now it means something that reads your repo, plans a change, edits multiple files, runs your tests, and asks permission (or doesn’t) before it touches anything destructive. That shift happened along genuinely different design axes: terminal versus IDE versus cloud, model-locked versus bring-your-own-key, ask-every-time versus full autonomy. This page maps that field, then teaches the patterns underneath it, because the patterns outlive any one product’s pricing page.

DokiDex runs several of these against a local model rather than a cloud one, which is a deployment choice rather than a different category of tool. Run the CLIs locally covers that side. This page is about the field as a whole, and about why the underlying mechanics (the loop, the permission gate, the context budget) look so similar across nearly every tool here, regardless of who built it.

Note: this market moves in weeks, not quarters. Three products in the table below (Roo Code, the original Gemini CLI, Windsurf’s first credit system) were discontinued or replaced in the roughly 60 days before this page was written. Every price is dated to July 2026. Treat anything you read here in six months as a starting point to re-check, not a current fact.

Open-source code doesn’t protect you from a hosted service being pulled by whoever operates it. That risk is structurally absent only for a tool running fully against your own local model.

2. The patterns underneath the products

Strip away branding and nearly every tool above is the same machine in different clothes. That’s worth understanding on its own, because it’s what you’re actually evaluating when you compare products.

2.1 The agent loop

Every entrant in this list implements some version of the same cycle: assemble context, let the model reason and pick a tool, execute that tool, stream the result back, and repeat until the model decides it’s done, with the user able to interrupt at any point without corrupting session state (architecture taxonomy, arXiv 2604.03515).

Tool schemas are what turn a chat model into an agent in the first place: actions like reading a file or running a shell command are exposed as typed function calls, not free-text conventions the model has to guess at. That same mechanism is also exactly what prompt injection abuses, because a tool’s output is just more text the model conditions on (§4 below).

2.2 Permission and approval: the hard part

The interesting engineering isn’t the loop. It’s the gate that decides whether “tool executes” is allowed to happen. Every product above has converged on some version of ask-every-time / auto-accept-with-limits / fully autonomous, but the mechanism differs in ways that matter:

  • True OS-level sandboxing (Codex CLI’s Seatbelt/bwrap+seccomp, GitHub’s cloud sandbox) constrains what a command can do, regardless of what the model intends.
  • Approval-workflow-only, with no technical boundary behind it, is weaker. Cursor’s own docs concede this plainly.
  • Two-layer MCP approval (connection-level, then per-call) is now typical, but gaps are common: GitHub’s own cloud firewall explicitly excludes MCP traffic.
  • Destructive-action gating, where a tool self-declares a call destructive, is promising but trusts that declaration. A malicious server can simply lie about it.

Approval fatigue and race conditions are structural, not incidental, and that’s the genuinely hard part here, not drawing this flowchart. A user asked to approve every tool call habituates to clicking “allow,” and an editor’s auto-reload can execute a file write before a human has actually read the diff. No product in this list has fully solved that. The two most credible partial mitigations are an automated reviewer model pre-screening risky requests (Codex) and OS sandboxing that makes the approval moot for a whole class of actions in the first place.

Common trap: treating any approval prompt as a security boundary. Cursor’s own documentation states its guardrails are “best-effort,” not a hard boundary, and even a strict per-call approval flow can be worn down by habituation. A prompt you click through on autopilot protects you from nothing.

2.3 Context management: orientation, retrieval, compaction, subagents

Orientation files (CLAUDE.md, AGENTS.md) are a project-level instruction file re-read every session: build commands, conventions, security rules. AGENTS.md was formalized as an open spec in August 2025 by OpenAI/Codex, Cursor, Google’s Jules team, and Factory, then donated to the Linux Foundation’s Agentic AI Foundation by December 2025, with over 60,000 projects and roughly 15 tools recognizing it (agents.md, guide). Most agents read whichever of AGENTS.md or CLAUDE.md exists, in a fixed precedence order. Maintaining more than one for different tools is usually redundant; pointing one at the other with a single include line is the cheap way to keep them honest. How much you should put in one has changed sharply with the current model generation. See 2.6 before writing a long one.

Two philosophies compete for what the model sees of your codebase: build a structural map up front (Aider’s repo map, LSP symbols) and let it request full files selectively, or lean on embedding-based retrieval for a very large monorepo. Full reads cost more tokens but eliminate “edited against a stale snippet” bugs. Retrieval scales further but reintroduces that risk.

As a session runs long, tools summarize-and-restart rather than truncate: this is compaction. What a compaction summary keeps (architectural decisions, unresolved questions, key facts) matters far more than how aggressively it compresses. Naive truncation reliably reintroduces bugs the agent already fixed once (compaction deep-dive).

Subagents delegate work to a child agent running in its own, isolated context window, returning only a summary to the parent rather than its full transcript. The dominant “supervisor” pattern keeps one auditable decision-maker instead of peer agents coordinating directly (subagent patterns). Claude Code’s Task tool implements the same shape, and on a single local card those subagents serialize through one seat rather than running in parallel.

2.4 Checkpoints, undo, and recovery

Three recovery mechanisms exist across this list, and they are not interchangeable:

  1. File-level checkpointing (Claude Code, Cursor) snapshots file content before a write/edit call. It restores files, not the shell, so a stray rm isn’t covered by either tool (Claude Code docs).
  2. Git-commit-as-checkpoint (Aider) makes every edit its own real commit, coarser-grained but recoverable with ordinary git tooling, not a proprietary command.
  3. Platform/VM-level checkpointing (Replit, Devin) snapshots the whole sandboxed workspace: the only approach here that can capture dependency installs and shell side effects, at the cost of being tied to that platform’s own infrastructure.

A tool that markets “checkpoints” without stating scope invites you to assume shell damage is recoverable when, in most implementations, it isn’t. Worth checking before you need it, not after.

2.5 Plan mode, act mode, and orchestration

The plan/act split (propose changes read-only, then execute in a separate, granted phase) is now close to universal (Claude Code, Codex, Cline’s original design, Junie, Replit, and most others’ /plan//act, which filter the model’s tool schema itself down to read-only calls, not just ask it nicely). Roo Code’s richer four-mode alternative was arguably more expressive. Its May 2026 discontinuation is a real data point that the simpler split is what actually stuck.

For orchestration beyond one agent, “supervisor” (one parent dispatching to isolated-context children) is reported as the production default for coding, because it keeps a single, auditable locus of decision-making, versus “swarm” patterns where auditability is harder to guarantee (orchestration guide).

2.6 What changed with the Claude 5 generation: fewer rules, later loading

Most published advice on writing orientation files and system prompts was worked out against 2024-2025 models, and a chunk of it is now counterproductive. In July 2026 Anthropic published its revised guidance alongside a concrete number: it removed over 80% of Claude Code’s system prompt for the Claude 5 generation with no degradation on coding evaluations (The new rules of context engineering).

The through-line is that capable models no longer need to be fenced in, and the fencing itself was costing quality. Six specific reversals:

Old practice Current guidance
Rigid rules: “never write multi-paragraph docstrings”, “default to no comments” State the goal and trust judgment: “write code that reads like the surrounding code: match its comment density, naming, and idiom”
Teach a tool with usage examples Design the tool’s interface so correct use is obvious: an explicit status enum (pending, in_progress, completed) does the teaching a paragraph of examples used to
Load all context up front Progressive disclosure: put detail in skills the model activates when relevant, and load tool definitions on demand rather than all at once
Repeat instructions in both the system prompt and the tool description Say it once, in the tool definition
Manual note-taking into an orientation file Automatic memory, where the harness supports it
Prose specs in markdown Richer references: actual code, test suites, rubrics. Prefer the real artifact over a description of it

Practically, for an orientation file today: keep it a lightweight repository summary plus the gotchas that are genuinely specific to this repo, and push everything else into skills or references. A long file restating general good practice is now a cost, not an investment. Claude Code ships claude doctor to rightsize existing skill and CLAUDE.md files.

Common trap: reading this as “context engineering is over.” It is the opposite: the guidance moved from writing more instructions to designing what the model sees and when. Interface design, progressive disclosure and choosing the right reference artifact are all context engineering, and they are harder than writing rules.

Note: how much of this transfers to a local model is an open question. We won’t pretend otherwise. Every claim above was measured by Anthropic on frontier Claude models. The reversals are all bets on model judgment, and judgment is precisely what a 30B local model has less of. The explicit guardrails Claude 5 no longer needs are plausibly still load-bearing for the models DokiDex runs. Our own experience points that way, since we chose the daily-driver tier over a higher-scoring candidate specifically because the alternative was less reliable at following tool-call structure. Treat “delete 80% of your prompt” as validated for frontier models and untested below them. If you run local, change one thing at a time and check it against your own evals.

3. Does it actually help?

This is the section vendor pages skip, and it’s the one that tests whether a site like this one is worth trusting on anything else.

METR’s 2025 randomized controlled trial (16 experienced open-source developers, 246 real issues from their own backlogs, AI-allowed versus AI-disallowed) found developers took 19% longer on issues when allowed to use AI (mostly Cursor with Claude 3.5/3.7 Sonnet). That’s the opposite of the expected direction. More striking was the perception gap: developers forecast a 24% speedup beforehand, and even after experiencing the slowdown, still estimated AI had made them roughly 20% faster (METR blog, arXiv 2507.09089).

METR’s 2026 follow-up had to be redesigned mid-study, because developers increasingly refused the “no AI” condition and a pay cut compounded the bias. A returning-developer cohort came back with an estimated 18% slowdown, confidence interval spanning roughly −38% to +9% (wide, and it crosses zero). A newly-recruited cohort showed a 4% slowdown (CI −15% to +9%). METR called it “very weak evidence,” in either direction (2026 update).

Read together: a rigorous 2025 study found a real slowdown in one expert-developer setting. Developers were reliably overconfident about AI’s benefit, a pattern that replicated across the before/after measurement. And the 2026 re-run became uninterpretable due to who dropped out. There is currently no methodologically clean estimate of coding-agent productivity impact for 2026: only weaker, self-selected evidence still trending negative, with intervals wide enough to cross zero.

Independent commit-history analysis points at an adjacent concern: quality. GitClear’s analysis of 623 million tracked code changes (2023-2026) finds cross-file reuse down 35%, refactoring activity collapsed to 3.8% of changed lines (down from 21% in 2022), and broad try/catch-style error-masking up 47% versus 2022 baselines, alongside a 15% rise in two-week churn (GitClear). A separate 211M-line cut reports AI usage correlating with up to 9x higher churn on some measures, though it attributes most heavy users’ raw output advantage to pre-existing differences between developers, not the tool: the AI-attributable gain, controlling for a developer’s own baseline, is closer to 25% (Arc.dev). GitClear is a code-analytics vendor with a commercial stake in this narrative, so treat its percentages as one lab’s methodology, not consensus. But the direction is worth taking seriously.

Misconception: “this tool makes me Nx faster.” The best available randomized evidence doesn’t support a specific multiplier in either direction, and the one thing that did replicate is that developers overestimate the benefit whether or not it’s actually there. If you want your own number, time yourself on comparable tasks with the tool on and off.

4. Security: prompt injection and the MCP supply chain

Prompt injection against coding agents is demonstrated, not theoretical. A systematic review cited across multiple 2026 sources reports that all tested agents (including Claude Code, Cursor, and GitHub Copilot) showed some vulnerability to prompt injection across 78 surveyed studies (Pillar Security).

The flagship case study, disclosed around April 2026 under the name “Comment and Control,” demonstrated working exploits against three production integrations: Anthropic’s Claude Code Security Review GitHub Action (a malicious PR title triggered command execution), Google’s Gemini CLI GitHub Action (issue-comment payloads bypassed guardrails), and GitHub Copilot Agent (payloads hidden in HTML comments bypassed content filtering). All three abused content the agent was already reading as part of its normal job, achieving command execution and secret exfiltration into public PR comments. The Claude Code and Gemini CLI variants fired automatically through CI, no manual step needed. Anthropic rated it critical and disallowed the ps tool in that context. Google added guardrail prompting. GitHub classified it as a known architectural limitation rather than a fixable flaw. That’s a meaningfully different triage than the other two gave. The researchers’ own framing: any agent with powerful tool access, exposure to untrusted input, and a channel to communicate externally is exploitable by construction (SecurityWeek).

MCP supply-chain risk is now treated as the primary 2026 threat vector, ahead of prompt injection as its own category: the Cloud Security Alliance frames it as “a supply chain problem first, a prompt injection problem second,” since MCP servers run with broader permissions than the package-ecosystem attacks (typosquatting, marketplace poisoning) they otherwise resemble (CSA research note). A formal taxonomy applying STRIDE/ATT&CK modeling to MCP calls out tool poisoning (a compromised server silently executing a harmful action behind a legitimate-looking call) and “rug pull” (a trusted server changed or replaced by its maintainer, or an attacker) as most severe, and notes a tool’s description is visible to the model but often invisible in the user-facing UI, so an adversarial instruction can hide where no human looks (arXiv 2603.18063). Researchers also reported a command-execution vulnerability in Anthropic’s own reference MCP SDKs in 2026. Even a reference implementation isn’t automatically safe from this class of bug.

Mitigations, ranked by how structural (versus cosmetic) each is: OS-level sandboxing of the whole execution environment. Egress firewalling with a default-deny allowlist (every implementation checked here excludes MCP traffic). Destructive-action gating at the tool-schema level (trusting the tool’s own self-declared schema). An automated model pre-screening risky requests. And bounty-driven disclosure, necessary but reactive. Defense-in-depth is the honest position in mid-2026. No single fix covers it. At least one credible vendor has stated some instances aren’t currently fixable, only mitigatable. Treat any agent with tool-execution rights and exposure to untrusted repository content as exploitable by default.
