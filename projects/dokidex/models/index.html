:: THE SERVING STACK

The Models DokiDex Runs

What actually loads onto the GPU when you run DokiDex, why each model got the seat it has, and what's still being tested: straight from the serving config, not the marketing copy.

Intermediate

Every claim on this page traces to a file in the repository: serving/llama-swap.yaml (the config that actually runs), media-assets/llm-model-catalog.json (display names and hashes), and a set of dated bake-off scorecards under docs/scorecards/. Where a doc and the running config disagree, the config wins. That happens more than once on this very page. We call each one out rather than smooth it over.

  • 272.7 tok/swarm decode, the daily-driver coder (docs/model-guide.md:436)
  • ≥91%golden-suite bar + zero tool-call flakes, to promote a candidate (docs/decisions.md:1488)
  • 32 GBthe VRAM ceiling every tier is sized against (one RTX 5090)
  • 1big coder or vision tier resident on the card at a time (one 3 GB utility model is the sole exception)

The serving architecture

DokiDex doesn’t run “a model.” It runs llama-swap, a small Go binary that exposes one OpenAI-compatible endpoint on :8080 and swaps the underlying llama-server process to match whatever model name a request asks for (serving/llama-swap.yaml:1-2, docs/wiki/10-how-it-works.md:98). The pinned engine is llama.cpp build b9878 (CUDA 13.3) behind llama-swap v235 (serving/llama-swap.yaml:3, confirmed site-wide in docs/CAPABILITIES.md:75).

That header line is now only part of the picture, and the config is what says so. FOUR engine trees are in play, not one:

  • 17 keys launch the pinned b9878 binary under serving/llama.cpp\.
  • 5 keys launch serving/llama.cpp-b10472\: gpt-oss-120b [128k] (Reasoning, Heavy), Qwen3-Coder-30B-A3B b10472 [128k] (Candidate, Light), Qwen3.8-27B f16 [104k] (Candidate, Standard), and Qwen2.5-3B-Instruct [32k] (Utility, Free). The tree is not a stray experiment: it held the seat from 2026-08-18 and its rows stay runnable by name, covered in Claude Code and Copilot, local. gpt-oss-120b [128k] (Reasoning, Heavy) joined it on 2026-08-20 for a concrete reason: gpt-oss needs grammar-constrained tool decoding, and b9878 could not compile the regex in one of Claude Code’s 26 tool schemas, so every request came back “failed to parse grammar”. b10472 compiles it.
  • 2 keys launch serving/llama.cpp-b11026\: the Qwen3.6-35B-A3B-MTP [128k] (Thinking, Standard) seat itself (since 2026-09-18, its CUDA-graph MTP fix measured +10.5% decode on this card), and the Qwen3.8-27B [256k] (Candidate, Standard) row that held the seat before it, kept runnable by name with its 256k window, vision and a full tool-call gate.
  • 1 key launches serving/llama.cpp-v4\: DeepSeek-V4-Flash [16k] (Reasoning, Heavy), built from the cchuter/llama.cpp fork because DeepSeek-V4 needs kernels the pinned build does not have.

Those four trees account for 24 of the 25 model rows. The 25th, GitHub Copilot Cloud [32k] (Cloud, Billed), launches no llama-server at all. Its cmd runs serving/copilot-shim.ps1, which wraps the real GitHub Copilot CLI instead.

The b9878 line at serving/llama-swap.yaml:3 predates all of that and has not been amended.

The reason it swaps instead of running everything at once is arithmetic, not preference: the box has one 32 GB card. The interesting models here don’t fit two-at-a-time. Qwen3-Coder-30B-A3B [128k] (Coding, Light) alone holds roughly 26 GB (weights plus a 128k-token KV cache). gpt-oss-120b [128k] (Reasoning, Heavy) needs its own 27 GB of GPU plus 40 GB of system RAM for the experts that don’t fit. There’s no combination of “useful coder” plus “useful heavy planner” that clears 32 GB together. Only one of them is ever loaded. Deciding which is llama-swap’s whole job.

Three more pieces of that architecture matter:

--cache-ram holds evicted context in host RAM, not VRAM. Qwen3-Coder-30B-A3B [128k] (Coding, Light) and Qwen3-Coder-30B-A3B [32k] (Coding, Light) (the two tiers that actually swap in and out across a normal session) carry --cache-ram 24576, raising llama-server’s prompt-cache allowance from its 8192 MiB default to 24 GiB of system RAM (serving/llama-swap.yaml:93-99). The point: when one of those two tiers gets evicted mid-session and swapped back in later, its old KV prefix can still be served back from host RAM instead of re-processing the whole prompt from scratch. Every other tier in the file, including every bake-off candidate, is deliberately left without this flag. It’s scoped to the two seats that actually swap.

One group gets to break the one-model rule. A llama-swap group named agent-seat carries swap: false, which pins both its members at once instead of evicting one for the other (serving/llama-swap.yaml:78-85). Its members are the Qwen3.6-35B-A3B-MTP [128k] (Thinking, Standard) seat and the zero-VRAM GitHub Copilot Cloud [32k] (Cloud, Billed) row. The 3 GB Qwen2.5-3B-Instruct [32k] (Utility, Free) sat here too until 2026-08-26. The reason is specific rather than general: Claude Code fires small background calls constantly, and on a one-model card each of those used to evict roughly 27 GB of coding weights and pay a full reload. Measured on this box across a 43-request concurrent soak, the pair peaks at 30,912 MiB of 32,607 MiB with 1,695 MiB free (serving/llama-swap.yaml:30-32). Read that pair with its conditions attached. It was taken at seat -c 131072 and utility model -c 8192 (docs/scorecards/2026-08-19-sidecar-vram.md:103-107), neither of which is what ships today. Treat 1,695 MiB as the shape of the margin rather than a current reading. The exception costs most of the remaining headroom either way. There’s no room for a second one. Claude Code and Copilot, local walks through what that buys a reader in practice.

There used to be a coarser split above this one, and it is worth knowing it is gone. Until 2026-09-02 the whole card belonged to one of two mutually exclusive groups at any moment, llm or media, and doki up media evicted the coding models to make room for image, video and audio generation. That half of the stack was removed (see archive.md), and with it the media profile. Every service is in the llm group now. doki up agent loads the seat plus the always-on embedding server, which is CPU-only and costs the card nothing. Run doki up coexist instead and you also get the FIM autocomplete model, at a reduced context so an editor and the agent can share the card. None of that’s this page’s subject (see the CLI tutorial for the commands). What survived the removal is the budget underneath it: one 32 GB card, pick one occupant.

The shipped tiers

Since the 2026-08-25 rename, a tier’s name IS its id. There’s no display name sitting apart from a key for the two to drift out of sync, and no alias standing between what you ask for and what answers. Read the name itself and it tells you what you need: the real model, its per-request context window in brackets, then what kind of work it does and what it costs you in parens, from a two closed sets. Nature is one of Thinking, Coding, Reasoning, Vision, Utility, Candidate or Cloud. Cost is one of Free, Light, Standard, Heavy or Billed. Free means it costs no GPU budget of its own to serve, not that it is loaded beside the seat. Only the Utility row carries it, and since 2026-08-26 that row is not co-resident, so asking for it evicts whatever is. Billed means real money leaves your account, and nothing routes there without you naming it by hand.

Before the rename, the CLI’s subagent seats and the local-CLI skills bound to specific tiers as aliases, so a bake-off promotion re-pointed a seat by editing one alias line rather than touching harness config. That indirection is gone. Re-seating a tier now means editing the model a skill or a harness names directly (harness/claude-skills/, serving/llama-swap.yaml), which is one edit either way, just without a second name to keep in sync.

The two rows above are identified by role rather than by a display name, because they aren’t llama-swap rows at all and never carried a llama-swap alias to lose. Every other row above is exactly the string /v1/models reports back, and exactly the string you’d type to ask for it.

Two numbers on those rows are both hard ceilings now, though one of them only became one recently.

The seat runs -c 262144, which is qwen35.context_length in its own GGUF: the model’s actual ceiling, not a fraction of it (serving/llama-swap.yaml:872). That’s been true since 2026-08-26. Before that date the row ran -c 106496, about 40% of the ceiling, and that older configuration is still on disk as the control row, Qwen3.8-27B f16 [104k] (Candidate, Standard) (serving/llama-swap.yaml:1227), kept for A/B against older scorecards. The bigger window didn’t cost more to reach. A q4_0 KV cache is a quarter the size of the f16 cache the 104k row still carries, so the seat holds 2.5x the tokens at 910 MiB LESS memory than the row it replaced (serving/llama-swap.yaml:844-846). What the extra room actually buys is the compaction floor. Claude Code’s compaction trigger is Max(100000, window x 0.75), so the retired 106,496 window compacted at exactly 100,000 tokens and the shipping 262,144 window compacts at 196,608. That’s the whole user-visible difference between the two rows. The utility model’s -c 32768 is a hard ceiling for a different reason. It’s qwen2.context_length in the GGUF, which llama.cpp clamps to. A larger -c is silently ignored. Measured 2026-08-20, a row launched at -c 49152 still answered a 41,638-token request with “exceeds the available context size (32768 tokens)” (serving/llama-swap.yaml:763-773). A rare oversized background call fails loudly there rather than corrupting anything.

Two things worth naming as tradeoffs, not just facts. The autocomplete server runs a 3B model rather than a 7B one specifically because the smaller model still measured “excellent” fill-in-the-middle quality at 292 tok/s. Unlike a 7B, it comfortably coexists with Qwen3-Coder-30B-A3B [32k] (Coding, Light) in 32 GB (docs/decisions.md:1323). And the embedding server is deliberately built with no GPU visibility at all (CUDA_VISIBLE_DEVICES=-1 scoped to its launch, serving/start-embed.ps1:12-16). A CUDA-built llama-server still grabs 100 to 300 MB of VRAM just for a CUDA context even at -ngl 0. The whole point of the embedding server is that it costs the coder tier nothing.

Why the daily-driver coder holds its seat

The 2026-07-05 bake-off (docs/model-guide.md) is the most instructive result on this page, because the winner wasn’t the highest scorer.

Qwen3.6-35B-A3B [128k] (Candidate, Standard) 218.4 hangs (killed at 27 min) 14/15 = 93% Not wired as an agentic default.
GLM-4.7-Flash [128k] (Candidate, Standard) 224.2 pass (needs GLM sampling) 13/15 = 87% Below the bar. Menu pick.

(docs/model-guide.md:436-439, measured against the installed instance on :8080, warm tok/s on an identical 256-token prompt.)

Qwen3-Coder-30B-A3B [128k] (Coding, Light) and Qwen3.6-35B-A3B [128k] (Candidate, Standard) tie exactly on the 15-task golden suite: 93% each. If promotion ran on suite score alone, it would be a coin flip. It isn’t a coin flip, because the promotion bar has two conditions, not one: ≥91% on the golden suite AND zero tool-call flakes on the native gate (docs/decisions.md:1488). Qwen3.6-35B-A3B [128k] (Candidate, Standard) fails the second condition outright. Sent the exact same native tool-call probe that Qwen3-Coder-30B-A3B [128k] (Coding, Light) passes cleanly, it hangs instead of returning, a known interaction with an unmerged llama.cpp fix (serving/test-toolcall.ps1, issue class #22684, still mergeable_state: blocked as of the 2026-07-06 research pass, research/model-lane-2026-07-06.md:42). Qwen3-Coder-30B-A3B [128k] (Coding, Light) wins the tiebreak decisively on the one axis that actually gates production use, not on the shared suite score (docs/model-guide.md:460-462).

Key idea: the a3b split verdict (93% golden, hangs on the native probe) is called out in the bake-off’s own method notes as its single most useful finding: harness scaffolding (like the crush harness the suite runs through) can mask a model’s raw tool-call instability. Gate a candidate both ways (native probe and full harness) before trusting either number alone (docs/model-guide.md:471-472).

gpt-oss-120b [128k] (Reasoning, Heavy) earns its seat on a related but different axis: at 39.7 tok/s with a roughly 53-second cold load, it’s the slowest tier on this page by a wide margin. But it’s also the only large model here that passes the native tool-call gate cleanly, at roughly four times the decode speed of the other heavy candidates that were only tested near or above 10 tok/s (docs/model-guide.md:439-441). Because a full swap-in is expensive, DokiDex doesn’t call it per-turn. The one routing change worth making per the research is plan-on-big: it drafts the plan, Qwen3-Coder-30B-A3B [128k] (Coding, Light) executes it. That way the ~53-second swap cost hides behind the human’s plan-approval pause instead of landing on every message (serving/llama-swap.yaml:166, docs/model-guide.md:463-464).

The 2026-09-17 games bake-off

The newest measured result on this page asked a different question than the promotion gate: not “can it drive an agent” but “can it build a working thing in one shot.” Five configs got the same three prompts, Conway’s Game of Life, Tetris, and a Mario-style platformer, two draws each, as single self-contained HTML files at the registered 450 W cap (docs/scorecards/2026-09-17-games-bakeoff.md). The bar was fully playable by a human, graded by referee agents that read every file end to end with a default verdict of broken. Decode speeds are llama-server’s own per-request timings on real generations.

Three findings carry past the table. The seat’s 0/6 is a protocol artifact worth knowing: its thinking block consumed the whole max_tokens budget on all six generations and emitted zero content. Multi-turn agent work doesn’t hit this, because the client controls thinking there, but one-shot long-form generation on the seat config needs a no-think variant or a much bigger budget. Second, a five-call multi-agent protocol (plan, ideate, build, critic, fix, in the GVS5H shape) did not lift the smaller models: 1/3 each, at the same cost for the coder and 3.1x the tokens for the MTP model. Its critic stage burned the thinking model’s whole budget reasoning and returned no verdict, and the coder shipped the same invisible-board Tetris defect before and after its repair round. Two plain draws from the 35B beat all of it. Third, none of this promotes anything: the native tool-call gate above still governs agentic tiers, and Qwen3.6-35B-A3B [128k] (Candidate, Standard) still hangs that probe.

Parked, with reasons

This is the section where the decisions that look wrong on paper get explained. Every one of these is a model that measured better on some axis and was still kept out.

Nemotron 3 Nano 30B-A3B (not yet a catalog entry). NVIDIA’s own benchmarks show it ahead of a comparable Qwen3-30B-A3B-Thinking model on several axes: SWE-bench 38.8 vs 22.0, BFCL v4 53.8 vs 46.4 (vendor-reported, research/nemotron-evaluation-2026-07.md:24-29). It’s parked anyway, because it’s a hybrid Mamba-Transformer architecture, and llama.cpp can’t partially truncate recurrent state the way it can a plain transformer’s KV cache. Every request reprocesses the entire context from scratch, even with an identical system prompt (research/nemotron-evaluation-2026-07.md:44-48). That would zero out the 92% to 99% per-turn cache reuse this stack’s agent economics are built on. We rejected a model that benchmarks better because it would be slower in practice, every single turn. Unblock condition: llama.cpp’s hybrid checkpoint-restore work (issue #22384) landing for append-only agent loops, re-checked roughly monthly (research/nemotron-evaluation-2026-07.md:69-71).

EAGLE3 speculative decoding on the quality tier. EAGLE3 (draft cheap, verify with the real model) merged into llama.cpp mainline as a way to speed up exactly the tier that’s slowest to swap in. It was the leading lever under consideration until the merged PRs’ own benchmark data came back: gpt-oss MoE EAGLE3 measures at or below 1×: 0.89×, 0.95×, 1.06× across three prompts on the reference 20B speculator. The two available 120B heads are explicitly tagged by their own authors with “a performance issue due to its MoE arch” (research/model-lane-2026-07-06.md:39). The verdict flipped from “the one lever that speeds the quality tier (1.3× to 2×)” to “likely no-win, measure-first, don’t build routing on it” (research/model-lane-2026-07-06.md:25).

Qwen3-Coder-30B-A3B Q5 [128k] (Candidate, Light): the daily driver’s own base, one quant step up. This is the most concrete parked result on the page, with a dated scorecard. The idea: the daily driver’s only known soft spot is an occasional tool-call-as-prose leak. The straightforward lever for that is more bits per weight: UD-Q4_K_XL → UD-Q5_K_XL. Gated 2026-07-07, both the native probe (twice) and the 15-task golden suite. Verdict: PARK. Pass-rate came in below Qwen3-Coder-30B-A3B [128k] (Coding, Light)’s own baseline under every accounting tried in the report (from 66.7% to 73.3% against a baseline of 80.0% to 86.7%, depending on how flaky first-shot failures get counted). And tool-call fidelity was a razor-thin, sign-flipping call depending on methodology (docs/scorecards/2026-07-07-coder-q5-gate.md). The genuinely interesting part: the defect the quant bump targeted (tool-calls leaking as prose) produced zero incidents for either model across all 30 task runs in this sample. The extra ~4 GB (94.3% of the card at full 128k context) bought no measurable reliability win, and cost some correctness.

Vision, repointed from 32B back to 8B. On 2026-06-21, an eval gate showed the 32B decisively out-reading the 8B on fine UI text and telemetry: a real quality win. A 2026-07-05 audit (P1.1) found that the 32B’s GGUF had never actually been wired into the installer: no manifest row, no setup switch. Every real install’s default Qwen3-VL-8B [32k] (Vision, Light) tier tried to load a file that was never fetched, which made Describe/Verify 404 on every clean machine (serving/llama-swap.yaml:197-201). The fix repointed the default vision tier back to the 8B (which is fetched) and split the 32B out as a separately opt-in Qwen3-VL-32B [32k] (Vision, Standard) tier (setup.ps1 -VisionHQ), which now has a real fetch path and a SHA-pinned manifest row (manifest id vision-hq in serving/model-manifest.json, a separate namespace this rename doesn’t touch). It stays non-default because the 2026-06-21 quality win was measured on the old b9616 engine, since re-pinned to b9878. The comparison needs to be re-run on the current engine before the default vision tier would repoint to it again (serving/llama-swap.yaml:206-209).

Honest caveats

A few things in the repository don’t agree with each other. We source this page from the config rather than the docs specifically so we can say so plainly instead of quietly picking one.

Two files disagree on the autocomplete server’s running VRAM. serving/start-fim.ps1:5 estimates the FIM server at “~4GB”. The Qwen3-Coder-30B-A3B [32k] (Coding, Light) comment in serving/llama-swap.yaml:123 estimates the same 3B Q8_0 model at “~6.6GB” for the coexistence math. The one solid number is the file size on disk, 3.29 GB (media-assets/llm-model-catalog.json:139). Either estimate still leaves the 64k-context Qwen3-Coder-30B-A3B [32k] (Coding, Light) plus the autocomplete server under 32 GB. Nobody has reconciled the two comments.

Note: figures on this page marked [vendor] elsewhere in the research corpus (Cerebras’s REAP pruning claims, for instance) are the pruner’s own numbers, not something measured on this stack. The scorecards above are what this project actually ran.

Devstral-Small-2-24B [128k] (Candidate, Standard) has two separate, unrelated problems, and one stale note about a third that’s already fixed. First: it’s still genuinely misconfigured. Its cmd in serving/llama-swap.yaml:282-285 carries no sampling row. It runs at llama-server’s default temperature (0.8) instead of the model card’s recommended ~0.15. And the bartowski build’s chat template mis-renders Mistral’s tool-call token on the pinned engine. Tool calls leak as roughly 112,000 tokens of prose until the request hits its cap. The resulting 0/15 golden score is a serving bug, not a verdict on the model (docs/model-guide.md:455). Second: it has no installer fetch path at all (no setup.ps1 switch, no row in serving/model-manifest.json). So today it only runs if someone hand-places the GGUF. Third, and this one is fixed even though the note claiming otherwise is still there: the catalog’s own inline comment warns that the yaml “currently points at an unsloth UD-Q4_K_XL filename, not this bartowski Q4_K_M file… before activating that tier” (media-assets/llm-model-catalog.json:175). It doesn’t anymore. The current serving/llama-swap.yaml:284 points at the exact same Devstral-Small-2-24B-Instruct-2512-Q4_K_M.gguf the catalog’s own download row fetches. The filename mismatch the comment warns about was already resolved when the tier was enabled. Nobody deleted the stale warning.

A comment can contradict the block sitting three lines under it, and the fix can outlive the bug it named. The example here used to be the seat’s own comment, which claimed opus, sonnet and haiku “ALL resolve here on purpose” long after the launcher’s actual ladder had quietly moved sonnet and fable onto different models chosen by capability, each one hardcoded by name. The 2026-08-25 rename didn’t just fix that comment. It deleted the hardcoded ladder the comment was describing. claude-local.ps1 no longer carries a table of names that mean “the seat”: it asks GET /running which models are resident right now and seats sonnet, haiku and fable from that, falling back to -Model when nothing else is loaded. There’s no ladder left for a comment to misdescribe.

This is the version of the caveat above that keeps recurring. A comment sitting right next to the code goes stale the moment neighboring code changes. It goes stale silently, because nothing tests a comment. This page used to cite two other yaml comments disagreeing about whether Qwen3-VL-32B [32k] (Vision, Standard) was live. Both have since been reconciled in the file itself (serving/llama-swap.yaml:205 and :249-253 now agree it’s a standalone A/B tier you request by name), which is what the fix looks like when someone gets to it. When a comment and a running config disagree, the config wins.

Qwen3-Coder-REAP-25B-A3B [128k] (Candidate, Light)’s 47% isn’t directly comparable to the 91%/93%/87% figures above. Its one completed gate run used the claw harness (docs/scorecards/2026-07-06-claw-Qwen3-Coder-REAP-25B-A3B [128k] (Candidate, Light).md), not the crush harness the daily-driver comparison table uses. Harness choice moves the number: the Qwen3-Coder-30B-A3B Q5 [128k] (Candidate, Light) gate re-measured Qwen3-Coder-30B-A3B [128k] (Coding, Light) itself under claw and got 86.7% (docs/scorecards/2026-07-07-coder-q5-gate.md), versus the 93% crush measured for the same model on the same day elsewhere in this page’s sources. Treat REAP25B’s 47% as a real signal that it’s struggling, not as a number on the same scale as the tiers above.

Common trap: a model’s presence as a keyed block in serving/llama-swap.yaml doesn’t mean it will answer a request. start-serving.ps1 silently drops any tier whose weight file isn’t actually on disk before handing the config to llama-swap, specifically so a missing GGUF produces a clean “not offered” instead of an HTTP 500 (serving/start-serving.ps1:101-193). This is working as designed. Qwen3-Coder-Next-80B-A3B [128k] (Candidate, Heavy) was confirmed dropped this way on 2026-07-07, mid an unrelated gate run, simply because its weights weren’t fetched yet (docs/scorecards/2026-07-07-coder-q5-gate.md). But it means the yaml above is the possible roster, not necessarily what a given install can actually serve.

Dropping a model turned out not to be enough on its own. A members: list naming a pruned model is fatal to llama-swap: it exits 1 with creating group router: no model config for "Qwen2.5-3B-Instruct [32k] (Utility, Free)" and binds nothing at all. One absent 3 GB utility model GGUF used to take the whole stack down that way. Reproduced on 2026-08-19 with only that one file marked missing. The repair is Remove-DokiDanglingGroupMembers at serving/start-serving.ps1:195, which drops a pruned model from every members: list and drops any group left with fewer than two members (serving/llama-swap.yaml:65-73).

The same underlying model has three different IDs across three files. The gpt-oss-20b tier is "reasoning" in the catalog, "reasoning-gptoss20b" in the installer manifest, and "gpt-oss-20b [128k] (Reasoning, Light)" in the yaml that actually serves it. None of these is wrong (they’re each file’s own namespace). But it’s worth knowing before cross-referencing them by name. Relatedly, that tier’s fetch switch (setup.ps1 -Reasoning) didn’t exist at all when the 2026-07-05 bake-off first ran into its missing weights. It exists now, but defaults to off (serving/model-manifest.json id reasoning-gptoss20b, defaultOn: false). Installing DokiDex today still won’t fetch it unless you ask for it by name.
