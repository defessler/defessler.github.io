emulatarr:~$ emulatarr --tutorial before

Before You Start

The wizard runs on your PC and does its work on the NAS over SSH. Nothing installs locally, and nothing is written to the NAS until you press Run.

  • SSH switched on - on Synology that's Control Panel, Terminal & SNMP, "Enable SSH service". Note the port if you changed it from 22.
  • An account that can sudo - the install creates folders and runs containers, so it needs to escalate. The wizard works out how on your particular box.
  • Docker or Podman - on Synology that's Container Manager, from Package Center.
  • Somewhere to put games - a shared folder on a volume with room. Cartridge systems are tens of GB. PS2 on its own is around 15 TB.
You don't need to prepare folders, write a .env, or pull any images first. That's the wizard's job. If you'd rather do it by hand anyway, QUICKSTART.md is the same install written out as commands.

emulatarr:~$ emulatarr --tutorial welcome

Welcome

First run is a single button. After that this screen lists the NAS profiles you've saved, so a second install, or a re-run against the same box, starts from what you already entered.

  +--------------------------------------------------+
  |  Emulatarr                                       |
  |  Set up a self-hosted game library on your NAS.  |
  |                                                  |
  |   [ Set up a new NAS ]                           |
  |                                                  |
  |  Saved profiles                                  |
  |   DS1522+        192.168.1.10   last run Jul 26  |
  |   Office NAS     10.0.0.5       last run Jun 02  |
  |                                                  |
  |  Import a profile...                             |
  +--------------------------------------------------+
  • Set up a new NAS - starts from empty and walks you through all six screens.
  • A saved profile - jumps in with the host, paths and settings already filled. Secrets are only present if that profile was saved on this machine.
  • Import a profile - opens a .emulatarr-profile.json file that was exported elsewhere. It'll ask for the passphrase.

emulatarr:~$ emulatarr --tutorial connect

Connect

Where the NAS is and how to log in. The most common mistake here is pasting the DSM web address, which is the management UI on port 5000, rather than the machine's address with SSH on port 22.

  +---------------------------------------------------+
  |  Host        192.168.1.10            Port  22     |
  |              not your DSM URL, that is port 5000  |
  |  Username    doug                                 |
  |                                                   |
  |  Auth        (o) password   ( ) private key       |
  |  Password    ............                         |
  |                                                   |
  |                            [ Test connection ]    |
  |  ok  connected as doug, sudo available            |
  +---------------------------------------------------+
  • Password or key - a key path plus its passphrase works if you'd rather not type a password. Both are handled the same way from here on.
  • Test connection - proves the login and works out how this box escalates privileges before you commit to anything.
Sudo passwords are masked at a fixed width before they reach the screen or the log file, so neither the value nor its length shows up in anything you might paste into a bug report.

emulatarr:~$ emulatarr --tutorial detect

Detect

One batched probe over the connection you just proved, turned into a picture of the box. This is read-only. Nothing here writes to the NAS.

  +----------------------------------------------+
  |  Platform     synology      Arch     x86_64  |
  |  Runtime      docker compose                 |
  |  Web port     8998 free                      |
  |  Library vol  28.4 TiB free                  |
  |  Existing DB  none found                     |
  +----------------------------------------------+

Two of these are worth reading carefully:

  • Web port - if 8998 is already taken, change it on the next screen rather than fighting whatever holds it.
  • Existing database - if a MariaDB data directory is already there, say so. It matters, and the next section explains why.

emulatarr:~$ emulatarr --tutorial configure

Configure

The one screen with real decisions on it. Everything here becomes a .env file on the NAS, written deterministically, with values quoted against an allow-list because the NAS side sources that file.

It's grouped into six sections, and you can usually accept the defaults for the last three:

  • Library - where the games live, and which platforms to prepare folders for.
  • Access - how you reach the web UI on your network. Host address and port.
  • Secrets - generated for you. You never need to remember these.
  • Metadata - cover art, descriptions and release dates. See below.
  • Automation - optional background jobs. Everything here is off by default.
  • Advanced - ownership, timezone, and names you rarely change.
The one that bites. MariaDB only applies a database password when it initialises an empty data directory. Generating a fresh password against a database that already exists leaves RomM unable to log in to its own data, and it presents as a RomM bug rather than a password one. Detect reports whether that directory exists, and Configure warns you before you regenerate.

For metadata, Hasheous and Playmatch need no account and are on by default. IGDB gives the best coverage but wants a Twitch application's client ID and secret. ScreenScraper is a free account. You can add any of them later by re-running the wizard.

emulatarr:~$ emulatarr --tutorial run

Run

This is the part that changes your NAS. The wizard uploads nas/scripts/, runs setup.sh, and streams the real output back. The rail on the left tracks eight steps:

  +------------------------------------------------+
  |  1 ok  Detect platform, runtime, capabilities  |
  |  2 ok  Validate configuration (.env)           |
  |  3 ok  Pre-flight checks                       |
  |  4 ok  Create folders and set permissions      |
  |  5 ok  Pull container images                   |
  |  6 >>  Deploy the stack                        |
  |  7  -  Enable optional extras                  |
  |  8  -  Post-deploy validation                  |
  +------------------------------------------------+
  | [emulatarr] creating /volume1/roms/roms/snes   |
  | [emulatarr] web port 8998 appears free         |
  | [  ok  ] folders ready                         |
  +------------------------------------------------+
  • Step 5 is the slow one - pulling images depends on your connection. Several minutes is normal.
  • Step 4 can be slow the first time - applying ownership and ACLs across a large existing library takes a while. It only touches newly created directories unless you ask for a full pass.
  • The log is the real thing - not a summary. You can save it from this screen, and it's what to attach to a bug report.
Safe to re-run. The whole install is idempotent, which is deliberate: networks drop and people click Run twice. If it fails at step 6, fix the cause and run it again rather than unpicking anything by hand.

emulatarr:~$ emulatarr --tutorial done

Done

The last screen runs the post-deploy health check and shows a tile per service. Showing the database and cache rather than only RomM is on purpose: when RomM won't load, "is MariaDB up?" is the first question, and the answer should be on screen instead of an SSH session away.

  +--------------------------------------------------+
  |   RomM web UI      RomM       Database    Cache  |
  |   ok  :8998        ok         ok          ok     |
  |   Start here     Container   MariaDB     Valkey  |
  |                                                  |
  |          [ Open http://192.168.1.10:8998 ]       |
  +--------------------------------------------------+

Only the web UI tile is clickable. The database and cache publish no host port, since they talk over the private bridge network, so linking them would hand you a dead link.

Open the web UI, create the admin user, then add games. The wizard's job ends here. Getting your collection in is the sourcing and ingest guide.

A newly deployed RomM can take a minute or two before it answers. If a tile is amber right after a successful install, give it a moment and re-run the check before assuming something broke.

emulatarr:~$ emulatarr --tutorial profiles

Profiles & Exporting

Everything you typed is saved per NAS, so re-running against the same box is a matter of picking it off the Welcome screen.

  • Encrypted at rest - profiles live in %APPDATA%\emulatarr-installer\, with secrets encrypted through the OS keystore. That ties them to your user on your machine.
  • Export - writes a .emulatarr-profile.json wrapped with a passphrase you choose. That's the way to move a profile to another machine, because the encrypted-at-rest copy can't travel.
  • Import - takes that file plus the passphrase and adds it to this machine's list.
Pick a real passphrase. An exported profile carries your SSH credentials and database secrets. The wizard asks for at least twelve characters and does not keep a copy, so there's no recovery if you lose it.

emulatarr:~$ emulatarr --tutorial updates

Updating the Wizard

The wizard checks for updates on launch and every six hours after. When one is available a New version banner appears.

  • Verified before it's applied - the download is checked against the size and sha256 published with the release. A truncated or tampered file is discarded rather than installed.
  • Applied on restart - clicking Restart & install swaps the new files over the running install and reopens. There's no installer and nothing to click through.
  • Profiles survive - they live in %APPDATA%, not in the program folder that gets replaced.

When Something Goes Wrong

The wizard ships a Troubleshooting panel with around thirty entries, each a symptom rather than a component, grouped so you can find yours by what you're seeing:

  • New to this? Start here
  • Install failed or timed out
  • RomM will not load
  • Database
  • Storage and permissions
  • docker compose
  • Library scanning
  • Metadata and artwork
  • Auto-ingest
  • Playing games
  • Remote access

Each entry explains what's actually happening and gives you the command to run, with your own paths and ports already substituted in, so it's copy-and-paste rather than fill-in-the-blanks.

A few worth knowing before you hit them:

  • "Another setup.sh is running" - a stale lock from an interrupted run. The panel shows you how to confirm nothing is actually alive before clearing it.
  • Connection refused on the web port - usually the stack is still starting. Check the tiles on the Done screen first.
  • Access denied for user 'romm' after a re-install - the MariaDB password case from Configure.
There's also a diagnostics collector: it bundles the logs and the state of the stack into a single tarball, with secrets stripped. Attaching that to an issue saves a round trip of questions.
