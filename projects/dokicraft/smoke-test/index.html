    Dokicraft — Smoke Test & Release Verification¶

    A repeatable verification pass. Run it after every iteration that touches tested surface area, and record the outcome in §F Results Log.

    • How to use: §A preconditions → §B automated build/test gates (run these first — a one-shot runner script should cover everything scriptable) → §C the consolidated MANUAL pass (everything a human still has to do, grouped into runnable sessions, with a quick-smoke fallback tier if the full automated harness can't be used) → §D detailed per-check reference (expected results + fail signatures at code sites, same IDs as §C) → §E regression watch-list → §F results log (append-only) → §G maintenance rules.
    • Status legend: [ ] not run · [x] pass · [!] fail (link an issue/note) · [-] N/A this iteration.
    • Check IDs are permanent. Never renumber. New checks get new IDs at the end of their section; removed checks stay listed, struck through, marked retired — the history is the point.

    A. Preconditions¶

    • [ ] Visual Studio 2026 MSVC toolchain, CMake 3.28+, Ninja present.
    • [ ] extern\vcpkg\vcpkg.exe bootstrapped (see README).
    • [ ] Vulkan-capable GPU driver installed (vulkan-1.dll present); discrete GPU (RTX 5090) is the render device.
    • [ ] Test-asset anchors. (none yet — the first anchor will be the fixed-seed test world once terrain generation lands; keep the SAME seed across runs so numbers are comparable.)

    B. Build gates (automated)¶

    Pass = exit 0 with zero errors/warnings scoped to this project's own modules (third-party/vcpkg warnings don't count — grep for Dokicraft's own target names, never trust a raw exit code alone).

    B0 — One-shot runners¶

    cmake --preset windows-release && cmake --build --preset windows-release
    - [ ] Usage / exit-code contract documented inline once a runner script exists.

    B1 — Debug build compiles¶

    • [ ] cmake --build --preset windows-release — zero errors/warnings in Dokicraft targets; validation-layer/debug-only code compiled out or inert.

    C. Manual test pass (consolidated)¶

    Everything a human must still do, in one ordered pass, grouped into runnable sessions — everything §B can cover should already be green before you start this section. Steps are terse on purpose; expected results and fail signatures live in §D under the same IDs.

    Quick-smoke fallback tier. If the automated harness in §B0 can't be used, fall back to running the manual equivalents listed under each §D check instead of skipping verification entirely.

    Session 1 — engine boot / render loop¶

    • [ ] [C1] Launch the game exe; window opens, clear color renders, no validation errors in log (→ §D C1)
    • [ ] [C2] Fly camera around the test scene; stable frame rate, no flicker/tearing (→ §D C2)

    Session 2 — voxel scene¶

    • [ ] [C3] Fixed-seed test world renders: terrain visible, lighting plausible, no missing/inside-out chunk faces (→ §D C3)

    D. Check reference — detailed steps, expected results & fail signatures¶

    C1 — engine boot¶

    1. Run the built game executable from a console.
    2. Watch the log for device selection and swapchain creation.
    3. Expected: window opens on the RTX 5090 (log line names the device); clear color visible; clean exit on close.
    4. Fail signatures: device is "Intel UHD" or "Parsec" → physical-device scoring; crash before window → loader/instance init; validation spam → the offending subsystem named in the message.

    C2 — camera / frame loop¶

    1. Move/rotate with WASD+mouse for ~30 s.
    2. Expected: smooth motion, no stutter beyond shader warm-up, no tearing.
    3. Fail signatures: input lag → event pump ordering; periodic hitch → per-frame allocation or descriptor churn.

    C3 — voxel scene¶

    1. Load the fixed-seed test world.
    2. Expected: terrain matches the reference screenshot for that seed.
    3. Fail signatures: holes at chunk borders → neighbor-aware meshing; z-fighting → depth precision/near-far config.

    G. Maintaining this test¶

    • Every future check lands in both places: a terse ticked step in the §C manual pass (in the right session block) + a detailed reference block in §D under the same check ID. Never let the two drift.
    • When adding a feature, add its check(s) in the same change that adds the feature — and if it's automatable, add/extend the automated suite in the same change, not as a follow-up.
    • Keep §E's code sites accurate if files move; each risk should always name the file that currently owns it.
    • On any dependency/engine-version upgrade, re-run the full pass — upstream changes are the most likely source of surprise.
