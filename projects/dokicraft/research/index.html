    Verified findings (confidence-ranked)¶

    1. Binary greedy meshing is the CPU meshing best practice — HIGH (3-0)¶

    Meshes a 64³-padded chunk in 50–200 µs single-threaded (avg 74 µs, Ryzen 3800X) by culling and merging 64 faces at a time with bitwise ops on binary occupancy masks. Output is 8 bytes/quad (6-bit x/y/z/width/height, vertex pulling), drawn in a single glMultiDrawElementsIndirect call. Verified in code, not just README; independently reimplemented (omar-owis/VoxelEngine, multiple Rust ports — Inspirateur's is ~30× faster than block-mesh-rs). Caveats: 64³ cap includes neighbor padding (62³ meshable); merging does per-quad voxel-type lookups; benchmark excludes block-type data prep. Sources: cgerikj/binary-greedy-meshing, omar-owis/VoxelEngine, grobert.eu/voxel-techniques

    2. Acceleration structures for ray-traced voxels: wide trees > SVOs; brickmaps diverge — HIGH (3-0)¶

    Wide 4³-branching trees (Tree64): ~209 Mrays/s primary vs ESVO's 57–137 in VoxelRT's benchmarks, best incoherent-ray ratio (~0.89×). Brickmap multi-level DDA is competitive on coherent primary rays (147.7 Mrays/s) but collapses on incoherent secondary rays (0.44×; plain DDA 0.10×) from SIMD divergence. Triangle-style BVH is among the fastest (~216 Mrays/s) and is the hardware-accelerated path. Caveat: all measured on an iGPU — author estimates 5–10× on discrete; rankings may shift on RTX hardware. Source: dubiousconst282/VoxelRT

    3. GPU-driven rendering + tiny chunks (Ascendant pattern) — HIGH (3-0)¶

    With 8×8×8 chunks, ~400,000 chunks can be in view — CPU culling is a non-starter; a compute shader frustum/occlusion-culls and writes indirect draw commands + count. Far field abandons meshing for one quad per voxel with ray/box intersection in the pixel shader (Majercik et al., JCGT 2018; costs MSAA). This near-mesh/far-raycast hybrid with GPU submission is the concrete pattern for small-voxel worlds at scale. Source: vkguide.dev Ascendant geometry

    4. Vulkan is the evidence-backed API choice — HIGH (3-0)¶

    Ascendant (most complete documented small-voxel engine) is Vulkan; Dwyer implemented a new Vulkan renderer for performance after building on wgpu/WebGPU. A fully GPU-driven pipeline is achievable on OpenGL 4.6 AZDO (verified in code) — so the API choice is about hardware RT, mesh shaders, and ecosystem, not a capability wall. No verified Vulkan-vs-DX12 head-to-head survived. Sources: vkguide Ascendant, Dwyer devlog #23, omar-owis/VoxelEngine

    5. Streaming/LOD: many shallow per-chunk SVDAGs, not one deep one — HIGH (3-0)¶

    Aokana (peer-reviewed, i3D 2025): one SVDAG per 256³ chunk; CPU octree filters chunks for async load/unload; only ~5% of scene data resident in VRAM; per-chunk distance LOD. Renders tens of billions of voxels at ~6 ms average on an RTX 3060 Ti (2–4× faster than HashDAG baseline). Caveats: static scenes, opaque voxels, simple shading, screen res unstated — proves primary visibility at scale, not destructibility or GI. Source: Aokana, arXiv 2505.02017

    6. GI: probe-based DDGI is the demonstrated practical choice — MEDIUM (3-0, single source)¶

    Dwyer replaced path tracing with DDGI ("less noisy, more efficient"); supports dark caves, bright exteriors, matte/shiny/emissive materials. Pattern: once-per-model probe bake (16-voxel grid cells, BFS probe placement toward largest empty subnode, 4 probe LODs) + per-frame compute culling (active-probe worklist) + fixed total ray budget → stable frame cost. Caveat: N=1 first-person devlog; no surviving comparison vs flood-fill, VCT, or HW-RT path tracing. Source: Dwyer Voxel Devlog #23

    7. Physics: Jolt with author-prescribed voxel integration — HIGH (3-0)¶

    jrouwe's own guidance: one Body + StaticCompoundShape per chunk (keep chunks small — 16³; 16×256×16 "may already be too much"), reuse shared BoxShapes per block size; "100K static bodies should not be an issue, so even if you have 5000 chunks loaded it should be fine." Caveats: edits rebuild the chunk's compound shape and wake sleeping bodies; batch-add + OptimizeBroadPhase; dynamic-destruction performance is an open question. Source: JoltPhysics discussion #446

    8. UI: Ultralight legitimate but encumbered; RmlUi is the FOSS path — MEDIUM¶

    Ultralight is GPU-accelerated HTML/CSS/JS purpose-built for game embedding (GPUDriver API). But its "~10× lower memory than Chromium" marketing claim was refuted 0-3 in verification; core is proprietary (free only < $100K/yr revenue), not thread-safe, no WebGL/video. RmlUi: fully FOSS, retained-mode, bring-your-own-renderer, no built-in JS. Dear ImGui remains the zero-risk debug/tooling default. Sources: ultralig.ht, RmlUi discussion #331

    9. ECS: EnTT vs flecs is not perf-decisive — MEDIUM (single microbenchmark)¶

    abeimler/ecs_benchmark complex-update (~2M entities, Linux/GCC 14.2): flecs 4.0.1 42 ms vs EnTT 3.13.2 views 85 ms (groups 87, runtime-views 184, stable 51; mustache fastest at 33). Iteration/storage choices matter as much as library. Choose on ergonomics. Caveats: single benchmark, not on Windows/MSVC, both libs have newer releases. Source: abeimler/ecs_benchmark

    10. Traversal fundamentals: DDA over fixed-step for small voxels — MEDIUM (one 2-1 vote)¶

    Amanatides & Woo DDA needed ~10.5M ray iterations vs 33.8M–130.4M for fixed-step marching (steps 0.2→0.05) in Grobert's thesis testbed — the textbook result; constants are scene-dependent. Sources: grobert.eu/voxel-techniques, Notiooo/Voxel-Techniques

    11. Reference codebases — HIGH (3-0)¶

    • Luanti (ex-Minetest) — most mature OSS C++ voxel survival engine (2010–2026, 5.16.1 May 2026, ~13.5K commits). Read for whole-engine architecture (chunk serialization, networking, modding) — not rendering (Irrlicht-era).
    • VoxelRT — acceleration-structure benchmarks.
    • cgerikj/binary-greedy-meshing — the meshing reference.
    • vkguide Ascendant series — production Vulkan small-voxel engine, our closest blueprint.
    • omar-owis/VoxelEngine — GPU-driven OpenGL 4.6.
    • Aokana paper — SVDAG streaming at scale.
    • Grobert thesis + testbed — technique survey.
    • Douglas Dwyer devlogs — DDGI, Vulkan migration.

    Open questions (revisit at the phases that depend on them)¶

    Update 2026-07-12: a second verified research pass addressed these — see DEEP-DIVES.md. Q1 (hardware RT) now has a settled direction, Q2 (Jolt under edits) has a canonical integration pattern, and streaming, persistence, and worldgen gained verified findings. Q4 (GI comparison) and the meshed-LOD seam question remain open.

    1. Does hardware RT (VK_KHR_ray_tracing over voxel AABBs or meshed quads) beat software wide-tree traversal on the RTX 5090? All surviving benchmarks were software on an iGPU. → revisit at far-field/GI phase.
    2. Jolt under frequent edits / Teardown-scale destruction — compound-shape rebuild cost, broadphase churn, debris counts. Verified guidance covers static terrain only. → revisit when digging/destruction lands.
    3. SDL3 vs GLFW and vcpkg-vs-FetchContent trade-offs for this exact library set — unverified; our picks are general practice. → cheap to revisit if friction appears.
    4. At what voxel scale does DDGI probe density fail for emissive detail / contact GI, and would ReSTIR path tracing + denoising win on a 5090? → revisit at GI phase.

    Cross-check: Hazel Engine (StudioCherno/Hazel, release 2024.1)¶

    Added at user request as a real-world reference stack, with the explicit instruction to validate, not blindly adopt. Hazel is TheCherno's general-purpose 2D/3D engine (Apache-2.0; premake build; an editor Hazelnut, a runtime, and C# scripting via Coral). Facts below are read directly from its Dependencies.lua and .gitmodules at commit d16adf5, not from memory.

    The load-bearing caveat: Hazel is a traditional PBR triangle-mesh / scene-graph renderer, not a voxel engine. Its rendering paradigm (mesh rasterization, material system, Assimp-imported models) does not transfer to Dokicraft's voxel-specific pipeline (binary greedy meshing, GPU-driven culling, SVDAG/raycast far-field, DDGI) — findings §1–§6 above still govern rendering. What Hazel usefully validates is the engine-infrastructure layer around the renderer.

    Diverges — validated, keeping our choice with reason¶

    • Windowing: Hazel = GLFW; us = SDL3. Research found no verified evidence either way. Keeping SDL3 for its gamepad/audio/haptics/IME breadth (a survival game wants these); Hazel confirms GLFW is a perfectly viable fallback if SDL3 friction appears.
    • Build: Hazel = premake; us = CMake + vcpkg. Keeping CMake+vcpkg for its dependency management and tooling ecosystem; premake is lighter but hands you manual vendored submodules (Hazel vendors ~25 of them).
    • Vulkan SDK: Hazel requires it; us deliberately SDK-free (volk + vcpkg headers + runtime shaderc). Keeping the SDK-free approach — it builds on a clean machine, which Hazel's os.getenv("VULKAN_SDK") does not.
    • Shader language: Hazel = HLSL→dxc; us = GLSL→shaderc. Noted as a real alternative (HLSL+dxc is increasingly the modern default). Not switching now, but reconsider if/when the shader system matures.

    Worth adopting from Hazel (validated additions, not in the original stack)¶

    • Tracy profiler — adopt early (vcpkg tracy). A frame/zone profiler is high-value infrastructure for a performance-critical voxel engine and cheap to wire in. Best pulled in during §3.
    • SPIRV-Cross — adopt when the shader system needs reflection (auto descriptor-set/pipeline-layout generation). vcpkg spirv-cross.
    • stb (stb_image) — texture/image loading; will be needed for block atlases. vcpkg stb.
    • Deferred / later-phase, noted: MiniAudio (audio), Assimp (non-voxel model import, if ever), yaml-cpp (scene/config serialization — voxel chunks still want binary), msdf-atlas-gen + Freetype (crisp text), magic_enum (reflection-lite utility), NVIDIA Aftermath (GPU crash dumps on the RTX 5090 — proprietary, not in vcpkg).

    Structural patterns to borrow (Apache-2.0 permits adapting code with attribution)¶

    Hazel's module split is a proven shape for exactly this kind of project and matches Dokicraft's intended layout: a core engine library, a separate editor app (ImGui-based), a thin runtime/launcher, and an asset system. Adopt the organization; write our own voxel renderer inside it.
