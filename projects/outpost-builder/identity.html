Instance Identity and the Baked Registry

Everything on the Architecture page describes actors that find each other by a shared FPrimaryAssetId. That was true while one UOutpostDefinition meant exactly one placed outpost. It stopped being the whole story once a definition became a reusable template, and this page is the part that changed.

The short version: a definition now answers "built from what", and a new per-instance GUID answers "which one". A per-level registry asset bakes each placed outpost's default state so a simulation layer can read it while that level is streamed out.

Note: everything on this page is verified by compiler and 23 automation tests, and none of it has ever been watched running in an interactive editor. Current state says exactly what holds and on what evidence.

Why It Exists

The driving requirement was not "find the actor when it isn't loaded". It was a strategic layer sitting over a streamed world:

Bake off the default state of an outpost so that we can simulate its state even when the actor isn't loaded, and know what the handle to the actor and state is going to be before it loads, so we can get access.

Three things fall out of that:

  • The handle has to be stable and knowable before load, which rules out anything resolved by a live-world query.
  • The state has to be readable with the level unloaded, which means it has to be baked somewhere resident.
  • The handle has to survive the moment the level does load, so the same id addresses the baked entry and the live actor.

We evaluated NamedIdsPlugin for the handle and turned it down. It resolves by live-world query, and a target whose level is not loaded resolves to nothing, which is the exact requirement. Two of its ideas were worth borrowing anyway: re-key the ARRIVING copy rather than the incumbent, and fail closed on ambiguity.

The Handle

FOutpostInstanceId is an FGuid in a wrapper, carried as a UPROPERTY on all four family actors.

// OutpostBuilder/Source/OutpostBuilder/Core/OutpostInstanceId.h
USTRUCT(BlueprintType)
struct OUTPOSTBUILDER_API FOutpostInstanceId
{
    GENERATED_BODY()

    UPROPERTY(VisibleAnywhere, BlueprintReadOnly, Category = "Outpost")
    FGuid Value;

    bool IsValid() const { return Value.IsValid(); }
    static FOutpostInstanceId Generate(); // ... defined inline in the header
};

It's a wrapper rather than a bare FGuid because the family already carries an unrelated one. AOutpostPlot::PlotId identifies a plot's record within a definition, and passing one where the other belongs would compile perfectly. The wrapper makes that a type error.

The property is written out in each of the four headers rather than pasted from the accessor macro next to it. That is not a style choice.

UHT does not run the preprocessor, so a UPROPERTY inside a user-defined macro is invisible to reflection. It still compiles, as a plain C++ member that never serializes and never appears in Details.

Grep the generated .gen.cpp for NewProp_<Name> after adding any reflected member. Zero hits means UHT never saw it.

Definitions Became Templates

bForkDefinitionOnStamp on the settings asset is the switch.

Leave it on (the default, and what every page written before this one assumes) and stamping a prefab forks a private copy of the definition. One definition, one outpost, and the plugin behaves exactly as Prefabs describes.

Turn it off and a definition is a template many placements share. That is the mode this whole system exists for, and it changes what the definition means: it becomes the spawn-time default rather than the record of what is currently placed.

Because of that, a write to the definition is no longer a write to "this outpost". It's a write to every sibling's starting state. Every path that writes a record therefore asks whether the template is private first:

// The template is writable only while this outpost is its ONLY placement.
const bool bTemplateIsPrivate = !HasOtherActorSharingDefinition(Outpost);

When it isn't private, the write is refused and the actor keeps the data itself. The plot actor already carried its own PlotId, AssignedBuildingId, PlotSizeTag and PlotTags, so for the most part this is the actors becoming authoritative over data they were already holding.

Finding Family

Every ownership question now goes through an identity-preferring wrapper. It uses the instance id when there is one and falls back to the definition when there isn't:

template <typename AnchorT, typename Fn>
void ForEachFamilyActorOfIdentity(UWorld* World, const AnchorT& Anchor, Fn&& Visitor)
{
    if (Anchor.GetOutpostInstanceId().IsValid())
    {
        ForEachFamilyActorOfInstance(World, Anchor.GetOutpostInstanceId(), Forward<Fn>(Visitor));
        return;
    }

    ForEachFamilyActorOfDefinition(World, Anchor.GetOutpostDefinitionId(), Forward<Fn>(Visitor));
}

That fallback is load-bearing and worth understanding before you touch it. Content authored before instance ids existed has none, and outposts whose template is shared deliberately never get one, because with only a definition id to go on nothing can tell one placement's plots from another's. The fallback is what keeps all of that working instead of orphaned.

Anything that removes it, including a future sweep that "finishes the migration" by making these wrappers instance-only, silently detaches every shared-template placement in the project.

A blank identity matches nothing, in both directions. An anchor with neither id owns nothing at all, which stops an outpost dragged in from Place Actors sizing its bounds volume around every stray plot in the map.

The Baked Registry

UOutpostLevelRegistry is one UPrimaryDataAsset per level, holding an FOutpostBakedInstance per placed outpost:

Field What it carries
InstanceId The handle, known before the level loads
DefinitionId Which template it was built from
DisplayName, Faction Per-instance, not per-template
AnchorTransform World transform of the anchor
Plots Every plot with its building, size, tags and framing
OverheadCamera The saved framing
TerritoryBounds World-space bounds, so a query can answer "what is near here" without loading
AnchorActorPath Diagnostic only, deliberately an FString

AnchorActorPath is a string rather than an FSoftObjectPath on purpose. A soft path is a cook-graph edge, and under One File Per Actor it points into /Game/__ExternalActors__/, which would make the registry a recursive cook manager of the level's external actor packages. Nothing resolves it to answer a query. The bake is the answer.

One asset per level rather than one per project keeps edits local, so two designers working different maps never touch the same file.

The asset name carries a hash of the full package path. A primary asset id keys on the asset's SHORT name, so two levels both called "Main" in different folders would otherwise mint one id and make every outpost in one of them unanswerable.

Treat the registry as a generated artifact. It is derived from the actors, and it carries bBakeWasComplete plus IncompleteReasons to say how far to trust itself.

When It Bakes

Three paths BAKE it, and all three key on the level the ACTOR lives in, so an outpost in a streaming sublevel belongs to that sublevel's registry. A fourth path REPAIRS it, described under Reading It:

  • Per-actor, incrementally, as you edit.
  • On world save. PostSaveWorldWithContext also fires during cook, so the handler's first line is a cook guard. Without it the cooker silently overwrites a good designer-verified registry with a worse one assembled from cell-order streaming, and no editor test catches it.
  • The UOutpostRegistryBuilder commandlet, for a full pass over a partitioned map.

An FOutpostBakedInstance carries a ContentHash so an untouched outpost's entry is left alone. The hash is computed from the projected ENTRY rather than by re-walking the actors, so "the hash covers the payload" is true by construction.

Two things it deliberately avoids:

  • No FName-keyed hashing. FName hashes are a process-specific name-table index and would rehash every entry every session.
  • String terms use FCrc::StrCrc32, which is case-sensitive. GetTypeHash(FString) folds case, so a rename from Base to BASE would never have reached the registry.

Under World Partition a save only sees the loaded cells. The bake knows that and records why in IncompleteReasons, and it never retires an entry, because it cannot tell deleted from unloaded.

Deleting an outpost retires its own entry, in the delete's transaction, recoverable by undo and listed in the registry's RecentlyRemoved.

The bake is the only source that never retires. The other two do:

  • The map-open repair retires an entry whose anchor package is proven gone from disk.
  • The builder commandlet retires under earned completeness.

An outpost the bake cannot bake, because its shared template blocks migration, is named in the log rather than dropped in silence.

Reading It

UOutpostRegistrySubsystem is a UEngineSubsystem, so every registry is resident and answerable with no level loaded:

const FOutpostBakedInstance* FindInstance(const FOutpostInstanceId& InstanceId);
FName FindLevelForInstance(const FOutpostInstanceId& InstanceId);
AOutpost* FindLiveOutpost(UObject* WorldContextObject, const FOutpostInstanceId& InstanceId);
void GetInstancesContainingPoint(const FVector& Point, TArray<const FOutpostBakedInstance*>& OutInstances);

MakeLevelKey lives in the runtime module for the same reason. PIE renames packages with a UEDPIE_ prefix, and a caller who reached for World->GetOutermost()->GetName() in PIE would match nothing baked in the editor and get an empty array that reads as "no outposts here" rather than as a failure.

Every FOutpostBakedInstance* points into a registry's own array. Read what you need and don't store it. At cooked runtime nothing bakes, so they're stable for the session.

Two console commands exercise the whole path with no commandlet: Outpost.BakeRegistry then Outpost.DumpRegistry.

The Repair Pass

The bake writes what the world says. It cannot repair what the world and the registry disagree about, because the editor produces skews no write path is present for: a save declined after a delete, an undo, a Save As that clones every actor with its id, a deletion made outside the editor entirely.

So one pass runs on every map open, before the auto-bake toggle is even consulted, and it makes three repairs in a walk each:

  • Un-retire a live outpost. A retire mutated the resident registry, then the level save carrying the delete was declined (or the delete undone). The live actor wins and its entry returns, re-anchored to the actor that is actually there.
  • Re-key a Save As clone. Save Current Level As copies every actor with its id, so two levels claim one handle. Whichever map opens first re-keys ITS copy to a fresh id - deterministic and self-resolving - and only when the other side's anchor package genuinely exists on disk.
  • Scavenge a completed deletion. An entry with no live actor whose anchor package is gone from disk was deleted somewhere this editor never saw. Retired, and recoverable like any retirement.

All three rest on one primitive worth naming, because guessing is what the rest of the system spent three reviews learning not to do:

// True when the entry's anchor actor package is still on disk. Under One File Per Actor a completed
// deletion removes it; a declined save, a pending undo or an unloaded cell all leave it there.
static bool DoesBakedAnchorExistOnDisk(const FOutpostBakedInstance& Entry);

That distinction is the whole reason the repair can act at all. "No live actor" alone means nothing under World Partition - most outposts are unloaded most of the time. The package's absence is proof.

It also gates what Restore is allowed to offer: a retirement whose anchor is still on disk is skew, never a candidate, because restoring it would spawn a second claimant on a handle a living outpost already holds.

Note that nothing on the subsystem is a UFUNCTION. The data types are all BlueprintType with BlueprintReadOnly fields, but the API that turns a handle into data is C++ only. A Blueprint simulation layer would need that surface added.

Current State

The two defects that used to sit here - the ones that broke the goal - are closed, and the mechanism that closed them is worth knowing because it defines what the registry means now.

Retirement is the liveness signal. An entry in a registry's Instances is a placed outpost, loaded or not.

Deleting an outpost through the editor retires its entry into RecentlyRemoved inside the delete's own transaction. The registry is transactional, so undo restores entry and actors together, and Restore brings it back re-anchored to the new actor.

bVerifiedThisBake reverted to what it always meant, "the last bake saw it", a staleness hint the dump reports. Nothing derives existence from it anymore.

Two consequences. A partial World Partition save hides nothing. And a paste over an unloaded cell is contested by the registry and re-keyed, instead of silently sharing a handle with the streamed-out original.

The honest edges, stated rather than implied:

  • Nothing here has run in an interactive editor. Compiler plus 23 automation tests (the riskiest branches negative-controlled) is the entire evidence base. TESTING.md steps 119-126 script the session that checks it.
  • An out-of-band deletion lingers only until that map is next opened. Deleting an outpost outside the editor's delete path - source control revert, another user's change - used to wait for a registry-builder pass. The map-open repair now scavenges it: an entry with no live actor whose anchor package is absent from disk is a completed deletion, proven rather than guessed, so it is retired (and recoverable, like every retirement). What lingers is the window until that map opens, and the builder pass is still the fallback for levels nobody opens.
  • One undo wart remains (research/28 finding 20): undoing immediately after a paste undoes only the re-key step first, leaving two actors on one id until the next undo removes the paste itself.

Tests

The identity and registry surfaces are covered by automation tests under OutpostBuilder/Source/OutpostBuilderEditor/Tests/, run headless by scripts/run-tests.bat. Each test is named for a defect that actually shipped.

They cover:

  • The content hash, and the registry's upsert and retire rules.
  • Migration being atomic per family, and blank-identity matching.
  • The shared-template write guard, and the duplicate and paste re-keying rule.
  • The deliberate-spawn scope.
  • Reclaim-before-mint: an actor adopts the id a registry entry already anchors to its path.
  • The ghost list's disk-truth gate: a retirement whose anchor still exists on disk is skew, and is never offered for restore.

They do not cover the five editor listeners or the delete cascade, and the test files say so.
