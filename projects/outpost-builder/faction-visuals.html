Faction - Identity and Gating

EOutpostFaction is pure identity and eligibility, with zero visual effect. It decides which buildings a plot may field and nothing else. No tint, beam hue, or border color derives from it. This page covers the faction model and where the plugin's colors come from instead.

The Enum

EOutpostFaction (OutpostBuilder/Source/OutpostBuilder/Core/OutpostFaction.h, UENUM(BlueprintType)) is { Neutral, Faction1, Faction2, Faction3 }, and its header comment says plainly what it's for:

/**
 * Faction identity for an outpost: pure identity and eligibility, no cosmetic effect of its own.
 * Which buildings a faction may field is decided by UOutpostBuildingDefinition::SupportsFaction.
 * Append-only: this serializes as a raw uint8, so never reorder or renumber an existing enumerator,
 * and pair any rename with a `+EnumRedirects` entry in this plugin's Config/DefaultEngine.ini.
 */

The comment's last two lines are the APPEND-ONLY rule (not a visuals concern, but worth knowing). They cover a different hazard: EOutpostFaction serializes as a raw uint8 everywhere a faction is saved, so an existing enumerator's value must never be reordered or renumbered.

Renaming one needs a matching +EnumRedirects entry in this plugin's Config/DefaultEngine.ini so saved content heals instead of silently reverting to Neutral. See the header itself for the full contract.

AOutpost carries it as a plain property, with GetFaction()/SetFaction():

UPROPERTY(EditAnywhere, Category = "Outpost")
EOutpostFaction Faction = EOutpostFaction::Neutral;

SetFaction() follows the same no-op → Modify() → mutate → MarkPackageDirty() discipline as every setter in the plugin:

void AOutpost::SetFaction(EOutpostFaction NewFaction)
{
    if (Faction == NewFaction)
    {
        return;
    }

    const EOutpostFaction OldFaction = Faction;

    Modify();
    Faction = NewFaction;
    MarkPackageDirty();

    UOutpostEventSubsystem::NotifyFactionChanged(GetWorld(), this, OldFaction, NewFaction);
}

The write ends with a UOutpostEventSubsystem::NotifyFactionChanged broadcast, so any listener (game or editor) can react to a faction change without polling.

What Faction Controls: Which Buildings a Plot May Field

The one thing faction does is gate UOutpostBuildingDefinition::SupportsFaction:

bool SupportsFaction(EOutpostFaction OutpostFaction) const;

Takes the outpost's faction, not the building's, and is the one home of the rule. Never test SupportedFactions (TSet<EOutpostFaction>, default empty) directly:

  1. A Neutral outpost accepts every building, regardless of what SupportedFactions lists, checked first, before the set is read at all.
  2. An empty SupportedFactions list is a wildcard ("supported everywhere"), not "supported nowhere". That's the state every building authored before this field existed, or any building a designer never touches the field on, deserializes to.

UOutpostBuilderEdMode::GetFactionForPlot(Plot) is the read side: it resolves the plot's owning outpost (FindOwningOutpostForIdentity: the plot's instance id first, and the definition-unique lookup only as the unmigrated fallback, both failing closed on ambiguity) and returns its GetFaction(), or Neutral if there's no unique owner.

Neutral is the deliberate, honest fallback for "can't resolve" too. Neutral accepts everything, so an unresolvable owner never refuses a building it can't actually justify refusing.

That gate reaches two places in the Editing panel:

  • The Assign button - AssignBuildingToSelectedPlot re-checks eligibility authoritatively before writing the record (the button's own per-frame check is load-free and permissive when the definition isn't resident, so this is the real backstop); a mismatch disables the button and shows a refusal tooltip/toast:

"This outpost's faction does not field this building. Add that faction to the building's Supported Factions, clear that list to allow every faction, or set the outpost's faction to Neutral - a Neutral outpost accepts every building."

  • The palette itself - FOutpostPaletteModel::PassesFilters applies the same rule as a mandatory view filter: a building the editing outpost's faction can't field isn't shown disabled, it's left out of the palette entirely. If the gate empties the palette down to nothing, an explanatory text row naming the faction takes the grid's place.

Randomize's building pool excludes the same buildings. This gating is the entire reason EOutpostFaction exists on an outpost.

The Picker: Text Only

The Editing panel's identity header hosts a Faction row built from the engine's SEnumComboBox, constructed once with StaticEnum<EOutpostFaction>(). Its CurrentValue is a live TAttribute<int32>.

The widget re-resolves Context->GetEditingOutpost()->GetFaction() every frame rather than caching a mirror, so the combo needs no external refresh call anywhere. No post-undo/redo push, no settings-asset-changed push, nothing.

A genuine user pick fires OnEnumSelectionChanged, cast back from int32 to EOutpostFaction and handed to HandleFactionSelected, which fires the widget's OnFactionChanged delegate (it owns no faction state of its own to update first).

The toolkit's HandleFactionChanged answers that by calling UOutpostBuilderEdMode::AssignFactionToEditingOutpost and then re-running the palette's visible-entries refresh:

void UOutpostBuilderEdMode::AssignFactionToEditingOutpost(EOutpostFaction Faction)
{
    if (!CanAssignFaction()) // IsEditingOutpost()
    {
        return;
    }
    // PIE gate: every persistent-record mutator refuses while Play/Simulate is active.
    if (IsPlayOrSimulateActive())
    {
        ShowPlayOrSimulateActiveToast();
        return;
    }
    // ...
    FScopedTransaction Transaction(NSLOCTEXT("OutpostBuilder", "AssignFactionTransaction", "Assign Faction"));
    Outpost->SetFaction(Faction);
    if (UOutpostDefinition* Definition = GetOrCreateOutpostDefinitionForOutpost(Outpost))
    {
        Definition->SetFaction(Faction);
    }
}

That's it. It writes the live actor always, and the definition asset only while this outpost is the definition's ONLY placement - a shared template gets the actor write alone, so one placement's faction can't spread to its siblings the next time each is edited.

The click refuses outright, transaction cancelled, if no definition resolves at all. There is no color swatch in that row.

The combo shows the enum's display text only (SEnumComboBox's own GetCurrentValueText, reading StaticEnum<EOutpostFaction>()'s DisplayName metadata), and the row's tooltip says so outright.

There's a seam worth knowing about here. SEnumComboBox also binds its OWN per-value tooltip from the enum's ToolTip metadata, which EOutpostFaction doesn't carry, so that resolves empty and Slate falls through to this row's tooltip instead:

"Sets the faction of the outpost being edited. Faction gates which buildings its plots may field - it never changes their appearance."

The mandatory outpost-faction gate is the one faction rule the palette applies, and the Assign picker's own faction narrowing follows the same gate. A faction-ineligible building isn't shown as a disabled or chipped tile. PassesFilters' mandatory gate leaves it out of the palette entirely, so there's no tile left to grey out.

The Definition Asset Is the Source of Truth

A designer doesn't set Faction on the live actor directly. Note the definition is the authoritative home only while it backs a single placement - shared, it is the spawn-time default and each placement's actor owns its faction.

There is a third home besides those two: FOutpostBakedInstance::Faction in the level registry, written per instance by the bake and read back by RestoreOutpostFromBaked, so a registry-driven restore takes faction from the bake rather than from the definition asset.

UOutpostDefinition::GetFaction()/SetFaction() is the persistent, authoritative value. The live AOutpost::Faction syncs down from it on edit-entry only when this outpost is the definition's sole placement and the two have actually drifted (in-sync opens no transaction at all).

A shared template leaves each placement's actor faction alone (EnterOutpostEditMode), and also the moment the definition asset itself is edited directly in its own asset editor (via FOutpostBuilderEditorModule::OnDefinitionAssetPropertyChanged).

That handler finds the UNIQUE live outpost bound to the edited definition's id and calls SetFaction(Definition->GetFaction()) on it. An ambiguous id (shared by more than one live outpost) means the handler writes nothing rather than guess.

No Faction Color Anywhere

Faction drives no color. If you're porting from a fork that predates this (or reading old comments, commits, or research/03-faction-visuals-research.md), none of the faction-color machinery exists to hook into: no FactionColors map on the settings asset, no GetFactionColor/GetDefaultFactionColor resolver, no ApplyFactionColor/RefreshFactionVisuals, no faction swatch on any Slate row, and no faction branch in the beams, territory borders, or selection markers.

The one removal a porter must act on is Custom Primitive Data: faction tinting was CPD's only use, so the plugin writes no CPD at all now (a repo-wide grep for CustomPrimitiveData/CPD across OutpostBuilder/Source turns up nothing). If your project drove float4 index 0 off an outpost or plot as "the faction color," that node now reads nothing. Drop it.

Where Colors Come From Instead

Every surface that might plausibly take a color from faction instead uses a fixed or deterministic-but-faction-blind source:

  • Ownership beams (OutpostBuilder::Draw::Private::ResolveBeamBaseColor, OutpostBuilderDraw.cpp) - every beam cycles UOutpostBuilderUserSettings::BeamVibrantPalette (a designer-editable TArray<FLinearColor>), indexed by GetTypeHash(Plot->GetPlotId()) % BeamVibrantPalette.Num().
    • That's deterministic per PLOT (stable across frames, unaffected by selection order) and does not read Faction. The rule is written down on the Beam Color Palette property tooltip in OutpostBuilderUserSettings.h: "beams convey direction, not faction, so this is deliberately not a faction color".
    • An empty palette or a null outpost falls back to PlotGhostColor.
  • Territory borders (DrawTerritoryBorders, OutpostBuilderDraw.cpp) - always UOutpostBuilderUserSettings::TerritoryBorderColor for every AOutpostVolume in the level. A border never varies by the volume's owning outpost's faction, though a volume outside the outpost being edited is desaturated and dimmed by ApplyOutOfScopeFade when bDimOutOfScopeOverlays is on.
  • Selection markers (DrawSelectionMarkers, OutpostBuilderDraw.cpp) - UOutpostBuilderUserSettings::SelectionRimColor for a normal selection, SelectionOverlapRimColor for a plot overlapping a sibling's footprint. Neither has ever branched on faction.
  • The plot ghost's placement color (UOutpostBuilderEdMode::GetPlotGhostColor)
    • A hard RTS-style pick between three Debug|Ghosts colors, no gradient: UOutpostBuilderUserSettings::PlacementPlateValidColor, PlacementPlateWarnColor, and PlacementPlateInvalidColor, chosen by GetPlacementFeedback()'s three-state verdict.
    • Amber is a status color reporting a plot-tag advisory, not a faction color, and its own property tooltip says so.
    • PlotGhostColor also serves as the ownership beams' fallback color (see above) for a null outpost or an empty BeamVibrantPalette. None of these colors is faction-derived.

All four knobs live on UOutpostBuilderUserSettings (the per-user editor-preferences class) and are ordinary designer-tunable colors.
