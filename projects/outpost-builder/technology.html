Technology & Trade-offs

Every other page on this site explains how a part of OutpostBuilder works. This one explains why it is built out of these particular pieces: what was chosen, what was rejected, what each choice buys, and what it costs. The costs are the point: a technology page that lists only advantages is a sales sheet, not documentation.

Nothing here is aspirational. Every claim is drawn from the shipped code, the research notes under research/, or the project's own commit history.

The choices at a glance

References FPrimaryAssetId between the plugin's own assets and actors Hard TObjectPtr (asset payloads stay soft) Name-based ids; renames orphan actors in unloaded maps
Editor host UEdMode, via the UBaseLegacyWidgetEdMode shim Staying on legacy FEdMode; going all the way to the Interactive Tools Framework Still no ITF, so new engine gizmo/snapping capability stays out of reach
Panels FModeToolkit + hand-written Slate Editor Utility Widgets, details-panel-only UI Slate by hand; a load-bearing ToolkitBuilder opt-in
Viewport feedback Immediate-mode draws, plus transient preview components Spawned preview actors Per-frame world scans while the mode is active

The one idea everything else follows from

An outpost is not an actor hierarchy. It is a record graph on a UOutpostDefinition asset, and the actors in the level are a rendering of that graph.

AOutpost, AOutpostPlot, AOverheadCamera and AOutpostVolume are never attached to each other. They share no base class and no interface. UChildActorComponent is banned outright. Membership in a base is expressed as data: every one of those actors carries an FPrimaryAssetId OutpostDefinitionId, and a plot additionally carries an FGuid PlotId matching a FOutpostPlotRecord.

Why not attachment. Attachment couples lifetimes and transforms in ways this tool actively does not want. Moving the outpost anchor should not drag its plots around, because designers move a base by multi-selecting it, not by dragging one root. Attachment also implies a parent-child ownership story that the record model gets for free from a shared id.

Why not the engine's prefab systems. Both were scouted against engine source before being declined (research/07-prefab-mechanisms.md). Packed Level Actors flatten a sublevel into batched static meshes, and PackedLevelActor.h says plainly that "Other components are unsupported and will result in an incomplete APackedLevelActor". These actors exist to carry FPrimaryAssetIds, FGuids and faction state, none of which survives packing.

Level Instances were rejected for destructive creation semantics, a hardcoded Save-As dialog on the public API, reference fragility, and per-instance overrides gated on World Partition.

What it buys. Every stamped base is genuinely independent: ordinary actors with nothing shared to keep in sync. There is no .umap per prefab, so the plugin ships CanContainContent: false and needs no World Partition. Any actor can find its family by scanning for a matching id, which is what makes recovery features like "rebuild the definition from the actors" possible at all.

What it costs. Giving up attachment means giving up free relative-transform tracking, and the tool pays for that with the whole re-relativization machinery (AOutpost::ReRelativizeOwnedRecords and its per-kind sweeps).

It also gives up edit propagation: with bForkDefinitionOnStamp on, which is the default, editing a definition after stamping does not retroactively update already-stamped copies. That is a deliberate trade, fork-on-stamp independence in exchange for no live linkage, and it is a real limitation rather than an oversight.

What changed since. That trade is now a switch rather than a law. Turn bForkDefinitionOnStamp off and one definition becomes a template many placements share, which is what the per-instance identity work exists to support.

Identity then moves to a per-instance GUID, records move onto the actors, and a per-level registry bakes each placement's default state so a simulation layer can read it with the level streamed out.

Both of the unloaded-read defects that used to sit here are closed - retirement became the liveness signal, and a paste over an unloaded cell is contested by the registry. Instance Identity covers the whole system, including the residual edges that remain.

Data model

Definitions are primary data assets; ids are the currency

UOutpostDefinition and UOutpostBuildingDefinition derive UPrimaryDataAsset, each declaring a frozen PrimaryAssetTypeName and the identical GetPrimaryAssetId() body. Every reference between the plugin's own definitions and actors is an FPrimaryAssetId with meta = (AllowedTypes = "..."), never a raw UObject* or a hard pointer held across a save.

Asset payloads are a separate question and stay deliberately soft: TSoftObjectPtr meshes, a TSoftClassPtr building actor class, and the definition's FSoftObjectPath back-pointer to its placed anchor. That soft hop is exactly what the cook rule further down depends on.

Synchronous resolution has exactly two entry points, in OutpostBuilder/Core/OutpostAssetResolve.h, and the choice between them is a single question: does this call site run every frame?

// Never loads - mandatory on per-frame paths (Render, DrawHUD, Slate attributes).
template <typename T> T* FindLoadedPrimaryAsset(const FPrimaryAssetId& Id);

// Blocking load - for one-shot user actions (clicks, mode entry).
template <typename T> T* LoadPrimaryAssetSync(const FPrimaryAssetId& Id);

The rule exists because after a GC cycle evicts an asset, a loading call on a per-frame path would hit disk every frame, while a find-only call costs one frame of fallback value. Game worlds take a third route entirely: the async chain described under game-world plot rendering.

Cost. Ids are name-based, so asset names must be globally unique, and renaming a definition orphans every actor holding the old id. The editor module patches this with an OnAssetRenamed listener.

That listener can only rebind actors in the loaded world. Actors in maps that were closed at rename time stay stale.

The two-function resolve rule is also convention, not type safety: nothing stops a loading call being bound into a per-frame attribute.

The unit-scale record basis

Records are stored relative to AOutpost::GetRecordBasisTransform() (the anchor's rotation and translation with scale forced to unit), and the multiply direction lives in exactly one place, a compose/invert helper pair in Outpost.h.

Scale is stripped for a specific reason: FTransform composition multiplies scale along with location and rotation, so a designer who scales the anchor actor (even just to enlarge its editor preview cube) would otherwise distort every plot in every future stamp, forever.

Cost. The PlacedOutpostTransform invariant that makes this work is hand-maintained. It must always name the anchor transform the current records are expressed against; anything that moves the anchor without re-relativizing (or vice versa) breaks the pairing, and the per-plot camera records are what would silently drift. Nothing detects a violation automatically.

Lookups that fail closed

OutpostBuilder/Core/OutpostActorQuery.h answers every "which actors carry this id?" question as free function templates, duck-typed on GetOutpostDefinitionId() rather than expressed as an interface or a shared base. That's deliberate, because a common base is exactly the coupling the flat model exists to avoid.

There are three named ambiguity policies, and callers must pick one: FindUniqueActorForDefinition (the owner, or nullptr when zero or more than one match), FindFirstActorForDefinition (display-ish uses), and HasOtherActorSharingDefinition (the guard every record write-back runs first).

Cost. Fail-closed here means fail-silent at most call sites. If a designer Ctrl+W-duplicates a placed outpost (a reflexive editor gesture), both copies share one id, ownership becomes ambiguous, and record write-backs simply stop.

The plots still move in the level. The asset just stops hearing about it, with no toast and no log at most sites. The state is recoverable (delete the duplicate and the survivor is unique again), but the feedback gap is real.

Every lookup is also a full TActorIterator with no cache or spatial index.

Actor classes resolve through settings, never StaticClass()

Four statics on UOutpostRuntimeSettings (GetOutpostClass(), GetPlotClass(), GetVolumeClass(), GetOverheadCameraClass()) return the TSubclassOf<> a project configured on the settings asset, falling back to the plugin's native class. Never null.

Fifteen spawn sites across all four modules route through one chokepoint (SpawnOutpostFamilyActor), plus two ActorFactory class overrides that resolve the same statics directly, so a project drops in a C++ or Blueprint subclass and every path picks it up at once, with no call site to hunt down.

Cost. The resolver reads through a Get() that never loads by design. Any spawn running before the settings asset is pre-warmed (or in an editor session after GC evicts it) resolves the CDO's constructor default, which is the plugin's own native class, so a project's configured subclass is quietly ignored with nothing logged.

No migration system: an old asset just loads with the gaps defaulted

UOutpostDefinition, UOutpostBuildingDefinition, and the settings asset all serialize as ordinary UPrimaryDataAssets: no Serialize override, no custom version, no *_DEPRECATED fields. An asset saved by an older version of the plugin loads through the engine's own tagged-property serializer, which silently drops any property the current class no longer declares and leaves any property the class has gained since at its default.

The one place a plugin path leans on that default-filling: an unset plot-size tag resolves as Small everywhere, through OutpostBuilder::PlotSizeTags::ResolveOrDefault, rather than through a migration step converting it once.

What it buys. Nothing to keep in sync. No schema-version enum, no RAII scope guarding a UsingCustomVersion call, no deprecated field that has to stay serialized forever just so an old save still parses.

Cost. There's no conversion step, so a change that isn't a plain drop-and-default (an old float that should become a new struct, say) has no code path to ride in on. That kind of change needs a one-off script or a manual re-author instead.

Editor framework

UEdMode, on the legacy widget shim, with ITF still deferred

UOutpostBuilderEdMode is a UCLASS(Transient) deriving UBaseLegacyWidgetEdMode, which is a UEdMode that also implements the legacy widget and viewport interfaces. The mode used to be a legacy FEdMode. The move off it happened deliberately, and it's worth stating what it actually changed, since the answer is "less than the class name suggests".

The migration was the platform only. It did NOT bring in the Interactive Tools Framework. The direction of travel was already documented (research/26-comparable-tools.md), and it still reads the same way:

  • There was never a deprecation. The FEdMode API page is current through 5.8 with no banner, no redirect, and no mention in the 5.8 release notes. This wasn't a forced move.
  • The directional pressure is real but soft. Epic's own tooling has moved. Modeling Mode, the UV Editor, and the modeling Static Mesh Editor are all UEdMode/ITF, and the engine ships UBaseLegacyWidgetEdMode specifically as the transition shim we're now standing on.
  • The mechanism is attrition, not removal. New gizmo, snapping, and tool-target capability lands ITF-only. That hasn't changed.

What it bought. Three things, all of them lifecycle rather than capability:

  • The mode is a UObject, which makes garbage collection a plain UPROPERTY() instead of a hand-written AddReferencedObjects that every new strong member had to be remembered into.
  • Registration is gone entirely: UAssetEditorSubsystem::RegisterEditorModes sweeps UEdMode CDOs on OnAllModuleLoadingPhasesComplete and reads each one's GetModeInfo(), so the mode's own constructor fills in its FEditorModeInfo and the editor module no longer carries a RegisterMode/UnregisterMode pair to keep in sync.
  • The toolkit is built by the base class through a CreateToolkit() override, which puts the Init() call and the BindCommands() call in the engine's hands rather than in a hand-ordered Enter().

What it cost. There is no public unregister. The mode stays listed in the Modes panel until the asset-editor subsystem tears down. A runtime plugin unload leaves a dead entry behind, where the old UnregisterMode cleaned up after itself.

Enter()/Exit() also grew ordering rules that aren't obvious from reading them: the settings pre-warm has to happen BEFORE Super::Enter() (the base call builds the toolkit, and the panels read resolved settings), and CancelPlacement() has to happen BEFORE Super::Exit() (it needs GetWorld(), served by tools contexts the base call destroys). Neither is enforced by anything.

Exit() additionally must NOT close the toolkit, since FEditorModeTools::DeactivateModeAtIndex already did, which is the kind of rule you learn from an assert rather than a signature.

What it did not buy. Any ITF capability at all. Per-instance UInteractiveGizmos and the tool-target layer stay out of reach. Getting them is a separate migration on top of this one.

The project's own gizmo research found everything else still reachable from the legacy viewport interface this mode kept: hand-rolled hit-proxy drag handles, per-proxy cursors, and the standard transform widget. That remains a tracked "someday" item rather than a fire drill.

Panels: FModeToolkit plus hand-written Slate

FOutpostBuilderToolkit is an FModeToolkit and an FEditorUndoClient. Its inline content is a two-slot SWidgetSwitcher (Overview and Editing), and its implementation is split across seven .cpp files, roughly one per designer-facing surface: the two panels, the viewport bars, and the placement overlay.

Changing a surface means opening its file rather than scanning a monolith. Almost every function is still a member (two files add small file-local factory helpers), and the split introduces no new types.

Widgets never hold the mode or the toolkit. Those that need session state receive FOutpostBuilderWidgetContext: a shared bundle of bound TAttributes and delegates, all find-only.

That converts "widget knows the toolkit" into "widget knows a small bag of getters," which is what lets each SOutpost* widget be constructed independently. Several need even less: the viewport overlay shell and the tab bar are fully generic, and the banner takes only its data block.

The building palette is the one documented exception. FOutpostPaletteModel is shared mutable state with an observer list, because the palette's several hosts (the tile grid, the in-viewport command grid, the assign row, the Selected Building panel) must agree on the hot building by construction rather than by convention.

Cost. The ToolkitBuilder opt-in that makes panels height-bounded is a load-bearing dependency on engine internals rather than a documented contract. The widget-context invariant is convention-enforced: nothing in the type system stops a loading getter being bound into a per-frame attribute, and an unbound field fails silently, which is why the toolkit carries an explicit sweep to catch it.

Editor-only actor logic lives in the runtime module, not the editor module

OutpostBuilder/Core/OutpostActorEditingLibrary.h holds AOutpost and AOutpostPlot's editor-only behavior (record sync, cascade delete, import-identity handling, the mirrored-building preview) as free functions in OutpostBuilder::ActorEditing, each taking the actor as its first parameter. AOutpost::PostEditMove, Destroyed, and the matching AOutpostPlot hooks are one-line forwards into it.

Two constraints put it there instead of somewhere more obviously editor-side:

  • The hooks themselves are UObject virtual overrides (PostEditMove, PostEditChangeChainProperty, Destroyed, PostDuplicate, PostEditImport), and a virtual override can't move out of the class it overrides, so AOutpost/AOutpostPlot keep them.
  • Those classes live in the runtime module, OutpostBuilder, because a packaged game spawns and simulates them with no editor module loaded at all, and the runtime module can't link OutpostBuilderEditor to borrow its help.

The whole file is wrapped in #if WITH_EDITOR, so none of it reaches a cooked build even though its address is the module that ships.

What it buys. Outpost.cpp/OutpostPlot.cpp shrink to the one-line forwards plus their runtime-relevant code (mesh resolution, the plain accessors), and the editor-only logic reads as an ordinary function taking its subject as a parameter, easier to read and to grep as one file instead of interleaved with #if WITH_EDITOR blocks inside the actor's own method bodies.

Cost. The split is a naming and file-location convention, not something the compiler enforces. Nothing stops a future hook's body from growing back inline on the actor class instead of forwarding, and reading the whole story of what one lifecycle hook does still means opening both files.

The mode draws the viewport itself

Footprint rings, selection markers, ownership beams, outpost labels, the outpost placement ghost and the invalid-placement text are immediate-mode drawing from Render and DrawHUD through FPrimitiveDrawInterface and FCanvas. Those draw functions are free functions taking explicit parameters. None of them holds a reference to the mode.

The geometry itself lives one layer further down, in OutpostDrawPrimitives: segments, rectangles, wire squares, rings, pulsed beams, and screen text, built with zero Outpost types anywhere in it.

OutpostBuilderDraw.cpp's functions gather Outpost state (which actors are selected, a beam's color, whether a border needs the out-of-scope fade) and hand it to that layer, which any other editor tool in the project could link against untouched.

Two pieces of feedback are deliberately not immediate-mode, and it is worth being exact about them: the plot placement ghost and its RTS-style plate are real transient UStaticMeshComponents registered into the editor world for the session (a mesh preview is not something line primitives can draw), and the HUD banner is a Slate overlay widget. What is rejected everywhere is spawning preview actors.

What it buys. Zero level pollution: nothing the tool previews can be selected, saved, or orphaned in the map. Restyling the structural draws is an edit to one .cpp, and the colors and sizes are settings knobs that need no code edit at all.

Cost. Immediate mode means recomputing every frame the mode is active, including world scans for the beams and the banner. One instance of that cost was measurable enough to need fixing: the banner recomposed its whole block on every Slate getter, a dozen-plus times per repaint, and now memoizes per engine frame. The general pattern's cost still scales with world size.

Where settings live, and the question that splits them

Surface Type Holds
Editor Preferences → Outpost Builder UOutpostBuilderUserSettings (UDeveloperSettings, config = EditorPerProjectUserSettings, editor module) Look and feel: colors, sizes, timings, hotkey modifiers
The settings asset UOutpostBuilderSettingsAsset (UPrimaryDataAsset, runtime module) Anything affecting validity: plot dimensions, exclusion distance, actor classes, folders
Project Settings → Outpost Builder UOutpostRuntimeSettings (UDeveloperSettings, config = Game) The pointer to that asset, plus the config-persisted pinned-buildings list

The line is drawn on whether a difference between two designers would change behavior. A tuned beam palette is personal and must never land in source control; a plot-size dimension is a project rule and must.

A few values skip that question entirely because they aren't a knob at all: plain constexpr in OutpostBuilderDraw.cpp's Private namespace (tessellation and segment counts, HUD text offsets, the out-of-scope fade amounts, the alignment-guide and selection-rim thickness), plus one shared instance, OutpostBuilder::UserSettings::BeamThickness, for the single constant more than that one draw TU needs.

Nothing there is meant to be retuned per project or per designer, so it isn't exposed as either kind of setting.

Cost. That boundary is a human judgement re-made per knob, and nothing enforces it. A validity-affecting value dropped into the per-user class would produce machine-dependent placement rules, precisely the failure the split exists to prevent.

One transaction per action, both halves inside it

Every mutating action opens a single named FScopedTransaction and, inside it, writes the live actor, the matching definition record, and - where identity is involved - the level registry entry. This is the write-through law.

It's why one Ctrl+Z restores level, asset and registry together (a whole-base delete is the case that deliberately keeps the definition record while retiring the registry entry), and why the actors constitute a complete enough backup of the asset for "rebuild the definition from the actors" to work.

Actions resolve the definition before writing anything that persists: Assign Building, Randomize and Assign Faction refuse with a message rather than writing the actor half alone. Placement is the necessary exception: creating a definition asset cannot be undone by cancelling a transaction, so it spawns the plot first and destroys that just-spawned actor if the definition turns out to be unresolvable.

Cost. The law is per-call-site discipline, not a type or a helper. Every new mutator must remember both halves, the ordering, and cancelling the transaction when nothing was written. There is no compiler help.

Asset creation is also not undoable (a cancelled transaction discards the undo record but does not un-create a minted asset), which is why placement spawns first and only then creates.

Correctness from editor lifecycle hooks, and what that really costs

Record coherence is enforced from actor hooks rather than a reconciler pass (the level registry is the exception, and has one - see Instance Identity): PostEditMove and PostEditChangeChainProperty sync transforms (typed Details-panel edits never fire PostEditMove), PostEditUndo re-derives visuals, PostDuplicate/PostEditImport handle copies, and Destroyed is the one home for record removal on delete paths outside the tool, so no outliner or other-mode delete can leave an orphan.

(The tool's own delete paths remove records explicitly, and a whole-base delete deliberately keeps its records. That is exactly what Restore rebuilds from.)

Every mutation entry point is additionally gated on Play/Simulate, with a BeginPIE hook cancelling in-flight sessions.

This is the most fragile class of code in the plugin, and the honest evidence is the project's own history.

The batch that made deletion always sync took four commits in one day: the batch itself, then three adversarial verification rounds, one of which proved the previous design rested on false assumptions about the engine. What that round established, by reading engine source:

  • DeleteActors deselects each actor immediately before destroying it. That means a dying actor always reads as unselected, while other members of the doomed selection still read as selected.
  • Paste and duplicate fire PostEditImport (sometimes twice) and PostDuplicate on the same new actor.

A third fact the design leans on (TActorIterator skips pending-kill actors, so an already-destroyed owner is unfindable) was already on record from the project's earlier engine research.

The final design accounts for all of it: an RAII scope marks whole-base deletes, the tool's own paths remove records explicitly rather than relying on inference, import handling is idempotent and reclaims a kept record before minting a new one, and every ambiguous case fails toward keeping a record rather than stripping one.

Cost. These are engine behaviors, not APIs with compatibility guarantees. Each one would have to be re-verified against a new engine version, and there is no test that would catch a regression automatically.

Assets, cooking and packaging

The scan lives in the runtime module, fused with AlwaysCook

RegisterOutpostAssetType<T> pairs two calls that must never be separated:

AssetManager.ScanPathsForPrimaryAssets(T::PrimaryAssetTypeName, { TEXT("/Game") },
    T::StaticClass(), /*bHasBlueprintClasses=*/false, /*bIsEditorOnly=*/false);
AssetManager.SetPrimaryAssetTypeRules(T::PrimaryAssetTypeName, Rules /* AlwaysCook */);

AlwaysCook is mandatory, not tuning. Nothing reaches these packages by an edge the cooker follows: definitions are referenced only by FPrimaryAssetId (a name pair, not a package reference), the settings asset only by an ini-hosted soft path, and the per-level OutpostLevelRegistry by nothing at all - it is found by name lookup alone.

With the default cook rule a packaged build drops all four silently. For the definitions that means every plot renders a fallback mesh with nothing logged. For the registry it means every unloaded-level lookup returns nothing, which reads as "no outposts here" rather than as a failure.

Registration sits in the runtime module even though scanning feels like editor plumbing, because packaged games never load the editor module yet still must resolve the same ids the editor wrote. Fusing the two calls in one template means a new definition type cannot be registered half-correctly.

Cost. The cook rule is type-wide and unconditional, so every definition asset anywhere under /Game force-cooks (scratch and work-in-progress assets included) with no per-asset opt-out. The scan path is also the hardcoded literal /Game.

Definitions under a configured out-of-/Game created-definition folder still resolve in the editor, through a separate editor-module rescan, but are invisible to a packaged build (warned, not prevented). A definition hand-authored anywhere else resolves in neither.

Game-world plot rendering

A plot carries one runtime UStaticMeshComponent. RefreshBuildingForCurrentWorld() forks on UWorld::IsGameWorld(): game worlds take an async load chain (cancelled on EndPlay/BeginDestroy, guarded by a serial so a late callback cannot apply a superseded result), while editor worlds stay synchronous so authoring feedback is immediate.

The resolution ladder never leaves a plot invisible: assigned building mesh, then the project's empty-plot mesh, then a fallback.

Async exists in game worlds because component registration is not editor-guarded: it runs for every plot at level load, on the game thread inside time-sliced streaming work, where a synchronous load hitches.

Cost. Two implementations of one ladder that must never drift, with nothing enforcing agreement. There is no batching either. N plots issue up to 2N requests.

Two engine versions, two named seams

The plugin targets UE 5.7 and 5.8. The standing rule is to prefer APIs present in 5.7. A genuinely required newer API gets a UE_VERSION_OLDER_THAN(5, 8, 0) seam with a working 5.7 fallback, homed in a named helper rather than scattered through call sites.

Two named helpers exist today: the post-engine-init delegate accessor (deliberately kept as one copy per module that needs it, so a grep finds four guarded blocks in total) and a details-view flag that simply degrades to visible category headers on 5.7.

Cost. The compatibility claim rests on an API audit rather than a continuously green 5.7 build in this repository. The 5.7 side is verified by discipline and review, not by CI.

The risks worth carrying into any decision about this tool

Most of the costs above are local. These are the ones that shape the whole project:

  1. Verification is mostly a human with three to four hours. Automation covers the identity, registry and content-hash surfaces - 23 tests across three files, run headless by scripts/run-tests.bat - and nothing else.

The five editor listeners, the delete cascade, and every visual, gesture and editor-integration behaviour stay a 126-step manual in-editor checklist, self-estimated at 3-4 hours. That is a defensible scope choice (the checklist covers exactly what a compiler and a code read cannot: visuals, gestures, editor integration, emergent state), but it means regression detection is gated on someone actually walking it.

In practice, changes ship when they compile and pass review. 2. Editor-hook correctness is built on behavior, not contracts. See above. Four commits in one day (one batch and three verification rounds, one of which refuted the design outright) is the honest shape of this risk. 3. Ambiguity is silent. The unique-or-null policy protects data perfectly and tells the designer nothing. A duplicated outpost quietly stops syncing. 4. Clicks can block on disk. One-shot actions load synchronously by design, inside an open transaction. The definition itself is tiny; what a load can chain into (mirroring a building Blueprint's mesh parts, for instance) is not bounded by anything. 5. Two editions are maintained. The standalone plugin here and a project-module port elsewhere are separate trees with different paths and naming, so parity cannot be verified mechanically and every fix is paid for twice. The port does earn its keep as a second test bed (defects found there have been ported back), but the burden is real.
