System Wiring

Every other sheet on this site zooms in on one subsystem. This one pulls all the way back: a single interactive map of the whole plugin (the editor tool, the definition and settings assets, the four flat world actors, and the runtime module that ships in a cooked game), with the edges that connect them.

It's the Architecture sheet's mental model made clickable. Click any box to read its contract in the Inspect panel; pick a flow along the top to dim everything except that one story.

Launch the interactive map ↗

How To Read It

  • Four columns, left to right - the editor tool (OutpostBuilderEditor, never cooked), the data model (the two definition assets, the level registry, plus the two settings objects), the flat world actors (AOutpost and its siblings), and the runtime module (OutpostBuilder, what a packaged game actually gets).
    • The map covers the core placement path. The registry bake and the map-open repair, which live in the editor module, have no node on it yet.
    • Edges take the color of the column they leave.
  • Click a node - the Inspect panel shows that piece's contract and invariants, paraphrased from the code's own headers. Every box names a real, greppable symbol.
  • Pick a flow - six named stories (place an outpost, write-through, assign buildings, fork-on-stamp, runtime & cook, plus the overview) light up only the nodes and edges that carry them, so you can trace one path without the other five in the way.

The Four Columns

  • Editor tool - the UOutpostBuilderEdMode state machine at the center, its FOutpostBuilderToolkit panels, the read-model and palette model the extracted Slate widgets pull from, the draw layer (Outpost-aware wrappers over a separate, zero-Outpost-type primitive vocabulary), and the fork/stamp/volume helpers. All of it is editor-only and never reaches a cooked build.
  • Data model - UOutpostDefinition is the record graph a base is built from, not an actor hierarchy. It is the single source of truth while it belongs to one placement, which is the default.
    • Reuse it across placements and the actors carry what is actually placed, while the definition becomes their shared starting point.
    • Beside it sit the building definition, the per-level UOutpostLevelRegistry that bakes each placed outpost's default state so it can be read with its level streamed out, and the two settings objects (the scanned project asset and its config-backed UDeveloperSettings front end).
  • World actors - AOutpost, AOutpostPlot, AOutpostVolume, AOverheadCamera. Flat siblings that never attach to each other; they carry identity and state, and find one another by scanning for a matching identity - the per-instance id where there is one, the definition id otherwise - never by walking an attachment chain.
  • Runtime - what survives into a packaged game: the module that force-cooks the definitions with AlwaysCook, the BlueprintCallable stamp library, the event subsystem that bridges to gameplay, the templated id-lookup over the loaded world, and UOutpostRegistrySubsystem.
    • UOutpostRegistrySubsystem is the engine subsystem that answers what an outpost is and what it contains while its level is streamed out, which the templated lookup consults rather than being replaced by.
    • Two residents of this module never ship despite living here, both wrapped whole in WITH_EDITOR: the actor editing library backing the flat actors' editor-only hooks (record sync, cascade delete), and the preview-mesh helpers, which live in the runtime tree for the same reason - the editor's placement ghost needs them.

The Six Flows

  • Place an outpost - Create drops an AOutpost, auto-creates its definition, records the placement, and seeds the exclusion volume.
  • Write-through - moving a plot or the anchor writes the definition's records in the same transaction, while that definition belongs to this one placement. Share the definition across placements and the template write is refused: the actors carry what is actually placed. Ownership is resolved by id, not by a pointer.
  • Assign buildings - one palette model feeds every surface; assigning writes through the plot into the record and mirrors the building's mesh at once.
  • Fork-on-stamp - dragging a saved definition into the level mints a fresh copy so each stamped base owns its own layout, then spawns the base from records. On by default. Turn it off and every drop shares one template.
  • Runtime & cook - the runtime module resolves the same ids the editor wrote, spawns bases from code, and renders each plot's building through a runtime mesh component.
  • Overview - everything at once, for the shape of the whole system.
