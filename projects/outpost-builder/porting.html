Porting Into Your Own Project

Outpost Builder is deliberately a raw-actor tool. There is no component you bolt on, no interface your actors implement, and no UChildActorComponent anywhere (that one is banned outright; see Architecture).

The editor mode binds directly to the concrete runtime actor classes AOutpost and AOutpostPlot. That is the whole design: keep the runtime tiny, keep the shapes copy-pasteable, and let you graft the few functions your own actors need rather than adopt a framework.

This page is the porting contract: the minimal surface each actor carries, so you can drop it into a project that already has its own base/building actors.

It is deliberately short, because the runtime really is small (several thousand lines across the whole runtime module, the biggest chunks being the plot actor, the definition asset, and the actor-editing library that backs the hooks below).

Engine versions

The plugin is developed against UE 5.8 and kept UE 5.7-compatible as a standing rule: new code prefers APIs that exist in 5.7 or earlier, and a genuinely-required newer API gets exactly one UE_VERSION_OLDER_THAN(5, 8, 0) seam with a working 5.7 fallback, never guards scattered through call sites.

Two such seams exist today: OutpostEditorUtils::HideDetailsViewHeaders (on 5.7 a details view keeps its grey category header band, cosmetic only) and the module-startup OnPostEngineInit accessor. There's also one runtime-checked icon fallback (OutpostEditorUtils::GetBrushOrFallback) for a brush name newer style sets register.

The .uplugin declares every engine plugin the editor module links (including GeometryMode, which the volume-editing hand-off activates), so a stripped-down engine that disables it fails loudly at plugin load instead of silently at button-click.

The two decisions this design already made for you

  • Raw actors, not components or interfaces. The editor names AOutpost/AOutpostPlot directly (~250 references across the editor module). Porting therefore means one of two things:

    • Subclass AOutpost/AOutpostPlot in your project and add your own visuals/logic on top.
    • Copy the surface below onto your own AActor and repoint the editor module's type references at your class.

    There is intentionally no third "attach a component to any actor" path. That abstraction was considered and declined to keep the tool simple.

  • The data is already actor-agnostic. UOutpostDefinition stores:

    • Plot records as { FGuid PlotId, FTransform RelativeTransform, FPrimaryAssetId AssignedBuildingId, FGameplayTag PlotSizeTag, FGameplayTagContainer PlotTags } (PlotSizeTag is a gameplay tag under OutpostBuilder.PlotSize; PlotTags is a warn-only, project-owned tag set matched against a building's PlotTagQuery).
    • An outpost-level Overhead camera record, and a second, per-plot Overhead camera map keyed by the same PlotId (PlotCameras).

    All of it is stored relative to the anchor: World = RelativeTransform * AnchorTransform. Nothing in the record model knows or cares what class the anchor actor is. Copy the definition asset as-is.

Anchor actor: what to port from AOutpost

AOutpost is almost pure data: a definition id, a faction enum, and (editor-only) a preview mesh. The portable surface:

// Data (both UPROPERTY, EditAnywhere, Category = "Outpost")
FPrimaryAssetId OutpostDefinitionId;   // meta = (AllowedTypes = "OutpostDefinition")
EOutpostFaction Faction = EOutpostFaction::Neutral;

// Accessors the editor mode and the stamp library call
FPrimaryAssetId GetOutpostDefinitionId() const;
void            SetOutpostDefinitionId(FPrimaryAssetId NewId);
EOutpostFaction GetFaction() const;
void            SetFaction(EOutpostFaction NewFaction);   // Modify+Dirty (skipped if unchanged) - that's it

// The record basis: rotation + translation, UNIT scale. Records must never absorb anchor scale.
FTransform GetRecordBasisTransform() const { return FTransform(GetActorRotation(), GetActorLocation()); }

Faction has no visual effect. It is pure identity/eligibility, gating which buildings a plot may field via UOutpostBuildingDefinition::SupportedFactions/SupportsFaction(). There is nothing to resolve, cache, or re-apply on a timer or lifecycle hook: SetFaction is a plain data write, full stop.

If your port wants the same building-eligibility gate, implement that check on your own building type. If it doesn't, Faction can be ported as inert data or dropped entirely.

For full editor behaviour (not just placement), also port these hooks. On AOutpost itself each one is a single line, forwarding into OutpostBuilder::ActorEditing, a set of free functions in Core/OutpostActorEditingLibrary.h/.cpp where the actual logic lives. That split keeps AOutpost copy-pasteable while the logic can still reach the actor through its own public accessors.

The library is WITH_EDITOR-gated but sits in the runtime module on purpose: it's the actors' own editor-only logic, not editor tooling, and the runtime module can't link the editor module to reach it if it lived there. Port the header and source alongside the hooks below, or reimplement their guards yourself:

  • PostEditMove(bFinished) / PostEditChangeChainProperty(...) -> OutpostBuilder::ActorEditing::ReRelativizeOwnedRecords - a finished move (or a typed Details edit) re-relativizes every matching plot/camera record against the new anchor transform, so plots stay put in world space.
    • This also re-relativizes the definition's per-plot Overhead camera map (PlotCameras), the one record with no live actor to read a transform from, reconstructed instead from the definition's previously-recorded anchor transform.
    • Skipped when more than one anchor shares the definition id (ambiguous basis).
  • Destroyed() -> OutpostBuilder::ActorEditing::HandleOutpostDestroyedCascade - cascade delete: destroying the anchor also destroys every AOutpostPlot/AOverheadCamera/AOutpostVolume sharing its instance identity - definition id only for content that predates instance ids - in the same transaction (one undo restores all). The definition asset on disk is left untouched.

AOutpost has no OnConstruction, PostLoad, or PostEditUndo override. There is no faction tint to re-apply, so none is needed. If you only need placement and don't care about the anchor-move re-relativization or the cascade, you can skip the PostEditMove/PostEditChangeChainProperty/Destroyed() hooks (and the library behind them) too, and port just the data + accessors.

Plot actor: what to port from AOutpostPlot

The plot carries a little more, because it owns its own runtime visual (the building mesh that ships in packaged games):

// Data
FPrimaryAssetId OutpostDefinitionId;   // which anchor/definition it belongs to - VisibleAnywhere, never hand-edited (unlike the anchor's own EditAnywhere copy above - see AOutpost's snippet)
FGuid           PlotId;                // record identity - VisibleAnywhere, never hand-edited
FPrimaryAssetId AssignedBuildingId;    // meta = (AllowedTypes = "OutpostBuildingDefinition")
FGameplayTag    PlotSizeTag;           // size tag (gameplay tag under OutpostBuilder.PlotSize) - actor+record write-through pair, like the transform
FGameplayTagContainer PlotTags;        // warn-only placement-rule tags - actor+record write-through pair, like PlotSizeTag; GetPlotTags()/SetPlotTags() accessors
TObjectPtr<UStaticMeshComponent> BuildingMeshComponent;   // the single runtime visual (buildings are mesh-only)

// Resolve + apply (runs in editor AND packaged games; idempotent)
void RefreshBuildingPreview();    // AssignedBuildingId -> else the settings asset's EmptyPlotMesh -> else its DefaultPreviewMesh -> else cube
bool IsRecordOwnershipUnique() const;   // guards record write-backs against duplicated plots

PostRegisterAllComponents is not editor-only. It realizes the mesh on both spawn (game) and registration (editor), so port it regardless of whether you ship the editor tooling; in a game world it takes the async load path rather than the synchronous editor preview.

Plot WITH_EDITOR hooks worth porting for full editor behaviour: PostEditMove/PostEditChangeChainProperty (write this plot's relative transform back into the record, guarded by ownership uniqueness), PostEditUndo, and PostDuplicate/PostEditImport (reclaim the record this instance still uniquely owns, else mint a fresh PlotId, so a copy can't overwrite the original's record).

Like the anchor's hooks above, these are one-line forwards into OutpostBuilder::ActorEditing (SyncRecordTransform, SyncRecordPlotSize, SyncRecordPlotTags, HandleImportIdentityReset) in the same Core/OutpostActorEditingLibrary.h/.cpp. Port that file once and both actors' hooks are covered.

Keep it light

The runtime module ships in packaged games. The editor module does not. Keep the anchor and plot to data + one mesh component + the resolve helpers above and let all the tooling (placement, beams, HUD, camera pilot, prefab stamping) stay in the editor module where it already lives.

Core/OutpostActorEditingLibrary.h/.cpp is the one exception worth knowing about: it's WITH_EDITOR-gated editor-only code that still lives in the runtime module, because it's the actors' own logic rather than tooling. A cooked build strips it out like any other WITH_EDITOR block, same as it strips everything else this section is about.

UOutpostStampLibrary is the one runtime-callable entry point for spawning a full outpost from a definition at runtime. Port it if your game stamps bases at runtime, skip it if the builder is editor-only for you.

If you do lift the editor tooling too, there's one less thing to carry than you might expect. UOutpostBuilderEdMode is a UEdMode (on UBaseLegacyWidgetEdMode), discovered from its own CDO by UAssetEditorSubsystem::RegisterEditorModes.

There's no RegisterMode/UnregisterMode pair in the module startup to port, and no AddReferencedObjects either. The mode's strong references are plain UPROPERTY()s. What your module startup DOES still need is the command registration (FOutpostBuilderCommands) and whichever of the property/asset-registry watchers you want. See The UEdMode Deep Dive for the full lifecycle.

Cooking: the settings asset ships like the definitions

Every project-shared plugin tunable lives on ONE UOutpostBuilderSettingsAsset (a UPrimaryDataAsset in the runtime module) that a project authors once and points at from Project Settings > Plugins > "Outpost Builder" (UOutpostRuntimeSettings::SettingsAsset). The per-user debug-draw/editor-UI-style knobs live on a separate UOutpostBuilderUserSettings (editor module, Editor Preferences), none of which is runtime-relevant.

What lives on the asset and still needs to cook is the runtime section (DefaultPreviewMesh, EmptyPlotMesh, PlotSizeTagHalfSizeCm) plus the editor-only asset-creation/placement config. The latter never ships in a cooked build (WITH_EDITORONLY_DATA), so only the runtime section's soft mesh refs are what the cook story below is about. If you port the runtime surface, port the cook story with it:

  • The asset is AlwaysCook-registered exactly like the definitions. FOutpostBuilderModule::RegisterAssetScans registers a third primary-asset type ("OutpostBuilderSettings") alongside the outpost/building definition scans and gives all three the same EPrimaryAssetCookRule::AlwaysCook rule. Nothing else would make the cooker reach it: the only reference to the asset is an ini-hosted soft path (SettingsAsset in DefaultGame.ini), which is not a package-dependency edge the cooker follows.
  • Cooking the asset is what cooks its meshes. The soft mesh refs on it (DefaultPreviewMesh and EmptyPlotMesh, the fallback rungs of every plot's mesh ladder) are followed by the cooker OUT of the cooked asset, the same mechanism that pulls BuildingMesh out of a cooked building definition.
  • Host cook-critical meshes on the asset, not in an ini. A mesh referenced only from an ini (e.g. a UDeveloperSettings config soft path) is invisible to the cooker.
    • It gets silently never cooked, and every packaged-game fallback lands on the built-in cube with nothing logged. A mesh referenced from an always-cooked asset is not.
    • If your port re-hosts these settings, keep them on a cooked asset, not in config.

At runtime the asset resolves through UOutpostBuilderSettingsAsset::Get() (loaded-or-CDO, never a load on per-frame paths) with a one-shot pre-warm (PreWarm(), called from RegisterAssetScans at startup) that also roots the asset in cooked games so GC can't evict it. An unset pointer is a supported state: the class defaults apply.

What NOT to reach for

  • No UChildActorComponent, no actor-to-actor attachment. Plots are siblings of their anchor that share an OutpostDefinitionId, never children. To show another actor's visuals, render a UStaticMesh on a component your own actor owns (AOutpostPlot::BuildingMeshComponent) rather than instantiating or attaching it. See the "Never Child Actors or Attachment" pitfall in Extending.
  • No component or interface binding layer. If you find yourself wanting one, that's the abstraction this design deliberately left out. Reach for subclassing or the copy-the-surface approach above instead.
