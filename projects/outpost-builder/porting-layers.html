Porting, Step by Step

This page is meant to talk about getting the Outpost Builder into a project you already have, and how to set it up once it's there.

It's the practical companion to porting.html. That page is the contract: the minimal surface your own anchor and plot types have to carry, and the two decisions (raw actors, actor-agnostic records) the design already made for you. Read it first if you haven't.

This page covers the mechanics around that contract, which is where the files go, what the build needs, what your own module startup takes over, and the order to bring it all across if you'd rather not do it in one sitting.

Note: this page isn't in the Sheet Index and nothing on the site links to it. It's still built and published like every other sheet, so treat it as unlisted rather than private.

Two Ways In

There are two ways to get the tool into a project, and they're pretty different jobs.

As a plugin - you keep the modules as a plugin and consume them from your project. Nothing merges into your own modules. This is the cheap path, and it's the one the plugin ships expecting.

As source - you lift the module trees into modules you already own. More work up front, but the code ends up in your tree, under your naming and your build rules, with no plugin boundary in the way.

Route One takes a few minutes. Route Two is most of this page.

Route One: Keep It a Plugin

The clone, junction, build, and enable sequence lives on the front page already, check it out: index.html . Once "Outpost Builder" shows up in the Modes dropdown, there are two more things worth doing.

  • Author a UOutpostBuilderSettingsAsset somewhere under /Game. It's the single project-shared asset, so every tunable the whole team sees lives on it rather than in anyone's local config.
  • Point Project Settings -> Plugins -> Outpost Builder -> Settings Asset at it. That pointer is UOutpostRuntimeSettings::SettingsAsset.

An unset pointer is a supported state, so the mode works before you do either of those. The class defaults apply until you point it somewhere. The per-user knobs (nearly every color, size, and timing the mode draws with) live separately in Editor Preferences -> Outpost Builder, and those never land in source control.

That's the whole of Route One. Everything below is for the source lift.

Route Two: Lift the Source Into Your Own Modules

The tool is two module trees under OutpostBuilder/Source/. Nothing about either one requires being a plugin. They're ordinary Unreal modules, so they drop into modules you already own with a handful of adjustments.

Step 1: Copy the Two Trees

There are two, and the split matters more than anything else on this page.

  • OutpostBuilder/ - the runtime tree. Actors, the two definition assets, the per-level UOutpostLevelRegistry, the stamp library, the settings asset, and two subsystems: the world-scoped event one and UOutpostRegistrySubsystem, the engine subsystem a packaged game reads for unloaded levels. Core/OutpostInstanceMint and Core/OutpostRecordDerive live here too. This one ships in packaged games.
  • OutpostBuilderEditor/ - the editor tree. The mode, the toolkit, the widgets, the factories, and the utils. This one is never cooked.

Copy the runtime tree into a runtime module and the editor tree into an editor module. Keep the two folder names as they are, since the includes depend on them (Step 2). If a file name already exists in your target module, prefer a diff-merge over an overwrite so you don't roll back newer work of your own.

Everything editor-only in the runtime tree is already WITH_EDITOR-gated, so the runtime tree is safe to ship as-is.

Step 2: Put the Source Root on the Include Path

Both trees use a collapsed layout, so Public and Private are merged into the module root and every include is written from the Source root down.

#include "OutpostBuilder/Actors/Outpost.h"
#include "OutpostBuilderEditor/Mode/OutpostBuilderEdMode.h"

That means the directory holding both trees has to be on the include path. In the plugin it's one line in the runtime module's Build.cs, public so it propagates to the editor module:

PublicIncludePaths.Add(Path.GetFullPath(Path.Combine(ModuleDirectory, "..")));

If your own modules already put their Source root on the include path (most do), you should be able to drop the trees in and have the includes resolve with no change at all. If they don't, add the equivalent line rather than rewriting ~100 files of includes.

Step 3: Add the Build.cs Dependencies

The runtime module needs these:

PublicDependencyModuleNames.AddRange(new string[]
{
    "Core",
    "CoreUObject",
    "Engine",
    "DeveloperSettings",
    "GameplayTags"
});

GameplayTags is public rather than private on purpose. FGameplayTag and FGameplayTagQuery sit on public headers (plot-size tags and the buildings' tag queries), so a dependent module needs it too.

The editor module needs these:

PrivateDependencyModuleNames.AddRange(new string[]
{
    "Core", "CoreUObject", "Engine", "InputCore", "Slate", "SlateCore",
    "UnrealEd", "EditorFramework", "PropertyEditor",
    "AssetRegistry", "AssetTools", "ContentBrowser", "DeveloperSettings",
    "Settings", "EditorSettingsViewer", "LevelEditor", "ToolMenus",
    "RenderCore", "BSPUtils", "GeometryMode", "GameplayTags",
    "WidgetRegistration", "EditorWidgets", "Documentation",
    "OutpostBuilder"
});

A few of those are easy to miss, so they're worth calling out. Each one is needed by exactly one thing, which means leaving it out breaks exactly one thing and the rest of the module compiles fine.

  • Documentation - SDocumentationToolTip and IDocumentation, behind the two-tier tooltips. This is the classic miss.
  • WidgetRegistration - FToolkitBuilder and FToolkitBuilderArgs, the opt-in that makes the panels height-bounded.
  • EditorWidgets - SEnumComboBox, the identity header's Faction picker.
  • GeometryMode - FGeometryEditingModes::EM_Geometry, the Brush Editing mode id the Edit Volume excursion hands off to.
  • BSPUtils - FBSPOps::csgPrepMovingBrush, which preps the box brush for the default Outpost Volume that placement spawns. It sits next to GeometryMode in the list but isn't part of the excursion.
  • Settings and EditorSettingsViewer - only the tutorial capture command uses these. If you're not porting OutpostBuilderShotCommand.cpp, you can drop both.

The last entry, OutpostBuilder, is the runtime module. Replace it with whatever you named yours.

Step 4: Enable the Engine Plugins

One engine plugin has to be enabled in your .uproject. The .uplugin declares it today, so a source lift is exactly where it gets forgotten.

{ "Name": "GeometryMode", "Enabled": true }

Declaring them is what makes a stripped-down engine fail loudly at load instead of silently at button-click, so it's worth keeping the declaration rather than relying on the default engine config.

Step 5: Take Over the Module Startup Work

Losing the plugin means losing two module classes, so whatever they did has to move into module classes you own.

The editor listeners are the part most easily missed: FOutpostBuilderEditorModule defers past a null GEngine and then installs five of them (ActorAdded, GroupCascade, IdentitySync, InstanceHeal, RegistryBake), the last of which owns the package-saved, world-saved and map-opened hooks the registry depends on.

On the runtime side, FOutpostBuilderModule does one job: RegisterAssetScans(), covered in Step 6. It runs at startup if UAssetManager is already up, and defers to post-engine-init if it isn't. That fallback matters, since a runtime module at the PreDefault phase loads before UEngine::Init builds the asset manager.

On the editor side, FOutpostBuilderEditorModule does more:

  • FOutpostBuilderCommands::Register() on startup, Unregister() on shutdown. This is what surfaces the hotkeys in Editor Preferences -> Keyboard Shortcuts, and it has to happen before any mode instance exists so BindCommands always finds them.
  • A FEditorDelegates::BeginPIE hook calling UOutpostBuilderEdMode::CancelTransientSessionsForPIE(), so hitting Play cancels any in-flight placement or camera-pilot session up front instead of leaving a ghost dangling.
  • A FCoreUObjectDelegates::OnObjectPropertyChanged hook, which fans out three ways rather than one. An edit to the runtime settings or the settings asset re-runs ScanConfiguredDefinitionFolder(), sweeps RefreshBuildingPreview() over every loaded plot, and refreshes the toolkit. An edit to an outpost definition reaches the live mode. An edit to a building definition refreshes the palette and every plot preview.
  • Hosting for the volume-edit excursion. BeginEditVolumeExcursion(FPrimaryAssetId) lives on the module, the toolkit reaches it by name through FModuleManager::GetModuleChecked, and the module owns its teardown. This one genuinely has to be module-hosted, so porting the delegate hooks and stopping there leaves a link error waiting for you at Layer 19.
  • A UToolMenus::RegisterStartupCallback for the Content Browser context menu. UToolMenus may not be ready at module load, and this defers until it is (and fires immediately if it already is).
  • An asset-registry OnAssetRenamed() hook, so renaming a definition rebinds the actors placed from it. This one is deliberately module-lifetime rather than toolkit-lifetime, so a rename heals placed actors whether or not the mode happens to be active.
  • ScanConfiguredDefinitionFolder(), with the same asset-manager-may-not-be-ready fallback the runtime module uses. It's what makes definitions resolve when a project points its created-definition folder somewhere outside /Game.

One thing you don't have to port is the mode registration, which surprises people. UOutpostBuilderEdMode is a UEdMode, and UAssetEditorSubsystem discovers those itself by walking UEdMode CDOs. The id, name, icon, and visibility all live in the mode's constructor instead.

There's no RegisterMode/UnregisterMode pair to carry across, and FEditorModeRegistry isn't an option anyway since its factory contract hands back a TSharedRef<FEdMode>, which a UObject mode isn't. The asset factories need no registration either, since UE discovers UFactory subclasses on its own.

Step 6: Keep the Asset Scans

Four primary asset types have to be scanned and given an AlwaysCook rule: OutpostDefinition, OutpostBuildingDefinition, OutpostBuilderSettings, and OutpostLevelRegistry. The last one is the generated per-level registry, reached only by name lookup - without AlwaysCook it is silently absent from a packaged build and every unloaded-level query returns nothing with nothing logged.

The plugin does this itself in FOutpostBuilderModule::RegisterAssetScans, which pairs the scan and the cook rule per type so the two halves can't be forgotten independently. The engine enforces that ordering anyway, since SetPrimaryAssetTypeRules ensures the type was already scanned at least once. Carrying that function across as-is is the least work and the least risk.

IMPORTANT: AlwaysCook is not optional. Nothing else reaches these packages. Outpost and building definitions are referenced only through FPrimaryAssetId, which is a name pair rather than a package reference the cooker follows, and the settings asset is referenced only from an ini-hosted soft path.

Drop the rule and packaged builds silently ship without them, with nothing logged. Every mesh fallback then lands on the built-in cube and you get no clue why.

If you'd rather drive it from config than from code, the equivalent goes in Config/DefaultGame.ini, merged into an existing [/Script/Engine.AssetManagerSettings] section if you have one.

Note the block below predates the registry: add a fourth +PrimaryAssetTypesToScan line for OutpostLevelRegistry on the same pattern, or the config route silently drops exactly the type whose absence is silent. Swap /Script/OutpostBuilder for whatever your runtime module is called.

[/Script/Engine.AssetManagerSettings]
+PrimaryAssetTypesToScan=(PrimaryAssetType="OutpostDefinition",AssetBaseClass=/Script/OutpostBuilder.OutpostDefinition,bHasBlueprintClasses=False,bIsEditorOnly=False,Directories=((Path="/Game")),Rules=(CookRule=AlwaysCook))
+PrimaryAssetTypesToScan=(PrimaryAssetType="OutpostBuildingDefinition",AssetBaseClass=/Script/OutpostBuilder.OutpostBuildingDefinition,bHasBlueprintClasses=False,bIsEditorOnly=False,Directories=((Path="/Game")),Rules=(CookRule=AlwaysCook))
+PrimaryAssetTypesToScan=(PrimaryAssetType="OutpostBuilderSettings",AssetBaseClass=/Script/OutpostBuilder.OutpostBuilderSettingsAsset,bHasBlueprintClasses=False,bIsEditorOnly=False,Directories=((Path="/Game")),Rules=(CookRule=AlwaysCook))

Note: bHasBlueprintClasses=False is deliberate on all three, and it already covers Blueprint subclasses as well as native ones. Flipping it to true is a regression rather than a fix. That reasoning doesn't live in the source (comments there stay short on purpose), so this page is the place to come back to if you need the why.

If you add a definition type of your own later, here's the recipe, and it has two halves. Declare PrimaryAssetTypeName plus a GetPrimaryAssetId() override on the type, then add one RegisterOutpostAssetType<T>(AssetManager); line. That covers the mount-point scan.

The editor-side sibling is FOutpostBuilderEditorModule::ScanConfiguredDefinitionFolder, which hand-lists the types it re-scans, so a new type that should also resolve under a project's out-of-/Game created-definition folder joins that list too.

Step 7: Author a Settings Asset

Same as Route One. Create a UOutpostBuilderSettingsAsset under /Game, then point Project Settings -> Plugins -> Outpost Builder -> Settings Asset at it.

Worth knowing while you're in there: host any cook-critical mesh on that asset rather than in an ini. A mesh referenced only from a config soft path is invisible to the cooker, so it silently never cooks.

A mesh referenced from an always-cooked asset is followed out of it, which is the same mechanism that pulls a building's mesh out of a cooked building definition.

Step 8: Build and Check

Build the editor target and open the editor. You should be able to find "Outpost Builder" in the Modes dropdown.

The fastest end-to-end check is the loop from the front page: place an outpost (a definition asset is created for you), add a plot inside it, assign a building, and save.

If plot transforms and assignments write through to the definition on their own, Steps 5 and 6 both landed.

Bringing It Over a Piece at a Time

A source lift in one sitting is a big diff to read. If you'd rather bring it across in slices and try each one in the editor before moving on, the order below is the one we'd suggest. Each layer builds on the ones before it and leaves you with something you can actually use.

This is a reading order, not a set of commits. Nothing tags these layers in the repo, so treat the boundaries as a sensible place to stop rather than a line the code enforces.

  • Layer 1 - the record model. Core/OutpostPlotSize.* and a minimal DataAssets/OutpostDefinition.* carrying plot records. After this you can author a definition asset by hand.
  • Layer 2 - the actors. Bare Actors/Outpost.* and Actors/OutpostPlot.*, data and accessors only. Drop them into a level by hand.
  • Layer 3 - stamping. Core/OutpostStampLibrary.* and Settings/OutpostRuntimeSettings.*. Spawn a recorded base into a world from code.
  • Layer 4 - the mode shell. A skeleton Mode/OutpostBuilderEdMode.* and an empty Toolkit/OutpostBuilderToolkit.*. "Outpost Builder" appears in the Modes dropdown.
  • Layer 5 - outpost placement. The click-place machine, Settings/OutpostBuilderSettingsAsset.*, the editor's Settings/OutpostBuilderUserSettings.*, Mode/OutpostDrawPrimitives.* (a generic draw vocabulary - segments, rings, pulsed beams, screen text - with no Outpost types in it), Mode/OutpostBuilderDraw.* (the Outpost-specific wrappers built on top of it), and Toolkit/OutpostBuilderCommands.*.
    • Click-place an outpost and get its definition asset created for you. The mint on that path is a plain NewObject on the mode.
    • Factories/OutpostDefinitionFactory.* is a separate thing worth taking at the same time, since it's what puts the type in the Content Browser's New Asset menu.
  • Layer 6 - plot placement. The plot ghost and its validity check, Ctrl-remove, and Del. Click-add plots inside an outpost.
  • Layer 7 - write-through editing. The PostEditMove, PostEditChangeChainProperty, and Destroyed hooks on both actors, plus Core/OutpostActorEditingLibrary.*, the free-function library those hooks forward into.
    • The actors themselves stay one-line forwards, and the actual logic lives in the library instead - WITH_EDITOR-gated, but in the runtime module rather than the editor module, since it's the actors' own editor-only logic and the runtime module can't link the editor module to reach it.
    • Move or edit an actor and the definition follows.
    • Deleting an anchor cascades to every family actor sharing its INSTANCE id, with the definition id only as the legacy fallback for content that predates instance ids, and the delete also retires the outpost's registry entry inside the same transaction.
  • Layer 8 - preview meshes. Core/OutpostPreviewMeshUtils.* and the plot's BuildingMeshComponent. Plots resolve a real mesh, and the ghost gains its mesh parts.
  • Layer 9 - viewport chrome. Widgets/SOutpostBuildModeBanner.*, Widgets/SOutpostViewportOverlay.*, and the outpost name labels. See mode state without looking at the panel.
  • Layer 10 - toolkit panels. Widgets/SOutpostIdentityHeader.*, Widgets/SOutpostPlotsSection.*, and the editing bar, which is where Save actually lives. The minimal placement tool is complete here. Widgets/SOutpostSaveFooter.* comes along for completeness, but nothing in the plugin mounts it, so don't go hunting for the call site.
  • Layer 11 - buildings data. DataAssets/OutpostBuildingDefinition.*, Factories/OutpostBuildingDefinitionFactory.*, and the plot's AssignedBuildingId. Assign buildings from the Details panel.
  • Layer 12 - the building palette. Widgets/OutpostPaletteModel.*, Widgets/SOutpostBuildingPalette.*, and Widgets/SOutpostPaletteTile.*. Pick buildings from the palette, with 1-9 and 0 as hotkeys.
  • Layer 13 - the assign row and the Selected Building panel. Widgets/SOutpostAssignRow.* and Widgets/SOutpostSelectedBuildingPanel.*. Edit the hot building inline and assign it to a selected plot.
  • Layer 14 - the in-viewport command grid. Widgets/SOutpostBuildingCommandGrid.*. The same tiles and hotkeys without leaving the viewport.
  • Layer 15 - organizing the palette. Pinning, Widgets/SOutpostPaletteCategoryTabRow.*, Widgets/SOutpostPaletteFilterRow.*, and Randomize Plots on J.
  • Layer 16 - the Overhead camera. Actors/OverheadCamera.* plus the camera records on the definition. Frame and save a per-outpost camera on O.
  • Layer 17 - the Overview panel. Widgets/SOutpostsOverviewPanel.*, Widgets/SOutpostBuildingsBrowser.*, and Widgets/SOutpostTabBar.h. The Outposts and Buildings tabs: list, place, restore, and locate.
  • Layer 18 - ownership beams. The beam draws in Mode/OutpostBuilderDraw.*, riding OutpostDrawPrimitives::DrawPulsedBeam from Layer 5 underneath. Animated plot-ownership beams while you're editing.
  • Layer 19 - volumes and the volume-edit excursion. Actors/OutpostVolume.* and Mode/OutpostBuilderVolumeExcursion.*. Exclusion blocking, the bounds rule, and Edit Volume on B.
  • Layer 20 - three-state placement validity. The ghost reads valid, warn, or blocked, told apart by fill treatment rather than hue alone.
  • Layer 21 - the placement aids. Live distance, footprint, and neighbour-gap numbers beside the ghost, plus the alignment guide.
  • Layer 22 - the eyedropper. Press E over a plot to load its building into Selected Building.
  • Layer 23 - Content Browser drop, the scoped fade, and two-tier tooltips. Utils/OutpostBuilderTooltips.*. Drag buildings onto the palette, let the edited outpost stand out, and get the long version of a gated control's tooltip on Ctrl+Alt.
  • Layer 24 - double-click in and out of editing. Double-click an outpost to start editing it, and double-click the one you're editing to leave.

The Stop Points

Three of those are natural places to stop for a while, and everything after each one stacks on top rather than weaving through.

Layer 10 is the early stop. Outpost and plot placement, write-through editing, previews, viewport chrome, and a working side panel, with none of the buildings, camera, volume, or palette weight. If that's all your team needs for now, stop there and come back later.

Layer 19 is the full editor tool. Everything the mode does for authoring, with the whole v1.30 UX pass still ahead of you.

Layers 1-24 stop at the v1.30 UX pass. The per-instance identity and baked-registry system sits on top of Layer 24 and is not decomposed into layers here.

It covers instance ids on the family plus the mint, the level registry asset and its engine subsystem, the bake and its save/map-open listeners, and retire-on-delete with restore-from-baked and the map-open repair. Instance Identity is the guide to that half.

Layers 20 through 24 are polish and correctness on a tool that already works, so stopping short of them costs you convenience rather than capability.

Layers Grow Files

Worth setting expectations on: layers add to files as well as adding files, so a file you copied at Layer 8 may well get extended at Layer 19.

The heaviest growers are the ones you'd expect. OutpostDefinition grows from Layer 1 all the way through Layer 19. So do the two actors and the actor-editing library behind them, the stamp library, and the whole mode, toolkit, draw, and settings family.

The practical version of that: don't treat a file as finished just because the layer that introduced it is done. If you're diffing your copy against the plugin to check, diff against the current tree rather than against the layer you took it from.

Dependencies You Can Defer

If you're porting a layer at a time, most of Step 3 can wait. At time of writing, this is roughly where each piece starts being needed.

  • Runtime Build.cs - the base list (Core, CoreUObject, Engine, DeveloperSettings, GameplayTags) from Layer 1.
  • Editor Build.cs - bring the full Step 3 list at Layer 4, except BSPUtils and GeometryMode, which nothing needs until Layer 19.
  • Documentation - only from Layer 23, for the two-tier tooltips. It's the one dependency whose absence breaks nothing else, which is exactly why it's easy to miss.
  • Settings and EditorSettingsViewer - only if you port the tutorial capture command. Skip both otherwise.
  • Asset scans - the definition and settings types from Layer 5, the building definition type from Layer 11.
  • Module startup work (Step 5) - from Layer 4.

A Few Heads-Ups for a Mid-Stack Stop

These are all rough edges of stopping partway rather than defects, and each one heals on its own by the layer noted. Since the layers aren't commits, treat the middle two as what you should expect at that point rather than as states anyone has sat in and observed.

  • At Layer 1, hand-authoring two or more plots in the Details panel needs a fresh GUID typed per plot. Array entries default to the zero GUID, and duplicates trip the coherence check on the next load.
  • Between Layers 6 and 9, the interim panel shows the outpost placement hint during plot placement too. Layer 10's real panel replaces it.
  • At Layer 10, a few tooltips promise things that haven't landed yet, like faction gating of buildings and the outposts overview list. They stop lying once the layers behind them arrive.
  • Before Layer 19, the territory border and the exclusion check aren't there, so nothing stops two outposts overlapping. That's worth knowing if designers start authoring real content at an earlier stop.
