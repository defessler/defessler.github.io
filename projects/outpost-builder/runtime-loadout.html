Per-Plot Building Rendering (formerly "Runtime Faction Loadout")

This page used to document UOutpostLoadoutLibrary, a runtime-gameplay system for spawning a faction-specific building actor on each plot and swapping it on a faction change. That library is gone: buildings are mesh-only now, and a plot renders its own building directly.

There's no separate spawned actor left to spawn, swap, or clean up. This page describes the model that replaces it.

What's Gone

UOutpostLoadoutLibrary (ApplyFactionLoadout, RandomizeLoadout) and the whole spawn/destroy/re-swap model it existed for are gone. So is the idea that assigning a faction changes WHICH building a plot shows. UOutpostBuildingDefinition::FactionActorClasses/GetActorClassForFaction (the per-faction actor-class override map this library read from) are gone too.

The header now carries:

  • DisplayName
  • BuildingActorClass - the class a project's own gameplay spawns for this building, and the EDITOR preview source when it's set, covered in "Editor Preview" below. GAME worlds only ever spawn the real actor from it, never render from it directly.
  • BuildingMesh
  • PlotSizeQuery - a gameplay-tag query for which plots the building fits.
  • PlotTagQuery - warn-only, over the plot's general tags.
  • SupportedFactions
  • BuildingCategory - palette grouping only.

SupportedFactions does NOT revive faction-swapping: it decides whether a building may be ASSIGNED to an outpost's plot at author time, never which building a plot shows at runtime.

Game code that called ApplyFactionLoadout/RandomizeLoadout will no longer compile. There's no drop-in replacement function, because the model it served (spawn a separate actor, tag it, destroy-and-respawn on every faction change) doesn't exist anymore.

The New Model: A Plot Picks Its Own Building

This section describes the mesh ladder that resolves BuildingMeshComponent: the plot's one RUNTIME visual, and the ONLY thing a GAME world (packaged game or PIE) ever shows.

There is an earlier, EDITOR-world-only rung in front of it (see "Editor Preview: the Actor-Template Mirror" below), but every plot still falls through to this same ladder whenever that earlier rung doesn't apply, and it is unconditionally the whole story in a game world.

Every AOutpostPlot resolves which building to render, in this priority order:

  1. AssignedBuildingId, if it's a valid FPrimaryAssetId: the fixed per-plot assignment the toolkit's Building Picker/Assign row and the Editing panel's palette (the Select Plot Contents section) hot-slot one-action placement write.

  2. Otherwise (the plot is unassigned), the plugin-wide empty-plot mesh: UOutpostBuilderSettingsAsset::EmptyPlotMesh, ONE field on the project's settings asset, read through the never-loading UOutpostBuilderSettingsAsset::Get() resolution.

    • It is what EVERY unassigned plot of EVERY outpost renders, in the editor AND in packaged games alike.
    • It carries no transform of its own: a plot renders the mesh at the plot's own transform. To give a plot a specific building, assign one.

  3. Otherwise, when no mesh resolves at all (the plot is unassigned and the project authored no EmptyPlotMesh; or it is assigned and that definition has no BuildingMesh set / fails to load), the fallback chain: UOutpostBuilderSettingsAsset::DefaultPreviewMesh if a project has one configured (a settings-asset field too), else the plugin's built-in cube (cached at construction as EmptyPlotFallbackMesh).

Rung 3 is not decoration. A plot is never invisible is a load-bearing invariant, not a cosmetic one: editor tooling traces a plot's mesh to hit it, so an invisible plot would be both unselectable and un-removable. Leaving EmptyPlotMesh unset is fine; the chain simply ends at the cube.

This selection reuses the building-mesh resolution off UOutpostBuildingDefinition. The mesh is hosted on a runtime component the plot owns directly, so it renders in packaged games as well as in the editor: exactly one representation, on one actor, in every GAME world.

There's no separate spawned building actor to keep in sync with it. (In an EDITOR world that "one representation" can become several transient PARTS instead of a single mesh. It's still one actor, still nothing spawned. See "Editor Preview: the Actor-Template Mirror" below.)

The runtime component is the plot's UPROPERTY UStaticMeshComponent, BuildingMeshComponent. Realization runs from PostRegisterAllComponents (which fires in both the editor and packaged games, and is re-entrancy-guarded via bIsRealizingBuilding), and it splits by world type:

  • An editor world calls RefreshBuildingPreview(): idempotent, synchronous, and also called from the editor-only OnConstruction, which early-returns in a game world so the async path below owns realization there.

  • A game world (packaged game + PIE) calls BeginAsyncBuildingRefresh() instead. It shows the built-in cube placeholder only if the component has no mesh yet (a mesh that serialized or streamed in with the cell stays visible, avoiding a cube flicker), then async-loads the real mesh and swaps it in on completion.

    • It forks the same way RefreshBuildingPreview() does: an assigned plot chains the building definition → BuildingMesh (OnBuildingDefinitionLoaded → OnBuildingMeshLoaded). The mesh path lives one soft-ref indirection inside the definition, which is exactly why it can't be resolved without a load first.
    • An unassigned one (BeginAsyncEmptyPlotMeshLoad → OnBuildingMeshLoaded) is shorter: EmptyPlotMesh is a direct soft ref on the already-resident settings asset, so there is no definition hop to chain through.

These are two code paths resolving the same question, so the empty-plot choice is funnelled through one shared settings-asset field rather than being re-derived at each call site.

Both paths read the same UOutpostBuilderSettingsAsset::EmptyPlotMesh (the synchronous path via ResolveEmptyPlotMesh()). If the two paths could pick independently, the editor and the packaged game would be free to disagree about what an empty plot looks like.

The split exists because PostRegisterAllComponents runs on the game thread inside time-sliced AddToWorld while (World Partition) cells stream in, where a synchronous load would hitch. In the editor the asset registry is resident and there's no frame budget, so the preview stays synchronous and immediate.

Both paths resolve the mesh only. There is no faction-derived tint to apply on either one (see "Faction No Longer Affects Rendering" below).

Editor Preview: the Actor-Template Mirror

Everything above is the mesh ladder, and it is the ONLY thing that ever renders in a game world. It is still the editor's fallback.

But in an EDITOR world, before any of that runs, an assigned plot whose building has a BuildingActorClass set gets one earlier chance to preview that ACTOR instead of BuildingMesh.

AOutpostPlot::RefreshBuildingPreview() calls OutpostBuilder::ActorEditing::RebuildMirroredBuildingParts(), which loads the class (synchronous: this is a one-shot editor path, never a per-frame one) and mirrors its template's static-mesh parts (the native CDO's UStaticMeshComponents plus every Blueprint class's SCS nodes, via OutpostPreviewMeshUtils::CollectMeshParts()) into plain, transient UStaticMeshComponents owned directly by the plot actor (MirroredBuildingParts, WITH_EDITORONLY_DATA).

Each mirrored part carries the template's own authored per-slot material overrides only (not the ghost's translucent material: that repaint is the placement ghost's job, covered in edmode.html). No faction tint is layered on top (see "Faction No Longer Affects Rendering" below).

Never a child actor and never a spawned instance: mirroring templates into plain components this actor owns is the hard-law-compliant pattern, the same one edmode.html's placement ghost uses via the identical CollectMeshParts() collector.

Because both sides read the same collector off the same class, ghost and mirrored plot render the same template by construction.

While MirroredBuildingParts is non-empty, BuildingMeshComponent is set to carry no mesh: the parts ARE the visual (and, being ordinary collidable components, the trace target editor selection/click-picking hits). The mirror only ever REPLACES what BuildingMeshComponent would have shown; it never renders alongside it.

This rung is skipped (and the ladder above runs unchanged) whenever RebuildMirroredBuildingParts() returns false: the plot is unassigned, the assigned building's BuildingActorClass is unset, the class fails to load, or the class contributes no static-mesh parts at all (an Actor with only non-mesh components, say).

"A plot is never invisible" still holds in every one of those cases, because the fallback is the same ladder that already guaranteed it.

Game worlds never mirror, on purpose. RefreshBuildingPreview()'s actor-template branch is gated on the world NOT being a game world (!PlotWorld->IsGameWorld()). BeginAsyncBuildingRefresh(), the async path PostRegisterAllComponents uses in a packaged game or PIE, never calls it at all.

Gameplay is expected to spawn the real BuildingActorClass actor itself when it wants one. Mirroring its template into the plot as well would render it twice.

Faction No Longer Affects Rendering

Faction is not a rendering input. None of AOutpostPlot's realize paths (RefreshBuildingPreview(), BeginAsyncBuildingRefresh(), RebuildMirroredBuildingParts()) apply any color to what they render, and the plugin uses no Custom Primitive Data anywhere. (Porting note: if your project drove a plot tint off CPD float4 index 0, that contract is gone. Nothing writes it now, so drop that node.)

Faction still matters upstream of all of this, just not as a rendering input: UOutpostBuildingDefinition::SupportsFaction() decides whether a building may be ASSIGNED to a plot in the first place (a Neutral outpost accepts everything; an empty SupportedFactions list is a wildcard).

Once a building IS assigned, what a plot renders (mesh or mirrored actor-template parts) is governed entirely by the ladder and the mirror described above, with no faction input anywhere in either path. See faction-visuals.html for the full model of what faction still does (identity and eligibility gating).

What This Trades Away

The old RandomizeLoadout(Outpost, Seed) was an explicit, stateless function game code called on demand with a caller-supplied seed, returning a map a second call (ApplyFactionLoadout) then used to spawn actors.

That gave two things the current model doesn't: an explicitly re-rollable pick (call it again with a new seed, get a new pick), and a documented multiplayer story (every peer replicates (FactionId, Seed) and computes the same result locally).

The current model has no automatic picking at all. An unassigned plot doesn't choose a building. It shows the authored empty-plot mesh. So there is no runtime randomness left in plot rendering: nothing to re-roll, nothing to replicate, and no seed-agreement problem across peers.

What the mesh ladder resolves is a pure function of authored data (AssignedBuildingId, or the settings asset's EmptyPlotMesh). World type selects between that ladder and the editor-only actor-template mirror described below, but neither side injects randomness.

The trade is variety-for-free. If a project wants a field of visually varied unassigned plots, that variety must now be authored: assign buildings to the plots you want varied.

The Editing panel's Randomize Plots action does exactly that in one undoable transaction: it is an explicit designer re-roll that WRITES AssignedBuildingId on each SELECTED plot (actor and definition record; it acts on the plots you select, disabled with nothing selected), so its results are authored data, not a runtime fallback.

It is the only randomization left in the plugin.
