The routing call

  1. The first output line is the routing call, and nothing goes above it.
  2. The format is Routing call: <inline|fan-out> — <reason, one clause>.
  3. Obvious routes still get the line.
  4. Leading with the deliverable and explaining the route afterwards does not count.
  5. Terseness is not an exemption, since one line is the terse form.
  6. The rule: plan with the strong model, implement with the cheaper model, escalate on demonstrated failure.
  7. Never escalate on a hunch.
  8. Never escalate above your seat unasked.
  9. Invoke with /smartplan <task> on Claude Code or Copilot CLI.
  10. Route the task yourself, and never ask the user to invoke anything.

Pick the route

  1. The first matching row of the route table wins.
  2. Work that exceeds one context window fans out.
  3. Four or more independent units with disjoint FILES fan out when finishing sooner beats finishing cheaper.
  4. The wall-clock row never fires on Copilot.
  5. Inline work that already failed twice on the same signature fans out.
  6. A risky merge (C++ UB, concurrency, templates, security) runs inline plus an independent verify.
  7. The verify floor holds at every size.
  8. Everything else runs inline, because one strong context out-runs N cold cheaper ones.
  9. Count units, not tokens.
  10. A 1M window holds large work without bounding it, so "fits in one context" is no longer the size test.
  11. N files taking the same edit is one leaf.
  12. N files taking different edits is N leaves.
  13. Firing the wall-clock row trades tokens for wall-clock knowingly.
  14. Fan-out costs 1.5 to 2.9x an inline pass at equal quality.
  15. That cost holds at every leaf count and size measured, so width and size never amortize it.
  16. Fire fan-out only when you mean to buy something with that cost, and say what.
  17. A fan-out routing call also names what it bought.
  18. After the call, start. No deliberation essay.
  19. An unstated call defaults to inline, and that silence is the miss.
  20. At 4 or more independent units, name the count and why inline still wins.

Inline route

  1. Batch independent reads into one turn and independent writes into one turn.
  2. Never re-read a file already in context.
  3. Hold the mode's output ceiling.
  4. Output bills about 5x input.
  5. The verify floor is the strongest available oracle, not merely a fresh one.
  6. Oracle tier 1 is executable: compiler, assertion, or replayed real input.
  7. Oracle tier 2 is a fresh-context model.
  8. Oracle tier 3 is a same-context model.
  9. A cold model shares the writer's training and blind spots. A compiler does not.
  10. Code-emitting work has tier 1 by definition, so nothing below it counts.
  11. Before a green check counts, say what would turn it red.
  12. If that answer does not name what you just changed, it is not verification.
  13. Below Strong, escalate the verify one tier above your seat when the work has no executable oracle.
  14. Below Strong, escalate the verify when the change crosses a second caller.
  15. Below Strong, escalate the verify on a never-Cheap class: concurrency, UB, templates, security.
  16. Those signals are countable, never a hunch.
  17. Escalating emits an artifact, never an intention.
  18. The artifact is the missing check, or the verify brief written out in full.
  19. "Should be verified", "the next step is a test", and handing the run to the user are one miss wearing three faces.
  20. The pre-flight lives in routing.md § Seat-aware pre-flight.

Seat ceiling

  1. Your seat is the model this session runs as, named by the system prompt or /model.
  2. If you cannot name the seat, treat it as Mid.
  3. Nothing dispatches at a tier above your seat until the user says yes.
  4. That covers an escalated verify, a fail-twice target, and an Opus or Fable planner.
  5. No initial seat pick prices above the incumbent at all.
  6. Pick the cheapest adequate row, with a named gate for every climb.
  7. Write the artifact first, then ask in one line.
  8. The one line names what it is for, which model, and that the brief is already written.
  9. Dispatch on the yes.
  10. One yes covers that tier for the rest of the session.
  11. At or below the seat needs no ask.
  12. The ask names a spend, so it is not the question-stall the spiral guard bans.
  13. A Cheap seat never asks.
  14. Nothing leaves a Cheap seat priced above its own model.
  15. A Cheap seat writes the artifact, offers the session model the work would suit, and carries on.
  16. On Copilot, every subagent runs GPT-6 Luna.
  17. On Copilot, a pricier session orchestrates and verifies Luna leaves (copilot.md § Luna ceiling).

Offered, never required

  1. Every tier named in the skill is advice.
  2. A no, or a model the plan does not serve, never stops the work.
  3. The work then runs on the strongest model on offer at or below the seat.
  4. Oracle first, and a fresh context for any verify.
  5. Name the gap at the gate and in the verdict.
  6. Judgment that reader cannot settle returns UNKNOWN.

Spiral guard

  1. Two failed self-repairs against the same failing signature means STOP.
  2. Dispatch one fresh-context diagnosis instead of a third blind attempt.
  3. The diagnosis runs Mid where on offer, or Fable by ask on a never-Cheap row.
  4. The diagnosis carries the ESCALATION REPORT.
  5. The report holds the task, the tier history (each attempt, its verdict, a one-line why), evidence, hypothesis, and what the receiver should do differently.
  6. Evidence is pasted byte-verbatim, never reworded or split up.
  7. The report shape lives in flow.md, which the inline route never loads, so it is named in SKILL.md.
  8. Write the report out in full. Referring to it is not carrying it.
  9. Brief the diagnosis in gated phases, each written into its report before the next starts.
  10. The phases are reproduce, narrow to the smallest input, state one falsifiable hypothesis, prove it with the oracle.
  11. No fix before the proof.
  12. Do not keep debugging in the context that failed twice.
  13. Do not turn back to the user with questions instead. That is the same stall as a third guess.
  14. A Cheap seat runs the diagnosis at its own tier.
  15. A user saying "try again" does not reset the count.

False-success guard

  1. The spiral guard needs a failing signature, so all-green attempts never trip it.
  2. A repeat report of a symptom you claimed fixed is a strike.
  3. The next action is not a third fix. It is proving your observable measures what it describes.

Land the check, not a note

  1. A fix whose only durable trace is a note has not landed.
  2. Leave the executable oracle in the repo: a compile step, an assertion, a fixture.
  3. Compaction re-injects skill bodies, not the references you read.
  4. Mid-run, re-read flow.md, artifacts.md and run-state.md before the next dispatch.

Cost mode

  1. Honor {{MODE}}.
  2. The default is max-quality, and max-savings on Copilot, which meters credits per token.
  3. Copilot never trades tokens for wall-clock, at any mode.
  4. On an explicit budget ask or stated budget pressure, bias inline choices toward cost.
  5. On Copilot, print the budget preflight first.

  2. Never dispatch a tiered subagent, compile a brief, or fan out at all without that file loaded.
  3. The human plan-review gate and the mode-invariant floors live in flow.md.
  4. A denied read is a STOP, never an obstacle to route around.
  5. With smartflow off, there is no fan-out.
  6. A lone verify dispatch is not a fan-out.
  7. The inline-plus-verify row and an escalated seat-aware verify are inline routes.
  8. For those, send the smartplan-verifier seat at the named tier within the seat ceiling and carry on.
  9. Your harness reference owns the lever.
  10. The fan-out checklist has 6 steps, worked in order.

  15. Step 5: every result independently verified, never in the executor's own context.
  16. Step 6: cross-leaf seams integrated and confidence notes written.
  17. Steps 3 and 5 are floors. Skipping either is a worse process, not a shortcut.

Core policy

  1. The strong model plans. The cheaper model does the mechanical fan-out.
  2. Escalate only on real failure.
  3. A human sits at the plan boundary.
  4. flow.md loads from SKILL.md's fan-out gate. Never fan out without it.
  5. Independence is tested, not assumed.
  6. Fan out only on independent, separately verifiable units.
  7. Anthropic's C compiler post is the warning: "compiling the Linux kernel is one giant task", with a 148 to 289% loss.
  8. Coordinate through durable artifacts (a task-lock file, contracts.md, run-state.md), never agent messaging.
  9. Orchestrate the flow yourself. Load the references and attach the smartexec payload at the step that needs them.
  10. Never ask the user to invoke anything.

Step 1: plan

  1. Plan on the planner seat.
  2. Ask about shape-changing ambiguity before decomposing.
  3. Ask one question at a time, with a recommended answer.
  4. Record the answers in the persisted plan. Skip the questions if the task is unambiguous.
  5. On a multi-subsystem plan with smartdiagram in the catalog, offer a wiring diagram in one line. Invoke it only on an explicit yes.
  6. Ownership domains suggest leaf boundaries.
  7. Decompose for maximum parallelism with disjoint FILES, and serialize true dependencies.
  8. The pair test asks three questions: same file, needs the other's output, renames a symbol the other reads.
  9. Any yes serializes or merges the pair.
  10. Run the pair test before sizing the wave.
  11. A wave is 3 to 5 concurrent leaves. More than 5 to 8 needs justification.
  12. A hotspot file serializes its leaves.
  13. The swarm rebuild cut conflicts from 70k to under 1k at about 8x the cost.
  14. Freeze shared outputs in contracts.md before fan-out, and have briefs cite it.
  15. When class-to-tier is unclear, read routing.md.

Step 2: gate

  1. Present the plan for human review and persist it.
  2. Quote the go-signal verbatim into each brief's AUTHORIZATION.
  3. Plan approval differs from execution authorization.
  4. The plan names every seat above the session's own (SKILL.md Seat ceiling).
  5. The starting request is neither approval nor authorization ("get them done", "wall clock matters").
  6. The approval is also the user request that the Opus 5 don't-dispatch injection requires (claude-code.md).
  7. On a material mid-flight change, the gate re-arms for the delta. Re-gate the changed slice.
  8. Dynamic workflows are out of scope for gated work: no mid-run user input beyond permission prompts.
  9. The launch prompt is skipped under bypass, claude -p, the Agent SDK, and ultracode, and shown once ever in auto mode.
  10. Agents inherit the permission mode. A definition's permissionMode counts only from default, dontAsk, or plan.
  11. If you launch a workflow anyway, the gate moves to the launch boundary. Approve before start.

Step 3: dispatch

  1. Dispatch in parallel through the harness lever (§A or §B).
  2. A dispatch is a subagent with its own model, never in-context work.
  3. The cost ceiling (routing.md) holds: the initial pick is never above the incumbent, and every climb is a named gate.
  4. Fire all ready disjoint-FILES leaves concurrently.
  5. Ready means every blocked-by leaf has passed. Dispatch at that pass, within the wave cap.
  6. A cache entry becomes readable once the first response streams.
  7. To stagger: dispatch one leaf, await its first output, then fire the rest (0.1x read vs 1.25x cold write).
  8. Stagger only when (N-1) x shared prefix x cold-write premium exceeds orchestrator context x cache-read rate.
  9. Measured 2026-09-07: seven Haiku scouts under an about 80K Fable seat, and staggering lost about 4x. Fire them in one turn.
  10. Claude Code workflows stagger for you, with an about 5s hold on all but the first when model, effort, agent type, tools, schema and directory match.
  11. Sonnet-tier leaves take the plan task text.
  12. Cheap leaves take a compiled brief (brief.md) plus the smartexec protocol.
  13. Track leaves in run-state.md.
  14. Render one dispatch-board line, transitions only.
  15. End the turn while the wave is in flight.
  16. Shapes live in artifacts.md.

Step 4: verify

  1. Every Cheap result goes through fresh-context smartcheck (check.md), never the executor's context.
  2. The verifier is never weaker than the executor.
  3. Sonnet and Opus leaves get an Opus-or-comparable verifier.
  4. Exception: an Opus-or-stronger session reading the full diff may verify leaves it did not author.
  5. Self-review is the trap. "Looks done" is never a review.
  6. Scouting leaves produce no diff, so skip the protocol. The consumer spot-checks load-bearing facts (check.md Scouting).
  7. A C++ gamedev leaf layers cpp-gamedev-check.md under its Engine Profile (vanilla, custom, unreal, from the smartreview standards doc).

Step 5: integrate

  1. Integrate on the planner seat.
  2. Reconcile cross-leaf seams: naming drift, duplicate helpers, contracts.md mismatches, guessed imports.
  3. Integrate before human acceptance, including after a resume.
  4. Write 3 to 4 confidence notes for the human, as short plain full sentences.
  5. The notes cover what you are least sure of, what may surprise, what breaks later, and what was assumed.
  6. Put the recommendation inline, not dot-separated. The per-leaf half in check.md's Reflective sweep stays terse.
  7. At most one optional unrequested-improvement offer, never pre-built.
  8. One session-retro line: the worst friction plus an environment fix, as an executable check where it fits.
  9. A rule gap goes to "Evolving this skill".

Step 6: escalate

  1. Escalate on two strikes, exactly one tier, with the ESCALATION REPORT.

Fail-twice (canonical)

  1. A FAIL is a strike.
  2. Classify first. A 5xx or 529, a stop_reason refusal (Opus and Fable classifiers, HTTP 200), or max_tokens is infrastructure, not a strike.
  3. On infrastructure: check status.claude.com, back off, and never escalate a tier.
  4. On a refusal: re-brief fresh without the flagged text. Never resume.
  5. reasoning_extraction has no fallback.
  6. BLOCKED gets one same-tier retry with a repaired brief, resuming the same executor.
  7. SendMessage auto-resumes on 2.1.211 or later. Copilot uses --resume.
  8. Two strikes are two FAILs, a FAIL after a repaired BLOCKED, or two post-repair BLOCKEDs.
  9. Two strikes escalate exactly one tier with the report.
  10. A target above the session seat is asked first, with the report written (Seat ceiling).
  11. On a no, or on a Cheap seat: one fresh retry at the top tier is allowed, report attached, then return the best attempt with caveats (check.md).
  12. Never silently re-run. Never skip tiers.
  13. Counts persist in run-state.md.
  14. Terminal: an Opus strike-out means the orchestrator takes the leaf in-context, report attached.
  15. If the seat is below Strong, offer a stronger session first.
  16. The same arithmetic runs the inline route (SKILL.md Spiral guard).

Purpose

  1. Loaded by smartplan at flow step 1 when the tier is not obvious, or read for a routing or budget question.
  2. In: a task. Out: a tier plus effort, with its floor, under the escalation rule.
  3. Route by task class, not by vibes or by the loaded model.
  4. Every class has a floor: the cheapest tier that reliably lands it.
  5. Start at the floor. Escalate one tier only on fail-twice (canonical in flow.md).
  6. Never route above the floor "to be safe".
  7. Never route below the floor to save pennies.
  8. Never route above the session seat unasked (SKILL.md § Seat ceiling).
  9. Never make an initial pick above the incumbent's price (§ The cost ceiling).
  10. Floors are offered, never required. A declined or unserved tier falls to the strongest model on offer, said at the gate.
  11. "Never Cheap" means never while a stronger tier is offered.

3. Performance hot-path

  1. [G] A heap allocation sits inside a per-frame function or an inner entity loop.
  2. [G] A virtual call or std::function dispatch sits in a tight loop where the type is knowable.
  3. [G] A pass-by-value or push_back copies a non-trivial type where a move or const& would do.
  4. [G] A hot loop touches a few fields of a large AoS struct that is SoA-shaped.
  5. [G] A shared_ptr is copied across a per-frame boundary with no ownership transfer.
  6. [G] Logging or formatting sits on a hot path with no build-config guard.

4. Threading model

  1. [G] Shared mutable state is written from several threads with no lock or atomic.
  2. [G] Game-thread-only state is touched from a render or job thread.
  3. [G] An atomic memory order does not match its invariant, or a non-atomic access races an atomic write.
  4. [G] A blocking call runs on a worker thread or on the game thread's per-frame path.
  5. [G] A lambda captured by reference is queued to another thread with no outlives guarantee.
  6. [G] A lazy singleton or double-checked lock lacks an atomic or once guard.

5. Build and header hygiene

  1. [G] A header includes something used only in the .cpp, or relies on a transitive include.
  2. [G] A full type is included where a forward declaration would do.
  3. [G] A heavy header is pulled into a widely included header.
  4. [G] A non-inline function or variable is defined in a header, which risks an ODR violation.
  5. [G] A stable, widely used header is added per file instead of through the PCH.
  6. [U] A *.generated.h file is not the last include.
  7. [C] An engine-layer header is pulled into a lower layer that should not depend on it.

6. Determinism and serialization

  1. [G] Sim logic reads DeltaTime directly instead of a fixed timestep where determinism is needed.
  2. [G] A float comes from a platform-varying path with no bit-identical guarantee.
  3. [G] A save or replay format change has no version tag or upgrade path.
  4. [G] A static or singleton has no re-init path across hot-reload.
  5. [G] Non-deterministic container iteration feeds a saved, replayed or cross-client result.
  6. [G] A random source is not seeded per the determinism contract, such as a global rand().

What it does

  1. Review one changelist or fileset and report in three ranked categories.
  2. Two layers: a driver (ranking, protocol, report) and a swappable standards doc (checklist, tag legend, breaking classes, fill-once tokens).
  3. Rank before you report. A BREAKING buried under nits is not surfaced.
  4. BREAKING blocks the merge: crash, UB, memory or save corruption, data loss, hang, deadlock, memory-exhausting leak, desync, config-only build or link failure.
  5. PRACTICE is fix or file: API misuse, missing guard, avoidable allocation off the hot path, dead registration code, a trap.
  6. CONVENTION is fix in place: naming, formatting, comment style, ordering.
  7. Name the failure or demote. A BREAKING row states the concrete failure for the player, build, or save.
  8. If you cannot name the failure, it is PRACTICE.
  9. Inflating severity destroys the ranking's only value, and the reverse is worse.

Profile

  1. The {{STANDARDS}} token defaults to references/cpp-review-standards.md.
  2. A set path loads. An unset path asks: confirm the C++ default or take a path.
  3. Never guess the standards doc from file extensions.
  4. An unresolvable path: say so and stop.
  5. A Python or TypeScript project points {{STANDARDS}} at references/<lang>-review-standards.md. The driver is unchanged.
  6. Web UI ships its own doc, references/web-ui-review-standards.md.
  7. Three knobs: Indentation, Max line length, Local-variable case.
  8. The Epic example column is tabs (size 4), no max line length, PascalCase.
  9. The shipped "This project" column is unfilled on purpose, because the skill installs globally.
  10. Unfilled rows are N/A until filled, never guessed.
  11. Provenance is in references/cpp-review-standards.md § Provenance & Epic-standard validation.

Protocol

  1. The checklist has 5 items.
  2. Step 1: gather the files (VCS describe or diff, or user paths) and read them in full.
  3. Step 2: hunt breaking first, across every class {{STANDARDS}} names.
  4. The hunt is not checklist-driven. Read for what the code does: allocation owner, thread, failure path, malformed or stale input.
  5. A clean sweep is a result. Report it.
  6. Step 3: walk the checklist per file.
  7. Gate rows by the tag legend and profile selector.
  8. Every row is PASS, FAIL or N/A, never skipped.
  9. A FAIL files under the doc's severity map.
  10. Step 4: report with the template.
  11. A clean checklist does not replace the hunt, and a crash does not excuse the checklist. Both run.

Report

  1. The report template is fixed.
  2. An empty category prints its heading and none. Silence reads as not looked at.
  3. The standards line reads cpp-review-standards.md · Engine: vanilla (or custom, or unreal) when Engine is unset.
  4. smartreview is the merge gate over a whole fileset. smartcheck's cpp-gamedev-check.md is the verify seat over one leaf's diff.
  5. Both reuse the taxonomy through the standards doc.
  6. Name the category on every BREAKING row so reports collate on category · file:line.
  7. Mark rows already filed by a leaf's smartcheck as already-filed.
  8. Review away from the author: hand it to the smartplan-verifier seat, which loads the skill read-only.
  9. Fixes are always proposed, never applied by the reviewer.

Output register

  1. When the only reader is another model seat, free-text fields follow modes.md's caveman register.
  2. The free-text fields are <what's wrong> and <why unsure>, not counts, rule IDs or headings.
  3. The default for that case is max-savings (caveman ultra).
  4. That default replaces smartplan's per-harness shipped default, and the higher-set mode wins.
  5. Paths, rule IDs, quoted code, and the BREAKING failure description stay verbatim.
  6. Interactive output is full prose, per modes.md's human-facing floor.

vcs-adapters.md

  1. Load it only when the common path is not enough: detecting the VCS, shelved, pending, working-tree or PR work, scripting the gather, or a third VCS.
  2. IDENTIFY names the change, DESCRIBE lists it without diffs, DIFF covers text files, READ fetches a file at a revision.
  3. Detect Git: git rev-parse --is-inside-work-tree prints true, or a .git dir or file exists (worktrees and submodules use a file).
  4. Detect Perforce: p4 info succeeds, or P4CONFIG or P4PORT is set, or a .p4config sits above cwd.
  5. Perforce has no per-directory marker, so lean on p4 info.
  6. When both are present, the ref shape decides. Otherwise ask.
  7. The ref-shape table has five rows.
  8. Only bare digits are reliably Perforce. Hex, named, ranged or #-prefixed refs are Git.
  9. Perforce submitted: describe works fully.
  10. Perforce pending: describe -s lists files, and the description comes from p4 change -o <CL>'s Description field.
  11. Perforce shelved: -S lists shelved files and diffs against the depot.
  12. P4 DESCRIBE: p4 describe -s <CL>. -s means short, no diffs. Cap a huge CL with -m <max>.
  13. P4 DIFF: p4 describe <CL>. -du is a unified patch-compatible diff, -dc context, -ds summary counts. Shelved: p4 describe -S -du <CL>.
  14. P4 READ: p4 print -q //depot/path#rev. -q drops the header. Shelved: p4 print -q //depot/path@=<CL>.
  15. P4 scripting: prefix -ztag (p4 -ztag describe -s <CL>) for stable key/value output.
  16. P4 file types: text, binary, binary+l (exclusive lock, the norm for game assets so two people cannot edit one .uasset at once), +S (head revision only, purges older on submit).
  17. A binary* file cannot be diffed or read. Describe it from the name and CL description.
  18. Git single commit: git show -s --stat <ref>, git show --name-status <ref> (A/M/D), git show -s --format='%an %ad %s' <ref>. DIFF git show <ref>. READ git show <ref>:<path>.
  19. Git range: git log --stat <base>..<head> (or --name-status), git diff --name-status <base>..<head> for the net file list. DIFF git diff <base>..<head>. READ git show <head>:<path>.
  20. Git PR: gh pr view <n> --json title,body,author,files,commits. Request only the fields you need (also additions, deletions, changedFiles, baseRefName, headRefName).
  21. PR DIFF: gh pr diff <n>, with --exclude '<glob>' repeatable. PR READ: check out or fetch the head, then git show <headSha>:<path>.
  22. Git working tree: git status (--porcelain to parse). DIFF git diff unstaged, git diff --cached staged, git diff HEAD both against the last commit.
  23. Working-tree READ: the disk file is current, and git show HEAD:<path> is pre-change.
  24. Git raw binary (LFS off): the diff prints Binary files ... differ, --stat shows Bin, --numstat shows - -.
  25. Game projects almost always use LFS for .uasset and .umap (often .fbx, .wav, large media) via *.uasset filter=lfs diff=lfs merge=lfs -text.
  26. A pointer is three lines, so --stat shows a small count (such as 3 +++), not Bin.
  27. A Cheap executor trusting --stat will summarize the oid and size.
  28. The reliable signal is filter=lfs for the extension and a pointer body. Treat it as unreadable binary, like binary+l.
  29. LFS assets are lockable (git lfs lock) since binaries cannot merge.
  30. The binary table covers both VCS. The widget or level name plus description tells the reader what to look at. Never invent internal contents.
  31. A third VCS fills the same four verbs.
  32. Mercurial: hg root, hg log -v -r <rev> (with --stat), hg diff -c <rev> (or -r a:b), hg cat -r <rev> <path>.
  33. SVN: svn info, svn log -v -r <rev>, svn diff -c <rev>, svn cat -r <rev> <url/path>.
  34. If a verb is not cheap, approximate it (full diff, ignore hunks) rather than bend the Protocol.
