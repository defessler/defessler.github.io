StableActorId: How The System Works

References to one specific placed actor in Unreal Engine 5.8, keyed on the engine's per-placement guid, so they survive renames and the level-instance boundary where soft object paths break.

Motivation

The Problem: Paths Stop Being Identity

TSoftObjectPtr<AActor> is the standard way to point one actor at another across streaming boundaries. It works because an object path is normally two things at once. It's stable, which lets it survive a save and load round trip. It's also unique. Exactly one object answers to it.

Inside a level instance you lose both properties. A level-instance asset is saved once and placed N times. Every placement's contents share one authored path. That path can't tell placement 1 from placement 2. At runtime the level loads as an instanced package whose name is generated per placement. 

// Engine/Private/LevelInstance/LevelInstanceLevelStreaming.cpp
FString Suffix = FString::Printf(TEXT("%s_LevelInstance_%016llx_%d"),
    *ShortPackageName, LevelInstance->GetLevelInstanceID().GetHash(),
    LevelInstanceActor->GetWorld()->IsGameWorld() ? 1 : 0);

So the path you can author in the editor isn't the path the actor has at runtime. Each placement produces a different one. That trailing IsGameWorld() flag also means the editor path and the play path differ for the same placement. The engine's own actor locator concedes the point in a source comment, saying actors "should be relative to their level in order to support streaming within level instances, but world partition makes that impossible".

Renames and outliner moves break path references for the same underlying reason. The reference was keyed on something the editor is free to change. That's what shapes everything below. References that survive can't be paths.

Design

The Shape Of The Answer

StableActorId doesn't invent an identity. It keys every reference on the one the engine already keeps for each placement: the actor instance guid, which combines the guids of the level instances an actor sits in with the actor's own ActorGuid. Where the engine stamps nothing, which is a level instance open for editing, the plugin folds that value itself from the level-instance ancestors, so it holds in both modes. Three placements of one room give the door inside it three different values. Renaming or moving the door between outliner folders changes none of them.

We call each of those copies a "placement". A placement is one copy of an actor as it exists in the world, as opposed to the actor as it's saved in a level asset.

Nothing is minted. Nothing keys off labels or object paths. UStableActorIdLibrary::GetPlacementId is the one place that answers "which placement is this?". The resolver, the picker, the cook bake, and Data Validation all go through it.

Building Blocks

The Two Types

To use this system, you need to understand two main building blocks:

UStableActorIdComponent
The component you put on an actor. Any actor that has one can be referenced. You can add it to a class in C++ or a Blueprint, or to one placed actor in the level, engine classes included. It holds one field, PlacementId, which only the cook writes.
FStableActorRef
The reference you put anywhere that points at an actor. It's a plain value struct holding the target's placement id in TargetId, and the target's label and level-instance path from when the ref was made in CachedLabel and CachedLevelInstancePath.

The ref has the basics you'd expect from a handle, modeled on FMassEntityHandle: IsSet, Reset, ==, <, GetTypeHash, and ToString. Two refs are equal when they point at the same actor, whatever their labels say. That lets a ref work as a TSet element or a TMap key in C++ and in Blueprint.

Data

Where The Data Lives

Every piece of saved data is an ordinary UPROPERTY that saves with whatever object owns it.

The target's identity
Not stored by the plugin in the editor at all. It's the engine's own ActorGuid, saved in the actor's level package or its external actor package, plus the level-instance chain the engine already tracks.
PlacementId
On the component. Empty in every editor-saved package. The cook fills it so a packaged build can still answer which placement an actor is.
TargetId and the cached labels
On the ref, saved as tagged properties inside whatever owns the ref: an actor, a component, a data asset, a Blueprint default, or a save game.

A ref never stores a pointer to its target. It can't dangle. It never stores an object path either, which is what breaks under level-instance path mangling.

Both cached labels save in every build configuration, since a UPROPERTY can't be compiled out of Shipping alone and every configuration loads the same cooked data. Shipping empties them as each ref loads.

Runtime

Resolution: Unique, Or Nothing

Each UStableActorIdComponent registers itself with its world's UStableActorIdSubsystem in OnRegister and leaves in OnUnregister. Components register when their level becomes visible and unregister when it's hidden, unloaded, or destroyed. The subsystem holds exactly the stable actors in loaded, visible levels. It mirrors what's loaded and never assigns anything.

GetActorFromStableActorRef resolves a ref in a few steps:

  1. Refuse an unset ref. An invalid guid would match every actor that has no instance guid.
  2. Find the world from the context object.
  3. Ask that world's subsystem for the stable actor whose placement id matches TargetId.
  4. Return null the moment a second actor matches.
  5. If you passed an actor class, the match has to be that class or a subclass.

The resolver never picks one actor out of several. Acting on an arbitrary one of two is worse than acting on nothing, since nothing would tell the caller the answer was a guess. With per-placement guids a collision should be rare. Data Validation reports one as an error long before a resolve hits it. 

if (ADoorActor* Door = UStableActorIdLibrary::ResolveStableActorRef<ADoorActor>(this, TargetDoor))
{
    Door->Open();
}

In Blueprint the node is "Get Actor From Stable Actor Ref". Its output pin takes the class you pick. Each world has its own subsystem. The editor world and every PIE world resolve separately. PIE copies keep the editor actor's guid, which lets a ref picked in the editor find the PIE copy of the same actor.

Packaged Builds

Surviving The Cook

In a cooked build the engine releases each actor's instance guid in AActor::PostRegisterAllComponents, long before gameplay can ask for it. So the editor module copies the guid onto the actor while the cook can still read it. On a cooking save it writes the live value into the component's PlacementId. It restores the editor copy after each package saves and again when the cook finishes. The engine's USmartObjectComponent::PreSave does the same thing, for the same reason.

In a packaged build the library reads that baked value. If the actor's level has a level-instance guid, it folds that guid back in first. A Standalone level instance cooks as its own asset. Nothing stamps an instance guid when that happens. The bake only captures the actor's own half. Embedded and Partitioned content bakes an absolute value instead.

IMPORTANT:

Don't simplify the fold to a plain read. It breaks cooked Standalone level instances and nothing else. That makes it easy to miss. StableActorId.Cooked.BakedRead catches a plain read at time of writing.

Workflow

Using It

Make An Actor Referenceable

Add a UStableActorIdComponent. In a Blueprint, use "Add Component" and pick "Stable Actor Id". There's nothing to fill in.

Point At One

An FStableActorRef property shows up as one row with a picker and a clear button. The picker is a Scene Outliner filtered to actors a ref can point at. Level instances expand like folders, which lets you pick one placement. Add AllowedClasses metadata to limit what it offers. 

  Target Door      [ BP_Door  Wing_A.Room_3      ▾ ] [✕]

Resolve At The Moment Of Use

Call the resolver on events, like an overlap or an interaction. Don't cache the pointer it returns. An unresolved ref keeps its guid and starts resolving the moment the target's level streams in.

Check out the tutorial for the full walkthrough.

Content Checks

Data Validation

UStableActorIdValidator plugs into the engine's Data Validation. "Validate Data", validate-on-save, and the commandlet all run it. It indexes every loaded actor by placement id, then checks each stable actor and each ref against that index, including refs inside containers, nested structs, and components.

  • Errors: a PlacementId a cook left in editor data, a placement id two stable actors share, a ref that matches several actors, a ref to an actor with no component, a ref to a child actor, and a ref outside its AllowedClasses.
  • Under World Partition, a ref whose target exists nowhere in the world, loaded or not. It rebuilds every placement id from the actor descriptors and only reports when that rebuilt set agrees with the loaded actors.
  • Warnings: two components on one actor, a stable actor with no instance guid, and outside World Partition, a ref that matches nothing loaded.

Status

What We've Verified

Editor and PIE resolution - covered by StableActorId.Resolve, including the class filter, two components on one actor, and a destroyed actor dropping out.
Containers - covered by StableActorId.Containers, native and reflected sets and maps.
The cook bake - covered by StableActorId.Cooked.Bake and StableActorId.Cooked.BakedRead, which drive the save hook with a synthesized cooking context.
Data Validation - covered by StableActorId.Validation outside World Partition.
A packaged build resolving a baked ref - not yet run. It needs a host with stable actors inside a level instance and a full cook.
The World Partition broken-ref check - untested. It needs a saved World Partition map with stable actors in it.

History

Decisions And Rejected Paths

The plugin started as NamedIds, a larger system with minted 8-byte handles, display names, and a Universal Object Locator fragment for crossing level instances. All placements of a level instance shared one authored handle. Ambiguity was the normal case. In October 2026 we cut it to keying on the engine's instance guid, which already tells placements apart. That took it from about 4,300 lines to under 1,000.

A struct property as the opt-in
Replaced by the component, which can register itself. A struct can't run code when its actor loads. Every resolve used to walk every actor in the world as a result.
A registry that assigns ids
Rejected early on. The subsystem only mirrors what's loaded and assigns nothing.
Our own guid plus FActorContainerID
Rejected for now. A component can't read its container id in a cooked build for Embedded and Partitioned content. It only removes the bake where we've already handled things without one.
Reading the guid at load instead of baking it
Backlogged. The component's OnRegister runs before the engine releases the value, which means it could capture it directly. That needs a cooked run to prove.

Next

Open Questions

  • A cooked acceptance run, which would also show whether the load-time capture can replace the bake.
  • A saved World Partition test map, so the broken-ref check gets a real test.
  • "Move to Level", "Create Level Instance", and "Break" give an actor a new guid and break refs to it. Data Validation now reports that under World Partition. An in-editor warning at the moment it happens would be friendlier.
